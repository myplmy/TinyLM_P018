## 1. 논문이 실제로 한 일 — "전부 FP8" 이 아니다

### 1.1 FP8 로 내린 것 / 고정밀도로 남긴 것 (A §3.3.1)

| | 정밀도 | 논문의 근거 |
|---|---|---|
| **Linear 의 GEMM 3개** — Fprop · Dgrad(활성 역전파) · Wgrad(가중치 역전파) | **FP8 (E4M3)** | "compute-density operations". 이론상 **연산속도 2배** |
| **임베딩 모듈** | BF16/FP32 | *"sensitivity to low-precision computations"* |
| **출력 헤드**(lm_head) | BF16/FP32 | 〃 |
| **MoE 게이팅** | BF16/FP32 | 〃 (우리에겐 해당 없음) |
| **정규화 연산**(RMSNorm 등) | BF16/FP32 | *"low-cost operators can also utilize a higher precision with a negligible overhead"* |
| **어텐션 연산** | BF16/FP32 | 〃 |
| **master weight · weight gradient · optimizer state** | 고정밀 | *"To further guarantee numerical stability"* |

> ★**핵심 문장 그대로**: *"after careful investigations, we maintain the original precision
> (e.g., BF16 or FP32) for the following components: the embedding module, the output head,
> MoE gating modules, normalization operators, and attention operators."*
>
> 즉 **선택 기준은 "중요도" 라는 모호한 말이 아니라 두 가지 구체적 기준**이다 —
> ① **저정밀도에 민감한가**(임베딩·헤드·어텐션·게이팅) ② **연산량이 작아서 고정밀로 둬도
> 전체 비용에 영향이 없는가**(정규화). 나머지 = **연산량이 크고 민감하지 않은 것 = Linear GEMM.**

### 1.2 정확도를 지킨 네 장치 (A §3.3.2)

| 장치 | 내용 | 왜 필요했나 |
|---|---|---|
| **미세 입도 양자화**(fine-grained) | **활성 1×128 타일**(토큰당·128채널) / **가중치 128×128 블록** | 텐서당 스케일 1개면 **활성 이상치 하나가 전체를 망친다** |
| **누산 정밀도 승격** | Tensor Core 에서 **N_C=128 원소마다** CUDA Core FP32 레지스터로 옮겨 누산 | Hopper Tensor Core 는 **가수 13비트(FP22)** 만 유지 → K=4096 에서 **상대오차 최대 2%** (B §3.1.1) |
| **E4M3 단일 포맷** | 종전 관행(Fprop E4M3 / 역전파 E5M2)과 달리 **전 텐서 E4M3** | 미세 입도가 지수부를 그룹끼리 공유해 동적범위를 대신 감당 |
| **온라인 양자화** | 타일/블록마다 amax 를 **그 자리에서** 계산(delayed scaling 안 씀) | 스케일 정확성 + 프레임워크 단순화 |

### 1.3 저장·통신 (A §3.3.3) — **속도가 아니라 메모리 이야기**

| 항목 | 정밀도 | 논문 문구 |
|---|---|---|
| **AdamW 1·2차 모멘트** | **BF16** | *"without incurring observable performance degradation"* |
| master weight · 누적 gradient | **FP32 유지** | 수치 안정성 |
| backward 용 활성 캐시 | **FP8** | Wgrad 가 FP8 이므로 자연스러운 선택 |
| ⚠️ **어텐션 뒤 Linear 의 입력 활성** | **커스텀 E5M6** | 어텐션 backward 에도 쓰여 **정밀도에 민감** |
| ⚠️ SwiGLU 입력 | FP8 캐시 + **backward 에서 재계산** | 메모리/정확도 절충 |

### 1.4 검증 규모와 결과

- 16B(1.33T 토큰) · 230B(0.9T 토큰) MoE 두 규모로 BF16 대비 검증(A 부록 B.1, B §2.4)
- **BF16 대비 상대 손실 오차 < 0.25%** — "학습 난수성 범위 안"
- ⚠️ **음성 결과도 있다**(A 부록 B.2): 활성 **gradient** 를 가중치처럼 128×128 **블록** 단위로
  양자화하니 **16B 모델이 300B 토큰에서 발산**했다. Dgrad 는 토큰 상관 이상치 때문에
  블록 양자화로 감당이 안 된다 → **1×128 타일이어야 한다.**

## 2. ★우리 구조에 대응시키면 — 매핑표

우리 모델(`m100R1c`)의 모든 Linear 는 `TLinear` 이고 `forward` 는 `F.linear(x, wq)` 하나다.
`wq` 는 **삼진 STE 출력**이다.

| DeepSeek-V3 의 구분 | 대응하는 우리 모듈 | 현재 정밀도 | FP8 후보인가 |
|---|---|---|---|
| Linear GEMM(FP8) | `MLP.gate_proj/up_proj/down_proj` (`TLinear`) | bf16 autocast | ✅ **1순위**(FLOPs 대부분) |
| Linear GEMM(FP8) | `Attention.q/k/v/o_proj` (`TLinear`) | bf16 autocast | ⚠️ **2순위** — 논문은 "attention operators" 를 고정밀로 남겼지만 그건 **SDPA·softmax** 지 q/o 투영이 아니다. **구분해서 읽어야 한다** |
| 어텐션 연산(고정밀) | `F.scaled_dot_product_attention` · QK-norm | 이미 별도 | 🚫 **손대지 않는다** |
| 정규화(고정밀) | `RMSNorm` (내부가 이미 `.float()`) | **이미 fp32** | 🚫 이미 논문 권고대로다 |
| 임베딩(고정밀) | `nn.Embedding` + `emb_up` | fp32 | 🚫 **특히 우리는 헤드와 tie** 돼 있다(결과 025) |
| 출력 헤드(고정밀) | `F.linear(F.linear(x, emb_up.T), emb.weight)` | fp32 | 🚫 위와 같은 텐서다 |
| optimizer state(BF16) | `torch.optim.AdamW(fused=True)` | **fp32** | ✅ **별개 레버**(§4) |
| master weight(FP32) | `TLinear.weight` (latent) | fp32 | 🚫 유지 |

## 3. ★★가장 중요한 발견 — **가중치 쪽 양자화 오차가 우리는 정확히 0 이다**

논문이 가중치를 128×128 블록으로 스케일한 이유는 **fp32/bf16 가중치를 FP8 로 눌러 담을 때
생기는 오차**를 줄이려는 것이다. **우리는 그 오차가 원리적으로 0이 될 수 있다.**

어닐 완료(`anneal ≥ 1`) 시점의 우리 가중치는

```
wq[o, i] = sign[o, i] × α[o, g(i)] ,   sign ∈ {−1, 0, +1} ,   g = micro_group = 128
```

이고, **α 로 나누면 값이 정확히 {−1, 0, +1} 세 개뿐**이다.
E4M3 는 −1·0·+1 을 **정확히** 표현한다(가수 3비트가 남아돈다).
따라서 **스케일 입도가 우리 α 입도(행 × 128입력채널)와 같기만 하면 가중치 FP8 왕복 오차 = 0.**

| | DeepSeek-V3 | **TinyLM** |
|---|---|---|
| 가중치 스케일 입도 | 128 × 128 **블록** | **행 × 128** (더 미세) |
| 스케일 개수(mC 기준) | — | **약 428,000개** (결과 028) |
| 가중치 FP8 양자화 오차 | 작지만 **0 아님** | ★**정확히 0**(스케일 입도가 맞을 때) |
| 활성 스케일 입도 | 토큰 × 128 채널 | 같게 하면 됨 |
| 누산 승격 간격 N_C | **128** | **micro_group 이 이미 128** — 우연히 일치 |

> ★★즉 **논문이 공들여 만든 "미세 입도 가중치 양자화" 를 우리는 이미 갖고 있다.**
> 우리 삼진 양자화의 α 그룹이 정확히 그 역할을 한다. **논문의 절반이 공짜로 성립한다.**
> 남는 오차원은 **활성 쪽과 누산 쪽 둘뿐**이다.

### 3.1 ⚠️ 그런데 바로 그 지점이 최대 장벽이다

논문 본문이 스스로 적어 놓았다(A §3.3.2):

> *"One key modification in our method is the introduction of per-group scaling factors along
> the **inner dimension** of GEMM operations. **This functionality is not directly supported in
> the standard FP8 GEMM.**"*

**GEMM 의 K축(내부 차원)을 따라 그룹 스케일을 주는 것은 표준 FP8 GEMM 이 지원하지 않는다.**
그래서 DeepSeek 은 **CUTLASS 커널을 직접 만들었다**(DeepGEMM, B §3.1).
그리고 우리 α 는 **정확히 K축 방향 그룹 스케일**이다.

`torch._scaled_mm` 이 지원하는 것은 통상 **per-tensor** 와 **per-row(rowwise)** 다.
결과 010 은 **per-tensor** 로 1.63~2.08× 를 쟀다. 그러면 갈림길은 이렇다:

| 경로 | 가중치 FP8 오차 | 실현 가능성 |
|---|---|---|
| **per-tensor 스케일** | 크다 — α 가 텐서 1개로 뭉개진다 | ✅ 오늘 가능(결과 010) / 🚫 **품질 근거가 이미 부정적**: 결과 028 이 per-tensor α 를 **+0.0465~+0.0862 bpb = 0.141~0.261 nats(최대 21.7σ)** 로 측정했다 |
| **per-row 스케일** | 중간 — α_g / α_row 비가 E4M3 가수 3비트로 반올림 | ⚠️ `_scaled_mm` 의 rowwise 가 **sm_89 에서 되는지 미확인** / 품질은 **미측정**(결과 028 의 per-row 는 α **재추정**이지 E4M3 **반올림**이 아니다 — 다른 오차원) |
| **per-(row × 128) 블록 스케일** | **0** | 🚫 `_scaled_mm` 미지원 가능성 높음 → **CUTLASS 커널 자체 제작**. P014B 에서 우리가 **접기로 한 길**이다 |

> ★**결론의 뼈대**: *"가능한가"* 의 답은 **"수치적으로는 우리가 논문보다 유리한데, 그 유리함을
> 쓰려면 논문이 만든 것과 같은 커널이 필요하다"** 이다. 그래서 **먼저 재야 할 것은
> 속도가 아니라 "거친 스케일로 내려갔을 때 E4M3 반올림이 얼마나 아픈가" 다.**
> 그건 **학습 0 · GPU 수 분**에 잴 수 있다 → **P022B 단계0.**

## 4. 논문에서 **지금 당장 값싸게 가져올 수 있는 것** — FP8 GEMM 이 아니다

우리 프로젝트의 1순위는 `CLAUDE.md` 첫 줄대로 **연산이 아니라 메모리**다.
논문 §3.3.3 은 **속도가 아니라 메모리** 절이고, 여기에 우리에게 맞는 항목이 있다.

| # | 논문 항목 | 우리 기대 효과 | 구현 비용 | 판정 |
|---|---|---|---|---|
| **M1** | **AdamW 모멘트를 BF16 으로** (master weight·gradient 는 FP32 유지) | mC 학습 파라미터 약 **63.5M** × 4B × 2모멘트 = **508MB** → **254MB 절감** | ⚠️ **중** — `torch.optim.AdamW(fused=True)` 는 상태를 파라미터 dtype 으로 만든다. **커스텀 스텝이 필요**하고 틀리면 **조용히 발산**한다 | ⏸ **P022B 단계2 설계만.** 구현 선결 |
| M2 | backward 활성 캐시를 저정밀로 | grad-ckpt 를 끄고도 VRAM 절감 | 대 | 🚫 지금 아님 |
| M3 | 통신 압축(LogFMT 등) | **해당 없음** — 단일 GPU | 0 | 🚫 |

### 4.1 M1 과 P042 를 합치면 `--no-ckpt` 가 열리는가 — **아니다. 산술을 미리 적는다**

| 항목 | 회수량 |
|---|---:|
| P042 교사 latent 해제 | **472.5 MiB** |
| M1 AdamW 모멘트 BF16 | **약 254 MB** |
| **합계** | **약 0.73 GB** |
| 필요량(15.7GB → 스필벽 13~14GB) | **1.7 ~ 2.7 GB** |

> ★**둘을 다 해도 부족하다.** P042 §3 이 P3 를 "가장 불확실" 이라 적은 판단은 여전히 유효하고,
> **M1 은 그 판단을 뒤집지 못한다.** M1 의 값어치는 `--no-ckpt` 가 아니라 **여유 VRAM 자체**
> (더 큰 M, 또는 P049 의 36층 구성)에 있다.
> ⚠️ 다만 **결과 033 이 타잉 VRAM −35.3%(7.82→5.06GB)** 를 실측했으므로 **tied 쪽 실측 15.7GB
> 자체가 낡았을 수 있다.** 그것부터 P042 단계1 이 잰다 — **M1 을 구현하기 전에 단계1·2 결과를 본다.**

## 5. 우리 스케일에서 FP8 이 값어치가 있는가 — 정직한 산술

결과 010 이 이미 잰 것: 순수 GEMM **1.63~2.08×**, 그러나 **GEMM 은 스텝의 약 50%** →
**end-to-end −15% 내외(상한 −23%)**. 표준 런 117분 → 약 99분 = **18분 절감**.

여기에 이 검토가 더하는 것:

| # | 논문이 알려준 것 | 우리에게 미치는 영향 |
|---|---|---|
| a | Hopper Tensor Core 누산은 **가수 13비트**뿐, K 가 크면 오차가 커진다(B §3.1.1) | ★**우리는 유리하다** — K = 768 / 2048 이고 논문 예시는 K=4096 이다. **승격 커널 없이도 견딜 여지**가 논문보다 크다 |
| b | 미세 입도 양자화의 **역양자화 오버헤드**가 Tensor Core → CUDA Core 데이터 이동을 만든다(B §3.1.1) | ⚠️ **우리도 똑같이 낸다.** 결과 010 §2-(3)c 가 추정한 "절감의 30~40% 잠식" 과 같은 항목 |
| c | **온라인 양자화**로 충분(delayed scaling 불필요) | ✅ 구현이 **단순해진다** — 결과 010 §4 가 "delayed scaling 필요" 로 잡아 둔 공수가 **줄어든다** |
| d | Dgrad 를 블록 양자화하면 **발산**(A 부록 B.2) | ⚠️ **설계 제약**: 활성 gradient 는 반드시 **1×128 타일**. "가중치처럼 하면 되겠지" 를 **미리 막아 준다** |
| e | 상대 손실 오차 **< 0.25%** | 우리 기준선 3.6442 nats 의 0.25% = **0.0091 nats** = **분해능 0.024 의 38%**. → **품질 대가는 분해능 안에 들어올 가능성이 높다**(단 그건 128블록 + 승격 커널을 갖춘 논문 조건에서다) |

> ★**판정은 뒤집히지 않는다.** 2026-08-06 의 P022 판단(*"지금 구현하지 않는다"*)은 **그대로 유효**하다.
> 이유가 **하나 더 늘었다**: 우리 α 를 살리려면 **K축 그룹 스케일 GEMM 이 필요**하고,
> 그건 **P014B 에서 접기로 한 것과 같은 종류의 커널 작업**이다.
>
> **그러나 검토 결과 "값싼 선행 질문" 이 하나 생겼다** — *거친 스케일(per-row/per-tensor)로
> E4M3 반올림을 받으면 우리 모델이 얼마나 나빠지는가.* 이건 **학습 0, GPU 수 분**이고
> **답이 "거의 안 나빠진다" 면 커널 없이 FP8 이 성립**한다. → **P022B.**

## 6. 결론

| 질문 | 답 |
|---|---|
| **논문 방식(선택적 FP8)을 우리도 할 수 있는가** | ⚠️ **원리적으로는 우리가 더 유리하다.** 삼진 가중치는 E4M3 로 **오차 0**이고, α 그룹(128)이 논문의 미세 입도와 **이미 같다** |
| **오늘 그대로 이식 가능한가** | 🚫 **아니다.** 우리 α 를 살리는 K축 그룹 스케일 FP8 GEMM 은 **표준 연산에 없다**(논문도 커널을 직접 만들었다) |
| **거친 스케일로 타협하면?** | ❓ **미측정.** per-tensor 는 결과 028 이 이미 **부정적**(0.141~0.261 nats). **per-row + E4M3 반올림은 아무도 안 쟀다** — 이게 P022B 단계0 |
| **지금 값어치가 있는가** | 🚫 **속도는 아니다**(표준 런 18분, 메모리 목표와 무관). ✅ **단 §4 의 M1(BF16 옵티마이저 상태)은 메모리 목표에 직결**되고 논문이 "성능 저하 관측 안 됨" 을 1T 토큰 규모로 보증한다 |
| **무엇부터 하는가** | **P022B 단계0**(GPU 수 분, 학습 0) → 결과에 따라 단계1(FP8 GEMM) 또는 종결. **M1 은 P042 단계1·2 결과를 본 뒤** |

## 7. 인용 시 주의

- **"1.9× 가속" 을 인용하지 말 것.** 우리 실측은 **순수 GEMM** 이고 end-to-end 는 **−15% 내외**다(결과 010).
- **"논문은 FP8 로 학습했다" 를 인용하지 말 것.** 논문은 **Linear GEMM 3개만** FP8 이고
  임베딩·헤드·어텐션·정규화·master weight·optimizer state 는 **전부 고정밀**이다(A §3.3.1).
- **"상대 오차 0.25%" 는 128블록 + CUDA Core 승격 + 온라인 양자화가 모두 갖춰진 조건**의 값이다.
  그중 하나라도 빼면 그 수치를 인용할 수 없다(부록 B.2 가 실제로 발산 사례를 준다).
- 논문의 하드웨어 한계 서술(FP22 누산·역양자화 오버헤드)은 **Hopper(H800)** 기준이다.
  우리는 **Ada sm_89** 이고 **같다는 보장이 없다** → P022B 단계0 이 실측한다.

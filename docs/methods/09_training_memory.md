# 09 — 학습 시 VRAM 상주 메모리 (방법론 원장)

> **신설 2026-08-08.** 사용자 요청: *"학습시 vram 상주 메모리 값을 줄일 수 있는 방법 검토 및 분석."*
> **living document** — 항목을 적용·측정할 때마다 이 표에 행을 추가·갱신한다.

⚠️ **이 문서는 "배포 메모리" 가 아니다.** 배포(packed/상주)는 `docs/METHODS.md` 와 P034 계열이다.
여기는 **학습 중 GPU 에 잡혀 있는 것**만 다룬다. 두 축은 **거의 겹치지 않는다** —
`micro_group`(P051)은 배포를 −3.6% 줄이고 학습 VRAM 은 **0** 이다. 반대로 KD 교사는 학습 VRAM 을
**+5.5 GiB** 쓰고 배포에는 **없다.** **섞어 인용하면 틀린다**(함정 1 의 학습판).

## 1. ★먼저: 우리 학습 VRAM 은 무엇으로 이루어져 있나 (실측 분해)

전부 **M = micro_bs × seq = 8,192**, `m100R1c`(tied g8, 63.5M), 250스텝, RTX 4070 Ti SUPER 16GB.
**reserved 는 OOM 예산**, **alloc 은 "무엇이 얼마나" 를 보는 값**이다.

| # | 구성 | reserved | **alloc** | 직전 대비 alloc | 근거 |
|---|---|---:|---:|---:|---|
| a | tied 단독, ckpt ON, **KD 없음** | 5.06 | **4.55** | — | 결과 033 `ts_g8` |
| b | a + **KD dense 교사** | 12.47 | **10.03** | ★**+5.48** | 결과 034 §9 `mC_tinf_off` |
| c | b + `--kd-teacher-infer` | 11.45 | **9.55** | **−0.48** | 결과 034 §9 `mC_tinf_on` |
| d | b 의 교사를 **압축 교사**로 | **10.59** | **9.52** | **−0.51**(reserved **−1.88**) | 결과 037 §3 `mC_ct250` |
| e | c + **`--no-ckpt`** | **15.37** | **14.00** | **+4.45** | 결과 034 §10 |
| (참고) dense 단독, ckpt ON, KD 없음 | 7.82 | 5.95 | | 결과 033 `ts_dense` |

### 1.1 ★★가장 큰 단일 항목은 모델도 옵티마이저도 아니다 — **KD 손실 계산**이다

**b − a = +5.48 GiB.** 그런데 **dense 교사의 파라미터 상주는 945 MiB 뿐**이다
(삼진 latent 123.86M×4B = 472.5 MiB + dequant 사본 472.5 MiB).
**나머지 약 4.5 GiB 는 파라미터가 아니다.**

`torch.autocast(bfloat16)` 아래에서 `cross_entropy`·`log_softmax`·`softmax` 는
**autocast 의 fp32 목록**에 있다. `M × V = 8192 × 32768` 이므로:

| 텐서 | dtype | 크기 | backward 위해 보존 |
|---|---|---:|---|
| 학생 `logits` | bf16 | **512 MiB** | ✅ |
| `F.cross_entropy` 내부 log_softmax | fp32 | **1024 MiB** | ✅ |
| `logits / T` | bf16 | 512 MiB | 임시 |
| `F.log_softmax(logits/T)` | fp32 | **1024 MiB** | ✅ |
| 교사 `tlog` | bf16 | 512 MiB | 임시 |
| `F.softmax(tlog/T)` | fp32 | **1024 MiB** | 임시 |
| `F.kl_div` 원소별 | fp32 | **1024 MiB** | 임시 |
| | | **피크 ≈ 5.1 GiB** | |

**회계가 실측 +5.48 GiB 와 맞는다.**
그리고 결과 034 §10 의 OOM 이 요구한 **`Tried to allocate 1024.00 MiB`** 가 **이 표의 한 줄**이다
(= `8192 × 32768 × 4B`, 정확히).

> ★★★ **결론: 우리 학습 VRAM 의 최대 단일 항목은 "어휘 전체 위의 KD 손실 계산" 이다.**
> **이 저장소는 그것을 한 번도 본 적이 없다.** 지금까지 메모리 논의는 전부 **배포** 축이었다.

### 1.2 나머지 항목의 자릿수

| 항목 | 크기 | 근거 |
|---|---:|---|
| 학생 파라미터(fp32 latent + dequant 사본) | **451.5 MB** | `report()` 상주 |
| AdamW 상태 2벌(fp32) | **약 508 MB** | 63.5M × 2 × 4B |
| dense 교사 파라미터 | **945 MiB** | 위 |
| **KD 손실 영역** | **약 5.1 GiB** | §1.1 |
| grad-ckpt OFF 시 추가 활성 | **+4.45 GiB** | e − c |

## 2. 레버 표 — **실측된 것과 계산만 된 것을 구분한다**

| # | 레버 | 절감(reserved) | 대가 | 상태 | 근거 |
|---|---|---:|---|---|---|
| **L1** | **압축 교사** `--kd-teacher-tag mC_wsd` | **−1.88 GiB** | **품질 −0.0220**(오히려 좋다) · 속도 무변 | ✅ **실측·채택 권고** | 결과 037 |
| **L2** | **`--kd-teacher-infer`** | **−1.03 GiB** | 없음(속도 측정 불가 수준) | ✅ **실측·채택 권고** | 결과 034 §9 |
| L3 | `M` 8192 → 4096(`--micro-bs 4 --accum 32`) | 활성 전부 절반 | **속도 −8.7%** | ✅ 실측(결과 007) | 007 |
| **L4** | **AdamW 상태 bf16** `--opt-dtype bf16` | **약 −254 MB** | 미측정. 조용한 발산 위험 | ⏸ **구현 완료·미실행** | P022B 단계2 |
| **L5** | **KD 손실 청크 분할** | ★**−2 ~ −3 GiB 추정** | 구현 중. 속도 영향 미지 | 🚫 **미구현** | §3 |
| L6 | 교사 softmax 를 bf16 으로 | **약 −512 MiB** | 비트 동일 아님. KL 타깃 정밀도 | 🚫 미구현 | §3.2 |
| L7 | `--kd-every 8` | 교사 forward 1/8 — **피크는 안 변한다** | 품질 미측정 | 🚫 미측정 | P042 §7-C |
| L8 | 교사 `to_int8()` | 약 −350 MB | CUDA 언팩 −12~15% × 1/4 | 🚫 미구현 | P042 §7-A |
| L9 | `PYTORCH_ALLOC_CONF=expandable_segments:True` | 단편화분(**관측 1.71 GiB**) | 없음 | ⏸ **미적용·권고** | 결과 034 §10.1 |

> ⚠️ **L7 은 피크를 안 줄인다.** `--kd-every` 는 KD 스텝의 **빈도**를 줄일 뿐이고
> **peak 는 KD 가 도는 그 스텝이 정한다.** 벽시계는 줄지만 **VRAM 예산은 그대로**다.
> **이걸 메모리 레버로 인용하면 틀린다.**

### 2.1 ★조합 산술 (계산값 — 미실측)

현재 표준(`b`, ckpt ON) 12.47 GiB 에서:

```
L1 압축 교사      −1.88
L2 교사 추론모드   −1.03   (★단 L1 과 겹칠 수 있다 — 둘 다 교사 쪽이다)
L4 옵티마이저 bf16 −0.25
                 ------
추정               약 9.3 GiB    → --no-ckpt(+4.45) 를 얹어도 약 13.8 GiB
```

**여유 약 2.2 GiB.** 결과 034 §10 의 15.37 GiB(여유 0.62)보다 훨씬 안전하다.

⚠️ **L1+L2 의 중복은 미측정이다.** 둘 다 교사의 메모리를 건드리므로 **단순 합산이 과대일 수 있다.**
→ **P018 단계2 가 그 조합을 실측한다.**

## 3. 미구현 레버의 설계 — **L5 가 가장 크다**

### 3.1 L5: KD 손실을 토큰 축으로 청크 분할

현재(`trainer.py`):

```python
logits = model(x)                                     # (B,T,V)
ce = F.cross_entropy(logits.reshape(-1, V), y.reshape(-1))
tlog = teacher(x)
kl = F.kl_div(F.log_softmax(logits.reshape(-1,V)/T, -1),
              F.softmax(tlog.reshape(-1,V)/T, -1), reduction="batchmean") * T*T
loss = ((1-a)*ce + a*kl) / accum
loss.backward()
```

**전체 8,192 토큰 × 32,768 어휘를 한 번에** 만든다. 청크 `C`(예: 1,024 토큰)로 쪼개
**부분 손실마다 backward** 하면 fp32 대형 텐서가 **C/8192 배**로 준다.

| 청크 | fp32 텐서 하나 | 추정 손실영역 피크 |
|---|---:|---:|
| 8192(현재) | 1024 MiB | 약 5.1 GiB |
| 2048 | 256 MiB | 약 1.8 GiB |
| **1024** | **128 MiB** | **약 1.2 GiB** |

★**−2 ~ −3 GiB 추정.** 우리가 가진 어떤 레버보다 크다.

⚠️ **선결·리스크**:
- `lm_head` 가 임베딩과 tie 돼 있어 **청크마다 같은 가중치에 gradient 가 누적**된다.
  수학적으로는 동일하지만 **누적 순서가 달라져 비트 동일이 아니다.**
- `reduction="batchmean"` 의 정규화를 **청크 간에 일관되게** 유지해야 한다(가중 평균).
- `torch.compile` 과의 상호작용 미검증. 그래프가 C 배로 늘어난다.
- **구현 난이도 중.** 커스텀 autograd 또는 `torch.utils.checkpoint` 기반.

> **그래서 지금 배치를 만들지 않는다**(`ai_dev_tool/03` §1). **설계만 남긴다.**
> 착수하면 **게이트는 "손실 값이 청크 크기와 무관하게 같은가"**(비트 동일 아님 → 4자리 일치).

### 3.2 L6: 교사 softmax 를 bf16 으로

`F.softmax(tlog/T, -1)` 는 **no-grad 타깃**이다. autocast 가 fp32 로 올리는데,
KL 타깃으로만 쓰이므로 bf16 이면 **1024 → 512 MiB**.
⚠️ **비트 동일이 아니다** — 확률값의 가수가 8비트가 된다. 작은 확률에서 상대오차가 커진다.
**게이트: 250스텝 손실이 4자리 일치.**

### 3.3 L9: 단편화 대책

결과 034 §10.1 의 OOM 메시지가 **직접 권고**했다:

```
1.71 GiB is reserved by PyTorch but unallocated.
If reserved but unallocated memory is large try setting
PYTORCH_ALLOC_CONF=expandable_segments:True to avoid fragmentation.
```

**1.71 GiB 가 단편화로 죽어 있었다.** 배치 진입점에서 환경변수 한 줄이다.
⚠️ **성능 영향은 미측정**(일반적으로 무시할 수준이라고 알려져 있으나 우리 워크로드에선 미확인).

## 4. ★스필(시스템 메모리 대체) 정책 — **권고: 금지**

> 사용자 질문: *"OOM 발생하지 않도록 시스템 메모리 대체 정책 기본값으로 설정해야 할지,
> 아니면 메모리 스필링을 아예 방지하도록 시스템 메모리 비대체 선호로 하는 것이 나을지."*

### 4.1 우리가 관측한 것

| 런 | reserved | 스필 | 정상상태 ms/step | ckpt ON 대비 |
|---|---:|---|---:|---|
| `mC_tinf_nockpt` | **15.37** | **없음**(순간값 ±0.5%) | **2836.1** | **−20.5%** |
| `mC_ct250_nockpt` | **14.95** | **있음**(순간값 3465~5795, +67%) | **4452.2** | **+26.4%** |

★**VRAM 이 더 적은 쪽이 스필했다.** 총량으로는 예측이 안 된다(결과 037 §5).

### 4.2 ★권고 — **"시스템 메모리 비대체 선호"(스필 금지)를 기본으로 한다**

근거 넷:

1. **스필은 조용하다.** `mC_ct250_nockpt` 는 **종료코드 0, `skip 0`, 손실 정상**이었다.
   로그 어디에도 *"스필했다"* 는 말이 없다. **순간 ms/step 을 손으로 복원해야만 보인다** —
   그리고 우리는 그걸 매번 하지 않는다. 결과 031 의 교훈 그대로:
   **조용한 실패가 가장 나쁜 실패다.**
2. **속도 판정이 통째로 무효가 된다.** `ms/step` 은 P021·P040·P042 판정의 주축인데,
   스필이 허용되면 그 값이 **그날의 단편화 상태의 함수**가 된다. **비교 불가능해진다.**
3. **OOM 은 즉시·명확·값싸다.** 03:19 의 OOM 은 **35초** 만에 났고
   원인(요구 1024 MiB, 단편화 1.71 GiB)과 **해결책까지 알려줬다**(L9).
   반면 01:21 의 스필은 **19.4분을 쓰고 틀린 수치를 남겼다.**
4. **스필은 상한을 감춘다.** 실제 예산을 모르게 되고, 그러면 `M`·교사 선택·`--no-ckpt` 같은
   **진짜 결정을 못 한다.** 이 저장소는 `M=8192` 무릎, 스필벽, VRAM 예산표로 굴러간다.

### 4.3 예외 두 가지 (허용하되 **반드시 표시**)

| 경우 | 조건 |
|---|---|
| **완주가 목적이고 속도를 안 읽는 런**(품질만 보는 2289스텝) | 로그·결과문서에 **"스필 허용 상태" 명시** + 그 런의 `ms/step`·`wall_sec` **인용 금지** 표시 |
| **일회성 구제**(다시 못 돌릴 런을 살려야 할 때) | 위와 동일 + 다음 런에서 원상복구 |

🚫 **절대 금지**: **"열리는가" 를 묻는 게이트**(P042 단계2 류)를 스필 허용 상태로 돌리는 것.
**게이트 자체가 무의미해진다** — 결과 034 §10 이 정확히 그 경우이고,
그래서 그 판정을 **"조건부 통과"** 로 낮췄다.

### 4.4 스필 대신 쓸 것 — **여유를 진짜로 만든다**

`L1(−1.88) + L2(−1.03) + L9(단편화) + L4(−0.25)` 로 **약 3 GiB** 를 확보하는 쪽이
스필을 허용하는 것보다 **모든 면에서 낫다**. 그중 **L1·L2 는 이미 실측**됐다.

### 4.5 계측 보강 — `scripts/check_spill.py` 신설

**스필을 사람이 매번 손으로 판별할 수는 없다.** 로그의 누적평균 `ms/step` 을 구간 순간값으로
복원해 **변동폭이 크면 경고**하는 도구를 만들었다(학습 0·GPU 0).

```
python scripts/check_spill.py test_result/037_log_20260808_P018_compressed_teacher-retry-mC_ct250_nockpt.txt
```

⚠️ **한계**: 이건 **징후 탐지**이지 증명이 아니다. 열·다른 프로세스·eval 스파이크도 변동을 만든다.
**"의심" 까지만 말하고 판정은 사람이 한다.**

## 1. ★Fishing for Magikarp — **우리 val_loss 를 오염시키고 있을 수 있다**

### 무엇을 말하는 논문인가

토크나이저는 **학습 코퍼스와 따로** 만들어진다. 그래서 어휘에는 있는데 학습 중 **거의 안 나오는
토큰**(under-trained / glitch token)이 생긴다. 논문은 그걸 **임베딩·언임베딩 가중치 지표**로
자동 검출하는 방법을 제시하고, 다양한 모델에서 **실제로 흔하다**는 것을 보인다.

### ★왜 이게 우리에게 특히 위험한가 — 세 가지가 겹친다

| 조건 | 우리 값 | 함의 |
|---|---|---|
| 어휘 크기 | **32,768** | 고정 |
| 학습 토큰 | **300M** | 어휘당 평균 9,155 토큰. **Zipf 꼬리는 사실상 0회** |
| 토크나이저 학습 표본 | **20만 문서** (`build_tokenizer`) | 코퍼스 전체가 아니다 |

그리고 결정적으로:

> **토크나이저를 학습시킨 그 20만 문서에 SEO 스팸이 들어 있었다.**
> 결과 018 이 `ko-edu-en` 에서 찾은 스팸은 `NRN-511`·`CATV612-ELEC-V6R2012` 같은
> **자격증 코드가 단어 중간까지 박힌** 텍스트다. BPE 는 반복되는 문자열을 토큰으로 만든다 —
> **그 제품 코드들이 어휘를 차지했을 가능성**이 있고, 그것들은 필터 후 코퍼스에서 **사라진다.**
> 즉 **필터가 under-trained 토큰을 새로 만들었을 수 있다.**

### 왜 지금 확인해야 하는가

**val_loss 는 우리가 쓰는 유일한 판정 지표**다. 어휘의 일부가 학습 중 거의 안 나왔다면
그 토큰들의 손실은 **정보가 아니라 잡음**이고, 모든 비교에 상수처럼 얹혀 있다.
σ=0.012 / 분해능 0.024 로 0.0136 짜리 차이를 논하는 중이라, **상수 오프셋이라도 확인은 필요**하다.

### 비용

**거의 0.** 학습 없음. 체크포인트의 `emb`(32768×256) 와 `emb_up` 을 읽어 지표를 계산하고,
학습 캐시(`train.bin`)에서 **토큰별 실제 출현 빈도**를 세면 된다. 후자는 `np.bincount` 한 줄이다.

> ⚠️ **논문 그대로가 아니다.** 논문의 주 지표는 **언임베딩 행렬**을 쓰는데 우리는
> **가중치를 묶어 쓴다**(`logits = x @ emb_up.T @ emb.T`, 팩터라이즈드 rank 256).
> 그래서 논문 지표를 그대로 옮길 수 없다. **우리 조건에서 가장 직접적인 것은
> "학습 캐시에서의 실제 출현 빈도"** 이고, 그건 논문 지표보다 **더 강한 증거**다
> (간접 추정이 아니라 직접 계수). 논문은 학습 데이터에 접근할 수 없을 때의 방법이다.
> **우리는 접근할 수 있으므로 더 쉬운 길이 있다.**

→ **P039 신설**: 어휘 활용도·미학습 토큰 진단. §4 에 설계.

## 2. 선형 어텐션 계열 (GDN-2 / KDA / Kimi-Linear / DeepSeek-V4) — **기각, 단 이유를 적어 둔다**

### 공통 주제

softmax 어텐션의 **무한히 자라는 KV 캐시**를 **고정 크기 순환 상태**로 바꾼다.
디코딩이 **상수 메모리**가 되고 시퀀스 믹싱이 선형 시간이 된다.
GDN-2 는 KDA 의 스칼라 게이트를 **채널별 erase/write 게이트로 분리**해 1.3B·100B 토큰에서
Mamba-2 / GDN / KDA / Mamba-3 대비 최고 성능, 특히 **RULER 롱컨텍스트**에서 강하다고 보고한다.

### 왜 지금 우리가 안 쓰는가

| 이유 | 근거 |
|---|---|
| **우리 병목이 아니다** | `max_seq_len` 2048, 학습 `seq` 1024. KV 캐시는 `n_kv=10층 × 2 × 192 × 2B ≈ 7.5KB/토큰`. 1024 토큰이면 **7.7MB** — 상주 96~278MB 옆에서 반올림 오차다 |
| **비용 구조가 반대다** | 결과 016 §10.4: 우리는 batch 1 에서 **런치 오버헤드 바운드**로 보인다. 선형 어텐션은 **긴 컨텍스트의 O(T²)** 를 없애는 기법인데 우리에겐 그 T² 가 없다 |
| **아키텍처 전면 교체다** | 어텐션을 바꾸면 CLA·삼진·타잉과의 상호작용이 전부 미지가 된다. 결과 006·012·019 가 쌓아 온 기준선이 **전부 무효**가 된다 |
| **검증 스케일이 다르다** | GDN-2 는 1.3B·100B 토큰. 우리는 132M·300M. 결과 019 §9 가 **Arenas 에서 정확히 이 스케일 격차로 데었다** |

### 그래도 보존할 개념 하나

**"고정 크기 상태로 디코딩" 은 우리 목표와 방향이 같다.** 다만 우리에게 먼저 필요한 것은
컨텍스트가 아니라 **가중치**다(96MB 중 KV 는 7.7MB). **롱컨텍스트가 목표가 되는 날**
— 즉 `max_seq_len` 을 16K 이상으로 올릴 때 — 이 절을 다시 읽는다.

> **판정 근거를 숫자로 남기는 이유**: "나중에 좋아 보여서" 다시 검토할 때, 그때의
> KV 캐시 비중을 여기 7.7MB 와 비교하면 **결정이 바뀌었는지 아닌지가 한 줄로 보인다.**

## 3. `slvDev/esp32-ai` — **배포 목표의 현실 점검**

ESP32 급 MCU 는 RAM 이 **수백 KB~수 MB** 다. 우리 상주는 **최선(mC + 단계3) 86.9MB** 다.

| 목표 | 필요 상주 | 우리 현재 | 격차 |
|---|---|---|---|
| ESP32 (512KB SRAM + PSRAM 8MB) | ≤ 8 MB | 86.9 MB | **10.9×** |
| 라즈베리파이급 (1GB) | ≤ 500 MB | 86.9 MB | ✅ 이미 만족 |
| 데스크톱 CPU | — | 86.9 MB | ✅ |

**`CLAUDE.md` 의 "저사양 CPU·엣지·모바일" 이 정확히 무엇인지 정하지 않고 있었다.**
이 표가 그 빈칸을 채운다 — **우리는 이미 라즈베리파이급을 만족하고, MCU 급은 아니다.**
이론값 12.4MB 에 닿아도 ESP32 는 **1.5×** 부족하다(PSRAM 8MB 기준으로는 만족).

> **쓸모**: 목표를 "MCU" 로 잡으면 P034 단계4 는 **필수**가 되고, "라즈베리파이" 로 잡으면
> 단계3 에서 이미 끝났고 **R8 은 선택**이 된다. **이건 실험이 아니라 사용자 결정 사항**이다.

## 4. P039 설계 (신규) — 어휘 활용도·미학습 토큰 진단

| 항목 | 내용 |
|---|---|
| **질문** | 32,768 어휘 중 몇 개가 학습에서 사실상 안 쓰였나? 그것이 val_loss 를 얼마나 오염시키나? |
| **방법** | ① `train.bin` 을 `np.bincount` → 토큰별 출현 빈도 ② 0회·10회 미만 토큰 수 ③ 그 토큰들이 **val 에 나타나는 비율**과 **손실 기여** ④ `emb` 노름 분포와 빈도의 상관 |
| **비용** | **0**(GPU 없음, 수 분). 학습 없음 |
| **선결** | 없음. 지금 가능 |
| **판정** | 미학습 토큰이 val 손실의 **1% 미만** 이면 무시. **5% 이상**이면 어휘 축소 또는 재토큰화가 실험 목록에 올라온다 |
| **한계** | 논문의 언임베딩 지표는 **우리 팩터라이즈드 타이드 임베딩에 그대로 안 맞는다**(§1). 직접 빈도 계수로 대체하며, 그건 논문보다 강한 증거다 |
| **부수 가치** | `ko-edu-en` 필터 전/후 어휘 활용도를 비교하면 **필터가 어휘를 얼마나 죽였는지**가 나온다 — 결과 023 이 아직 못 답한 "13% 를 버린 영향" 의 일부 |

**배치는 구현 후에 만든다**(`CLAUDE.md` 규범 — 지금 돌아가지 않는 배치를 최상위에 두지 않는다).

## 5. ★★T-MAC / bitnet.cpp — **우리가 만들려던 커널이 이미 오픈소스로 있다**

### 무엇을 말하는가

- **T-MAC**(arXiv:2407.00088, 코드 `github.com/microsoft/T-MAC`): 저비트 LLM 의 mpGEMM
  (mixed-precision GEMM)을 **역양자화 없이** 수행한다. 곱셈을 **비트 단위 테이블 조회**로 치환해
  곱셈을 없애고 덧셈도 줄인다. BitNet-b1.58-3B 에서 **M2-Ultra 1코어 30 tok/s**,
  **Raspberry Pi 5 에서 11 tok/s**.
- **bitnet.cpp**(arXiv:2502.11880, ACL 2025): 같은 계열의 후속. 커널 두 종 —
  **TL(Ternary Lookup Table)** 과 **I2_S(Int2 with a Scale, 무손실)**.
  **x86 2.37~6.17× / 에너지 −71.9~82.2%**, **ARM 1.37~5.07× / 에너지 −55.4~70.0%**.
  전정밀 대비 최대 **6.25×**, 기존 저비트(T-MAC) 대비 최대 **2.32×**.

### ★왜 우리에게 결정적인가 — 세 가지가 한꺼번에 풀린다

`test_plan/P034` §10.5 가 정리했듯 **남은 상주 레버 셋이 전부 같은 물건을 요구**한다:

| 레버 | 현재 | 필요한 것 |
|---|---|---|
| 단계4 R8(1.375bpw) | 삼진 53.9MB | 융합 커널 |
| 단계5 임베딩·헤드 | 32.0MB | 융합 커널 / 스트리밍 matvec |
| 단계3 int8 의 속도 대가 | CPU **−62~67%** | **역양자화를 없애는 것** |

**세 번째가 핵심이다.** 우리 `TLinear._wq_from_i8()` 은 **매 forward 마다 int8 → fp32 복원**을
한다. T-MAC 의 표현을 그대로 쓰면 우리는 *"data-type-centric multiplication"* 을 하고 있고
논문이 제안하는 것은 *"bit-wise table lookup"* 이다. **정확히 반대 방향이다.**

### ★현실 점검 — 우리 숫자가 얼마나 나쁜가

| | 모델 크기 | CPU 1코어 tok/s | 방식 |
|---|---|---|---|
| T-MAC / BitNet-b1.58 | **3B** | **30**(M2-Ultra) | LUT, dequant 없음 |
| **우리(`p6d`)** | **132M** | **36** | fp32 dequant 후 GEMM |
| **우리(`mC`, int8)** | 132M | **14.2~15.2** | int8 → fp32 복원 후 GEMM |

**모델이 23배 작은데 속도는 1.2배다.**
⚠️ **정밀 비교가 아니다** — CPU(M2-Ultra vs x86), 프롬프트·컨텍스트, 측정 방식이 전부 다르다.
**"격차가 자릿수급이다" 까지만** 말하고, 확정은 동일 하드웨어 측정으로 한다.

### 판정과 후속

| 항목 | 판정 |
|---|---|
| P014(커스텀 삼진 커널) | ★**선택 항목 → 남은 로드맵의 유일한 병목.** 재정의·재개. **`-done` 접미사를 뗀다** |
| 구현 방식 | **처음부터 만들지 않는다.** T-MAC / bitnet.cpp 의 **TL·I2_S 참조** |
| ⚠️ 착수 전 확인 | ① 두 구현 다 **자체 포맷(GGUF 계열)** 전제 → 우리 `TLinear` 에 붙이려면 변환층 ② **g128 그룹 스케일**이 우리 규약인데 I2_S 의 스케일 단위가 다를 수 있다 ③ 라이선스 ④ **초록만 보고 인용 금지**(함정 12) — 본문에서 **커널 인터페이스·정밀도 보장·요구 SIMD** 확인 |
| 비용 | **미산정.** 먼저 실사부터 |

> **★이번 검토의 최대 소득.** 종전 판정("R8 은 융합 커널이 있어야 하고, 융합해도 메모리만
> 번다")은 **커널을 우리가 만든다는 전제**에서 나왔다. 참조 구현이 있고 **속도까지 2.37~6.17×**
> 를 보고한다면 **전제가 바뀐다.**

## 6. MobileLLM — **우리 타잉 배치가 독립적으로 지지된다** (신규 작업 없음)

- arXiv:2402.14905 (Meta, ICLR 2024). sub-1B on-device 모델 최적화.
- 핵심 주장 중 하나: **immediate block-wise weight sharing** — 블록을 **바로 이어서** 반복하는
  공유. **모델 크기 증가 0, 지연 오버헤드 미미**, 125M/350M 에서 **+0.7/0.8%p**.

**우리 구현이 이미 그 형태다.** `mid_mlps[j // mlp_group]` 이라 **연속 g 층이 같은 MLP** 를 쓴다
(g8 이면 층 2~9 가 그룹0, 10~17 이 그룹1). 흩어 놓는 방식이 아니다.

그리고 이 배치가 **우리 실측 두 건의 전제**다:

- 층당 비용이 **g 순서로 단조**(g8 0.913 < g4 1.022 < dense 1.163 ms, 결과 014 §11) = 캐시 지역성
- **언팩 묶기**(P034 단계3C)가 성립하는 이유 — 같은 MLP 가 **연속으로** 온다

> **판정: 신규 실험 없음.** 설계 근거 문서에 인용만 추가(`01_architecture.md`).
> ⚠️ MobileLLM 은 **fp16 dense** 모델이다. 삼진·3:4 와의 상호작용은 그 논문에 없다.

## 7. Relaxed Recursive Transformers — **P008 재개 근거**

- arXiv:2410.20672 (ICLR 2025). 층 타잉을 **layer-wise LoRA** 로 완화한다.

### ★가장 무거운 결과 — U2 부정은 **우회 불가**다

우리 `_alpha` 는 shape 이 **`(O, I//g)`** 라 **출력 행에도 입력 그룹에도** 의존한다.
활성값 쪽으로도, 출력 쪽으로도 **접을 수 없다.** 텐서 하나로 뭉개면
`sign × max_g(α_g)` 가 되어 α 가 작은 그룹이 전부 과대해진다.

> **→ 외부 커널을 쓰려면 "텐서당 α 하나" 로 재양자화해야 하고 그건 가중치를 바꾸는 것이다.**
> **로짓 동등성 게이트는 원리적으로 통과 불가**이고, 품질 재측정이 필수가 된다.
> 그 손실이 분해능을 넘으면 **P014 는 "우리 g128 을 지원하는 커널을 직접 만든다" 로 되돌아간다.**

## 9. ★DeepSeek-V3 FP8 선택적 혼합정밀도 (2026-08-07 추가 검토)

**자료**: `article/DeepSeek-V3 Technical Report.pdf`(arXiv:2412.19437) §3.3 ·
`article/Insights into DeepSeek-V3 ... Hardware for AI Architectures.pdf`(ISCA '25) §3.1.
**전문 = [`docs/20260807_DeepSeekV3-FP8혼합정밀도-우리구조-적용가능성분석.md`](../20260807_DeepSeekV3-FP8혼합정밀도-우리구조-적용가능성분석.md).**
사용자 질문: *"중요한 부분은 고정밀도, 나머지는 fp8 이라는데 우리도 가능한가."*

### 무엇을 말하는가 — **"전부 FP8" 이 아니다**

FP8(E4M3)로 내린 것은 **Linear 의 GEMM 3개**(Fprop·Dgrad·Wgrad)**뿐**이다.
**임베딩 · 출력 헤드 · MoE 게이팅 · 정규화 · 어텐션 연산 · master weight · weight gradient ·
optimizer state 는 전부 고정밀(BF16/FP32) 유지**다(기술보고서 §3.3.1 원문).
선택 기준은 ①저정밀도 민감도 ②연산량 대비 비용이고, "중요도" 같은 모호한 기준이 아니다.

정확도 유지 장치 4개: **미세 입도 양자화**(활성 1×128 타일 / 가중치 128×128 블록) ·
**N_C=128 마다 CUDA Core FP32 누산 승격** · **전 텐서 E4M3** · **온라인 amax**.
검증: 16B(1.33T)·230B(0.9T) 두 규모, **BF16 대비 상대 손실 오차 < 0.25%**.

### ★왜 우리에게 특별한가 — **가중치 FP8 오차가 원리적으로 0이다**

어닐 완료 후 `wq = sign × α[o, g(i)]`, `sign ∈ {−1,0,+1}`, `g = micro_group = 128`.
**α 로 나누면 정확히 {−1,0,+1}** 이고 **E4M3 가 이 셋을 정확히 표현**한다.
→ **스케일 입도만 맞으면 가중치 양자화 오차 = 0.** 논문이 128×128 블록으로 애써 얻으려던 것을
우리는 **행×128** 이라는 더 미세한 입도로 **이미 갖고 있다.** N_C=128 도 우리 `micro_group` 과 일치.

### ⚠️ 그런데 그게 곧바로 장벽이다 — §5 의 U2 와 **같은 벽**

기술보고서 §3.3.2 원문: *"per-group scaling factors along the **inner dimension** of GEMM ...
**is not directly supported in the standard FP8 GEMM**"* → DeepSeek 은 **CUTLASS 커널을 직접 만들었다**(DeepGEMM).
우리 α 도 **정확히 K축 그룹 스케일**이다. `torch._scaled_mm` 은 통상 per-tensor·per-row 만 받는다.

> **★§5(T-MAC/bitnet.cpp)의 U2 부정과 같은 벽이다** — *"우리 α 는 (O, I//g) 라 접을 수 없다"*.
> 저비트 추론 커널에서도, FP8 학습 커널에서도, **막히는 지점이 동일**하다.
> 이건 우연이 아니라 **우리 아키텍처의 구조적 특성**이고, 그래서 **한 번 재면 두 축에 다 쓰인다.**

### ⚠️ 인용 주의

- **"논문은 FP8 로 학습했다" 는 틀린 요약**이다. Linear GEMM 3개만이다.
- **"상대 오차 0.25%"** 는 128블록 + 승격 커널 + 온라인 양자화가 **전부 갖춰진** 조건의 값이다.
  부록 B.2 가 반례를 준다 — 활성 **gradient** 를 블록 양자화하니 **16B 모델이 300B 토큰에서 발산**했다.
- 하드웨어 한계 서술(FP22 누산 = 가수 13비트, 역양자화 오버헤드)은 **Hopper 기준**이다.
  우리는 **Ada sm_89** 이고 같다는 보장이 없다. ★단 **K 가 작은 것은 우리에게 유리**하다 —
  논문 예시는 K=4096, 우리는 768/2048 이다.

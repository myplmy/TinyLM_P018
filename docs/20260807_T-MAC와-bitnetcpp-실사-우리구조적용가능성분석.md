## 1. 왜 지금 이걸 보는가 — 우리 숫자가 말이 안 된다

| | 파라미터 | CPU 1스레드 tok/s | 방식 |
|---|---|---|---|
| T-MAC / BitNet-b1.58 | **3,000M** | **30** (M2-Ultra) | LUT, **역양자화 없음** |
| **우리 `p6d`** | **132M** | **36** | fp32 dequant 후 GEMM |
| **우리 `mC` int8** | 132M | **16.1** | int8 → **fp32 복원** 후 GEMM |

**모델이 23배 작은데 속도는 1.2배다.**
⚠️ CPU(M2-Ultra vs 사용자 x86)·컨텍스트·측정 방식이 달라 **정밀 비교가 아니다.**
그래도 자릿수 격차는 조건 차이로 설명되지 않고, **원인 후보가 하나로 좁혀져 있다.**

그리고 우리는 이미 그 원인을 세 갈래로 만났다:

| 관측 | 출처 |
|---|---|
| int8 저장이 **CPU 속도를 −62~67%** 로 만든다 | 결과 016 §10·§12 |
| 그 대가가 **층당 +2.1~2.2ms**, 세 모델이 거의 동일 = **분리된 unpack 고정비** | 결과 014 §11.4 |
| **CUDA 에서는 −12~15% 뿐**(1/5) = 대역폭 문제이지 알고리즘 문제가 아니다 | 결과 016 §12.3 |

T-MAC 초록의 한 문장이 우리 상황을 그대로 서술한다:

> *"Existing systems, lacking native support for mpGEMM, resort to dequantize weights for high
> precision computation. Such an indirect way can lead to a significant inference overhead."*

**우리 `TLinear._wq_from_i8()` 이 정확히 그 "indirect way" 다.**

## 2. 용어 정리 (이후 설명에 계속 쓴다)

| 용어 | 뜻 | 우리 코드에서 |
|---|---|---|
| **mpGEMM** | mixed-precision GEMM. **저정밀 가중치 × 고정밀 활성값** 행렬곱 | `F.linear(x, wq)` — 지금은 `wq` 를 fp32 로 올려서 한다 |
| **역양자화(dequantize)** | 압축된 가중치를 계산용 정밀도로 되돌리는 것 | `_wq_from_i8()` = int8 코드 × α → fp32 |
| **LUT (lookup table)** | 미리 계산해 둔 결과표. 곱셈 대신 **조회**한다 | 없음 |
| **bit-serial** | w비트 가중치를 **1비트 평면 w장**으로 쪼개 각각 처리 | 없음 |
| **그룹 스케일** | 가중치 N개마다 실수 배율 α 하나 | `micro_group=128`, α는 그룹 최대/평균 |
| **활성값 양자화** | 활성값도 int8 등으로 낮추는 것 | **안 한다**(fp32/bf16) |

## 3. T-MAC 의 원리 — **왜 곱셈이 사라지는가**

### 3.1 핵심 착상

1비트 가중치는 값이 **두 개**뿐이다(+1/−1). 그러면 **1비트 벡터 4개짜리 묶음**이 가질 수 있는
패턴은 `2⁴ = 16` 가지밖에 없다.

활성값 벡터 `a = [a₀, a₁, a₂, a₃]` 가 주어지면, **16가지 패턴 전부와의 내적을 미리 계산**할 수 있다:

```
표[0000] = −a₀ −a₁ −a₂ −a₃
표[0001] = −a₀ −a₁ −a₂ +a₃
...
표[1111] = +a₀ +a₁ +a₂ +a₃      ← 16칸짜리 표 하나
```

이 표를 만들어 두면, **가중치의 4비트 묶음은 그냥 표의 인덱스**가 된다.
행렬곱이 **"조회 + 덧셈"** 으로 바뀌고 **곱셈이 사라진다.**

### 3.2 여러 비트폭은 어떻게 하나 — bit-serial

2비트 가중치는 **1비트 평면 2장**으로 쪼개고 각각 LUT 를 돌린 뒤 자릿값(1, 2)으로 가중합한다.
그래서 논문이 *"kernels scale linearly to the weight bit-width"* 라고 한다.
**비트폭이 몇이든 같은 커널이 돈다** — 이게 T-MAC 의 "unified and scalable" 주장이다.

### 3.3 실제로 어려운 점 (논문이 든 두 가지)

| 문제 | 내용 | T-MAC 의 해법 |
|---|---|---|
| **표 접근이 무작위다** | 가중치·활성값은 연속 접근인데 LUT 는 인덱스가 흩어져 있다. 캐시를 놓치면 이득이 사라진다 | **표를 레지스터(온칩)에 상주**시킨다 — 축 재정렬(axis reordering)과 타일링으로 표 재사용 극대화 |
| **표가 온칩 메모리를 먹는다** | 활성값 × 모든 비트 패턴을 저장해야 하므로 종전 mpGEMM 보다 온칩 사용량이 **늘어난다** | **table quantization**(표 자체를 낮은 정밀도로) + **mirror consolidation**(부호 대칭성 이용 — `표[¬p] = −표[p]` 이므로 절반만 저장) |

> **★이 두 문제가 우리에게 그대로 온다.** 우리 모델은 작아서(dim 768) 표 재사용 기회가
> 3B 모델(dim 2560+)보다 적다 → **§6 의 최대 리스크**.

### 3.4 논문의 결론 문장 하나 — 우리 관측과 정확히 만난다

> *"T-MAC makes the LLM inference speed on a CPU comparable or even higher to the GPU on the same
> device, mainly because T-MAC has no conversion cost."*

**우리는 결과 016 §12.3 에서 이미 "GPU 가 CPU 1스레드의 1.18배뿐" 을 관측했다.**
논문은 그 현상을 **역양자화 비용 제거로 설명**하고, 우리는 **그 비용을 아직 지불하고 있다.**

## 4. bitnet.cpp 는 T-MAC 과 무엇이 다른가

| | **T-MAC** | **bitnet.cpp** |
|---|---|---|
| 논문 | arXiv:2407.00088, EuroSys 2025 | arXiv:2502.11880, ACL 2025 |
| 대상 | **임의 저비트**(1·2·3·4bit …) | **삼진 전용**(BitNet b1.58 계열) |
| 방식 | **bit-serial LUT** — 1비트 평면으로 쪼갠다 | **TL(Ternary Lookup Table)** — 삼진을 **직접** 색인 / **I2_S**(int2+scale, **무손실**) |
| 장점 | 범용. 비트폭에 선형 | 삼진에 특화돼 **공간 효율이 좋다**(논문이 "spatial inefficiencies of previous bit-wise methods" 를 지적) |
| 보고 성능 | llama.cpp 대비 최대 **4×**, 에너지 −70% | 전정밀 대비 최대 **6.25×**, **저비트 기존 대비 최대 2.32×**(= T-MAC 대비). x86 **2.37~6.17×**, ARM **1.37~5.07×**, 에너지 x86 −71.9~82.2% / ARM −55.4~70.0% |

### ★한 줄 정리

> **T-MAC = 범용 저비트 LUT 엔진. bitnet.cpp = 삼진 전용으로 더 조인 것.**
> **우리는 삼진이다 → bitnet.cpp 쪽이 원리적으로 더 맞고, 실제로 T-MAC 대비 최대 2.32× 를 보고한다.**
> 다만 **범용성은 T-MAC 이 높아**, 우리 `sparse34`(1.25bpw) 같은 비표준 포맷을 실험할 여지는
> T-MAC 쪽이 크다(단 §5.3 참조 — 그대로는 안 된다).

## 5. ★우리 구조와의 대조 — 같은 것, 다른 것, 안 되는 것

### 5.1 ✅ **잘 맞는 것** (그대로 이어진다)

| 우리 | 그쪽 | 왜 맞나 |
|---|---|---|
| 가중치가 **삼진 {−α, 0, +α}** | BitNet b1.58 = 삼진 | **완전히 같은 값 집합.** TL 커널의 설계 전제 그대로 |
| **CPU·엣지 배포가 목표** | 둘 다 CPU/엣지 전용 | 목표 함수가 같다 |
| **배치 1 디코드**가 주 시나리오 | 논문 벤치도 token generation | 우리가 재는 것과 같은 양 |
| 병목이 **역양자화** | 논문이 지목한 바로 그 문제 | 결과 014 §11.4·016 §12 가 실측으로 확인 |
| **`mC`(g8)가 유력 후보** | 순수 삼진, 특수 포맷 없음 | **TL/I2_S 가 그대로 받는다** |

### 5.2 ⚠️ **확인이 필요한 것** (맞을 수도, 아닐 수도)

| 항목 | 우리 | 그쪽(추정) | 왜 문제인가 |
|---|---|---|---|
| **스케일 단위** | **`micro_group=128`** — 가중치 128개마다 α 하나 | BitNet b1.58 은 **텐서 단위 absmean** 스케일이 원형. I2_S 의 "Scale" 이 어느 단위인지 **미확인** | 그룹 스케일이면 LUT 결과에 **그룹마다 다른 배율**을 곱해야 한다. 커널이 그걸 지원하지 않으면 **α 적용을 밖에서 해야 하고**, 그러면 이득이 깎인다 |
| **α 계산 방식** | TWN 임계(`thr_ratio=0.7`) + **L2-optimal α** | BitNet = absmean 반올림 | 값이 달라도 **커널은 상관없다**(코드 + 스케일만 받으면 된다). 단 **정확도 비교 시 조건이 다르다** |
| **활성값 정밀도** | **fp32/bf16** | BitNet b1.58 = **W1.58A8**(활성값 int8) | 활성값이 int8 이어야 LUT 표가 작아진다. 우리가 fp16/fp32 활성값을 유지하면 **표가 커져 온칩에 안 들어갈 수** 있다 |
| **모델 규모** | dim 768 / ffn 2048 / 20층 | 3B급(dim 2560+) | **표 구축 비용의 상각**이 다르다. 작은 행렬은 표 만드는 비용 대비 재사용이 적다 → **이득 축소 가능** |

### 5.3 🚫 **적용 안 되는 것** (구조적으로)

| 항목 | 왜 안 되나 |
|---|---|
| **`sparse34`(mA, 1.25bpw)** | 우리 3:4 준정형은 **4개 가중치를 5비트 코드 하나**로 묶는 포맷이다. TL 은 삼진 색인, T-MAC 은 **1비트 평면 bit-serial** — **둘 다 이 코드북을 모른다.** 쓰려면 **우리가 커널을 새로 짜야 한다** |
| **`--infer-repeat`(P031) 같은 동적 스케줄** | 커널 층위와 무관하므로 실제로는 문제없다. 다만 **GGUF 로 내보내면 그런 실험 플래그가 전부 사라진다** |
| **학습 경로** | 이 커널들은 **추론 전용**이다. 우리 STE·어닐·KD 는 PyTorch 에 남는다. **학습이 빨라지지 않는다** |
| **`paired_eval.py`·`common_bpb.py` 등 평가 도구** | PyTorch 텐서를 전제한다. GGUF 경로로 가면 **평가 체계가 갈라진다**(§7 의 최대 비용) |

### 5.4 ★★그리고 하나 — **P034 단계3C 는 P014 가 삼켜 버린다**

우리는 방금 **언팩 캐시**로 `mC` +17%(대가 걷어내면 약 1.7× 추정)를 만들었다(결과 016 §14).
**LUT 커널에는 언팩 자체가 없다.** 즉:

> **단계3C 는 P014 가 오면 무의미해지는 임시 방편이다.**
> ⚠️ **그렇다고 3C 가 헛일은 아니다** — P014 는 착수 조건이 크고 실패할 수 있는 반면
> 3C 는 **오늘 완료 직전**이고 순수 PyTorch 다. **보험으로 완주할 값어치가 있다.**

그리고 **타잉(g)은 LUT 이득과 직교한다** — LUT 표는 **활성값**에서 만들어지고 활성값은 층마다
바뀌므로, 가중치를 공유해도 **표를 재사용할 수 없다.** 3C 에서 얻은 "타잉이 속도를 번다" 는
**언팩 경로 한정의 성질**이다.

### 6.3 ★기대치를 미리 못 박는다

우리 `mC` int8 은 **16.1 tok/s(62.3 ms/토큰)** 이고, 결과 014 §11 의 분해로는
**고정비 a ≈ 4.2ms(모델 밖: LM 헤드 + top-k) + 층당 b**다.

- 언팩(약 2ms/층 × 20 = 40ms)이 **전부 사라진다**고 가정하면 → 약 22ms/토큰 = **45 tok/s**
- 여기에 LUT 자체의 덧셈·표 구축 비용이 더해지므로 **그보다 낮다**
- **고정비 4.2ms 는 커널로 안 줄어든다**(LM 헤드는 별개 문제 — §5.3)

> **★현실적 기대: `mC` int8 16.1 → 25~40 tok/s.**
> **"6.17×" 를 그대로 인용하면 안 된다** — 그건 **전정밀 대비**이고 **3B 모델**이며
> **우리 고정비를 포함하지 않는다.** 결과 016 §7.4 가 "2.64× 가 실제로는 2.11× 였다" 로 데인
> 것과 정확히 같은 종류의 오류가 된다.

## 9. ★`mA` vs `mC` 에 미치는 영향 — REVIEW1 재확인

## 13.2 ★★U2 판정 — **부정. 그리고 예측보다 나쁘다**

**질문**: 커널이 우리 `micro_group=128` 그룹 스케일을 받는가?

### I2_S 경로 (`src/ggml-bitnet-mad.cpp:51`)

```c
size_t quantize_i2_s(const float * src, void * dst, int64_t nrow, int64_t n_per_row, ...) {
    int n = nrow * n_per_row;                       // ← 텐서 전체
    double max = 0;
    for (int i = 0; i < n; ++i)
        max = fmax(max, fabs((double)src[i]));      // ← 전체에서 최대 1개
    double i2_scale = max;
    ...
    float* scale_ptr = (float*)((char*)i2_weight + n / 4);
    scale_ptr[0] = i2_scale;                         // ← ★스케일 딱 하나
}
```

### TL 경로 (`include/bitnet-lut-kernels.h`, `ggml_bitnet_transform_tensor`)

```c
const int lut_scales_size = 1;
...
scales = (bitnet_float_type *) aligned_malloc(sizeof(bitnet_float_type));   // ← 1개분만 할당

```

| | 스케일 개수 |
|---|---|
| **I2_S** | **텐서당 1개** |
| **TL1 / TL2** | **텐서당 1개**(I2_S 가 쓴 그 값을 그대로 읽는다) |
| **우리(`mC`)** | `54.85M / 128` = **약 428,000개** |

> **★U2 = 부정 확정.** 예측 P2 는 "텐서 단위일 가능성이 높다" 였고 **맞았다.**
> 단 예상보다 나쁘다 — **행 단위조차 아니고 텐서 단위 하나**다.

### ★왜 이게 치명적인가 — 접을 수도 없다

우리 `_alpha` 는 `to_int8()` 에서 `wg = w.reshape(O, I//g, g)` → `amax(dim=2)` 로 만들어져
**shape 이 `(O, I//g)`** 다. 즉 **출력 행마다·입력 그룹마다** 다르다.

- 활성값 쪽으로 접기(pre-scale)? 🚫 **불가** — α 가 입력 열뿐 아니라 **출력 행에도** 의존한다
- 출력 쪽으로 접기? 🚫 **불가** — 같은 이유(입력 그룹에도 의존)
- 텐서 하나로 뭉개기? → `sign × max_g(α_g)` 가 되어 **α 가 작은 그룹이 전부 과대**해진다

> **→ I2_S/TL 을 쓰려면 우리 모델을 "텐서당 α 하나" 로 재양자화해야 하고,
> 그건 가중치를 바꾸는 것이므로 재학습 또는 최소한 품질 재검증이 필요하다.**
> **G1(로짓 동등성)은 원리적으로 통과 불가**다. P014B §단계1 의 "허용 오차를 미리 정한다" 가
> 선택이 아니라 필수가 됐다.

# §14. U5 빌드 실패 — **원인은 BitNet 저장소의 CMake 버그로 보인다**

## 14.1 증상

```
lld-link : error : undefined symbol: quantize_i2_s
  >>> referenced by ggml-base.dir\Release\ggml.c.obj:(ggml_quantize_chunk)
lld-link : error : undefined symbol: dequantize_row_i2_s
  >>> referenced by ggml-base.dir\Release\ggml.c.obj:(type_traits)
```

**configure 는 성공했다**(`generate_build_files.log` 마지막 줄 `Build files have been written`).
컴파일도 대부분 성공했고 **링크에서만** 죽었다.

## 14.2 ★원인 — `src/CMakeLists.txt` 의 두 줄

```cmake
set(GGML_SOURCES_BITNET ggml-bitnet-mad.cpp)
set(GGML_SOURCES_BITNET ggml-bitnet-lut.cpp)   # ← ★덮어쓴다 (list(APPEND) 가 아니다)
```

**두 번째 `set()` 이 첫 번째를 덮어쓴다.** 결과적으로 `GGML_SOURCES_BITNET` 에는
**`ggml-bitnet-lut.cpp` 만** 남고 **`ggml-bitnet-mad.cpp` 는 컴파일되지 않는다.**

그리고 **`quantize_i2_s` 는 정확히 `ggml-bitnet-mad.cpp:51` 에 있다.**
→ **링커가 못 찾는 것이 당연하다.**

## 14.3 `dequantize_row_i2_s` 는 어디에도 없다

`src/` 와 `include/` 전체를 검색해도 **`dequant` 문자열 자체가 없다.**
`ggml.c` 의 `type_traits` 테이블이 참조하는데 **정의가 어디에도 없다.**

**두 가지 가능성**:

| 가설 | 내용 | 어떻게 확인 |
|---|---|---|
| **H1** | `3rdparty/llama.cpp` 서브모듈이 **BitNet 이 고정한 커밋보다 최신**이라, BitNet 의 패치가 상정한 파일 구조와 어긋났다 | `git submodule status` |
| **H2** | 정의가 **llama.cpp 쪽 패치 파일**에 있는데 그 패치가 적용되지 않았다 | `git -C 3rdparty/llama.cpp log -1` |

**H1 을 뒷받침하는 정황**: 로그의 `ggml version: 0.15.3`, `ggml commit: 390c30775` 는
**꽤 최신 llama.cpp** 다. 그리고 최신 llama.cpp 는 ggml 을 **`ggml-base` + `ggml-cpu` 백엔드**로
쪼갰다(로그에 `Including CPU backend`, `Adding CPU backend variant ggml-cpu` 가 보인다).
**BitNet 의 패치는 그 분리 이전 구조를 상정했을 가능성이 크다** — 그러면 `ggml.c`(→`ggml-base`)가
참조하는 심볼의 정의가 **다른 타깃(`ggml-cpu`)에 들어가** 링크가 깨진다.

## 14.4 ★제안하는 해결 순서 (값싼 것부터)

| 순 | 조치 | 명령 | 왜 |
|---|---|---|---|
| **1** | **서브모듈을 고정 커밋으로** | `git submodule update --init --recursive --force` | H1 이 맞으면 이것으로 끝난다. **가장 값싸고 가장 유력** |
| **2** | 클론을 `--recursive` 로 다시 | `git clone --recursive https://github.com/microsoft/BitNet.git` | 1번이 안 되면. 서브모듈 상태가 꼬였을 때 |
| **3** | **CMake 한 줄 수정** | `src/CMakeLists.txt` 의 두 `set` 을 하나로: `set(GGML_SOURCES_BITNET ggml-bitnet-mad.cpp ggml-bitnet-lut.cpp)` | `quantize_i2_s` 는 이걸로 해결된다. **`dequantize_row_i2_s` 는 별개** |
| **4** | **`-q tl2` 로 시도** | `python setup_env.py -md ... -q tl2` | I2_S 경로를 아예 안 타면 그 심볼이 필요 없을 수 있다 |
| 5 | 이슈 검색·보고 | GitHub Issues | 저장소 버그면 우리가 고칠 일이 아니다 |

## 14.5 ★사용자에게 요청하는 정보 (진단에 필요하다)

지금 내가 가진 것은 **`src/` 와 `include/` 의 일부 파일뿐**이라 위 H1/H2 를 못 가른다.
다음을 주면 확정할 수 있다:

| # | 요청 | 명령 |
|---|---|---|
| **A** | **서브모듈 상태** | `git -C Z:\TinyLM_supplement\BitNet submodule status` |
| **B** | BitNet 커밋 | `git -C Z:\TinyLM_supplement\BitNet log -1 --oneline` |

## 14.6 ⚠️ 빌드 로그에서 발견한 부수 사항 두 가지

| # | 관측 | 왜 중요한가 |
|---|---|---|
| **1** | `Adding CPU backend variant ggml-cpu: /arch:AVX512 GGML_AVX512` | CMake 의 `HAS_AVX512_2 - Success` 는 **컴파일러가 그 플래그를 받는다**는 뜻이지 **CPU 가 AVX512 를 지원한다**는 뜻이 아니다. **CPU 가 미지원이면 실행 시 잘못된 명령(SIGILL)으로 죽는다.** 빌드가 성공해도 **먼저 CPU 를 확인**해야 한다 |
| **2** | `Could NOT find OpenMP` / `OpenMP not found` | 병렬화가 빠진다. **우리 벤치는 1스레드라 무관**하지만, 다중 스레드 수치를 인용하려면 문제가 된다 |

**★1번 확인 요청**: 사용자 CPU 모델명. (인텔 12~14세대 컨슈머는 AVX512 가 **비활성**이고,
AMD Zen4/5 는 지원한다. 이 차이가 **T-MAC/bitnet.cpp 성능에 직접 영향**을 준다.)

## 14.7 ★그런데 — **빌드는 단계0 의 필수 조건이 아니다**

P014B §단계0 의 게이트 G0 는 *"라이선스 + Windows 빌드 가능"* 이었다.
**라이선스는 통과**(MIT)했고 **빌드는 미결**이다.

**그러나 §13 의 코드 실사만으로 U2·U3 와 shape 문제가 이미 답이 나왔고, 그게 단계0 의 본 목적이었다.**
빌드는 **단계0.5(더미 벤치)와 단계2(속도 게이트)에 필요**하다.

> **→ 빌드가 막혀도 단계0 은 완료로 볼 수 있다.**
> 그리고 **§13.2 의 U2 부정**이 이미 P014 의 비용을 크게 올렸으므로,
> **빌드에 며칠을 쓰기 전에 §15 의 재판정을 먼저 읽는 것이 맞다.**

| 항목 | 값 | 함의 |
|---|---|---|
| CPU | **AMD Ryzen 7 9700X** (Zen 5, 8C/16T, 3.8GHz 기본) | **AVX-512 완전 지원**(Zen 5 는 512비트 데이터패스). §14.6 의 SIGILL 우려는 **해소** |
| **L3** | **32.0 MB** | ★**MLP 하나가 fp32 로 18.0 MiB** → L3 에 들어간다. 결과 014 §11 의 캐시 지역성 관측(g8 층당 0.913ms)과 정합 |
| L2 | 8.0 MB (코어당 1MB) | int8 MLP 하나 = 4.5MB → **L2 에도 거의 들어간다** |
| L1 | 640 KB | |

> **★"L3 32MB 상주" 라는 우리 종전 목표 문구가 이 기계에서는 실제 수치와 정확히 맞는다.**
> 그리고 **AVX-512 가 살아 있으므로 LUT·int8 GEMM 둘 다 최적 조건**이다.

## 17.2 ★★진짜 질문은 하나로 줄어든다 — **α 를 얼마나 거칠게 해도 되는가**

우리 병목은 **역양자화**(`_wq_from_i8()`)이고, 그걸 없애는 방법은 **융합 mpGEMM** 하나다.
그런데 **융합 연산들은 전부 우리보다 거친 스케일 규약을 쓴다**:

| 규약 | α 개수(mC) | 누가 |
|---|---|---|
| **g128**(우리) | 약 **428,000** | `tinylm` |
| **per-row** | **O 개**(768~2048/층) | ★**PyTorch 내장 융합 int8 matmul 계열** |
| **per-tensor** | **1** | bitnet.cpp I2_S · TL(§13.2 확인) |

> **★그러므로 "커널을 만들 것인가" 를 정하는 것은 커널 성능이 아니라
> "거친 α 를 감당할 수 있는가" 다.** 그리고 그것은 **학습 없이, GPU 수 분에 측정 가능하다.**

## 17.3 구현 완료 — `scripts/diag_alpha_group.py`

배포되는 `_wq`(= sign × α_g)의 **부호를 보존**하고 α 만 다시 묶는다.
`sign·A − sign·α_g = sign(A − α_g)` 이므로 **L2 최적 재추정은 `A = mean(|w|)`**(비영 위치).
**이것이 변환기가 실제로 할 일과 같다.**

그리고 **바뀐 가중치로 SQuAD 공통 원문 bpb 를 실제로 잰다** —
가중치 상대오차는 참고값이고 **판정은 bpb** 로 한다(결과 019 의 "구조가 정한 값을 지표로
읽지 말 것" 과 같은 계열의 주의).

**로직 검산**(numpy 로 수식 재현, torch 불필요):

| granularity | 상대오차 | 0 위치 보존 |
|---|---|---|
| g128(원본 복원) | **0.000000** ✅ | ✅ |
| per-row | 0.113 (합성 α, I=256) | ✅ |
| per-tensor | 0.360 (합성 α) | ✅ |

**g128 이 정확히 0 인 것이 구현 정합성의 증거**다(원래 α 를 되찾는다).

## 17.4 판정 분기 — 세 갈래로 미리 정해 둔다

| per-row 의 Δbpb | 판정 |
|---|---|
| **< 0.008**(분해능) | ★**커널 불필요.** PyTorch 융합 int8 matmul(per-row)에 얹으면 역양자화가 사라진다. **가장 값싼 결말** |
| g256/g512 는 통과, per-row 는 초과 | 중간 규약으로 타협. 단 **그 규약을 받는 융합 연산이 없으면** 결국 커널을 짜야 하고 그러면 g128 유지가 낫다 |
| **per-row·per-tensor 둘 다 크게 초과** | ★**g128 커널을 우리가 만든다**(P014 안 C). 그리고 이 표가 **왜 외부 구현을 못 쓰는지의 정량 근거**가 된다 |

⚠️ **이 표는 비관적 상한**이다 — **재학습하면 거친 α 에 적응해 대가가 줄어든다.**
per-row 가 0.008 을 조금 넘으면 **"재학습하면 될 수도 있다" 가 살아 있는 선택지**다.

## 17.5 ⚠️ 선결 확인 하나 — 융합 연산이 실제로 있는가

PyTorch 에 **per-row 스케일 int8 융합 matmul**(`_weight_int8pack_mm` 계열)이 있는 것으로
알고 있으나 **버전·디바이스별 존재 여부를 직접 확인하지 않았다.**
per-row 가 통과하더라도 **연산이 없으면 소용없다.**

**확인 한 줄**(사용자 환경에서):

```
python -c "import torch; print(torch.__version__); print(hasattr(torch, '_weight_int8pack_mm'))"
```

> `False` 여도 길은 남는다 — `torch.compile` 융합, `torchao`, 또는 우리 커널.
> 다만 **`True` 면 커널 없이 끝난다**는 점에서 이 한 줄의 값어치가 크다.

# P018-R1 현황점검

- 기준일: 2026-08-21
- 범위: 정적 조사, 최소 통합, 저장 로그 분석, 실행 전 gate 설계
- 자원 경계: AI는 모델 생성·checkpoint load/save·forward/backward·학습·추론·benchmark·대규모 tokenization을 실행하지 않음

## 1. 결론 요약

P018-R1의 dense MobileLLM-125M architecture는 TinyLM에 구현되어 있고, 저장된 2026-08-09 로그에서 공식 구현과 선택된 eager CPU 경로의 weight/hidden/logit parity가 정확히 일치했다. Tied Teacher의 주 조건은 사용자의 최종 정정에 따라 **MLP-only g6**이다. 공식 30개 layer를 6개씩 묶어 5개 고유 MLP를 쓰며 attention은 30개 모두 독립이다.

이번 정적 통합으로 `mobile125`가 trainer, checkpoint loader, online KD, eval/generate, 공식 tokenizer cache namespace로 라우팅되도록 최소 연결했다. 그러나 새 통합 경로는 아직 사용자 실행의 model smoke 및 mini trainer/KD smoke를 거치지 않았다. 따라서 상태는 **“정적 통합 완료, 자원 사용 검증 대기”**이며 300M 본 학습을 바로 시작할 단계는 아니다.

## 2. AI가 이해한 실험 목적과 비교 구조

질문은 “이미 학습된 dense teacher를 압축하면 어떤가”가 주 질문이 아니다. 같은 MobileLLM-125M 기반에서 dense teacher와 MLP-only tied teacher를 **각각 처음부터 독립 학습**했을 때 다음을 추정하는 것이다.

1. MLP 공유가 teacher의 고유 parameter 및 실제 KD teacher memory를 얼마나 줄이는가.
2. 그 개입이 teacher 품질을 얼마나 변화시키는가.
3. 동일한 student에 distillation했을 때 student 품질 차이가 얼마나 전달되는가.

실험표는 다음이 정본이다.

| Stage | arm | 정의 |
|---|---|---|
| A | Dense Teacher | TinyLM의 MobileLLM-125M dense, random initialization부터 학습 |
| A | Tied Teacher | 동일 base architecture, MLP-only g6, random initialization부터 학습 |
| A 후속 | Tied Teacher from Dense | 학습된 dense를 g6로 압축·이식; 주 실험과 분리 |
| B | No KD Student | teacher 없이 동일 student를 학습 |
| B | Dense KD Student | Dense Teacher로 동일 student를 KD |
| B | Tied KD Student | Tied Teacher로 동일 student를 KD |

고정 동등성 한계는 두지 않는다. 3개 paired seed의 raw difference, mean, standard deviation, confidence interval, effect size를 보고하고, “유의하지 않음”을 동일성 또는 동등성으로 표현하지 않는다.

## 3. g6 재검증

공식 `MobileLLM/configs/125M/config.json`은 `num_hidden_layers=30`이다. TinyLM은 tied일 때 `mlp_idx = layer_index // mlp_group`을 사용한다.

| 그룹 | layer |
|---:|---|
| MLP 0 | L0-L5 |
| MLP 1 | L6-L11 |
| MLP 2 | L12-L17 |
| MLP 3 | L18-L23 |
| MLP 4 | L24-L29 |

`g6`은 다섯 그룹이 모두 6층으로 균등하다. `g8`은 8+8+8+6으로 끝 그룹만 작아지므로 주 조건으로 부적절하다. `g10`과 `g15`도 30의 약수지만 공유 강도를 동시에 바꾸므로 후속 sensitivity arm으로만 다룬다.

정적 parameter 산술은 다음과 같다.

| 항목 | Dense | Tied g6 | 차이 |
|---|---:|---:|---:|
| logical parameter use | 124,635,456 | 124,635,456 | 0 |
| unique parameter | 124,635,456 | 58,280,256 | -66,355,200 (-53.24%) |
| unique MLP | 30 | 5 | -25 |

MLP 하나는 `3 × 576 × 1536 = 2,654,208` parameter이고, 25개 복제 제거분은 66,355,200이다. 실제 runtime peak 감소율은 activation, optimizer, allocator가 포함되므로 이 정적 비율과 같다고 가정하지 않는다.

## 5. 공식 tokenizer와 corpus 조사

### 5.1 공식 tokenizer

로컬 upstream에 `MobileLLM/configs/125M/tokenizer.model`이 있으며 다음을 확인했다.

- LLaMA tokenizer, vocab 32000.
- `<unk>=0`, `<s>=1`, `</s>=2`.
- 로컬 전용 `AutoTokenizer` 로딩 및 짧은 한·영 문자열 round trip이 가능했다.
- `tokenizer.model` SHA-256: `9e556afd44213b6bd1be2b850ebbbd98f5481437a8021afaf58ee7fb1818d347`.

통합 경로는 자동 BOS를 넣지 않고 문서 본문을 `add_special_tokens=False`로 encode한 뒤 문서마다 EOS 하나를 붙인다. 이 framing은 기존 TinyLM cache 방식과 개입을 맞추기 위한 선택이며 metadata에 기록된다.

기존 `tiny_bpe` cache를 오염시키지 않도록 Mobile cache는 예를 들어 `data_cache/ko-en__mobilellm_32k_300000000/`에 저장한다. metadata에는 tokenizer kind/path/hash, vocab, special-token 처리 규칙을 남긴다.

### 5.2 원 MobileLLM 학습 corpus

로컬 논문의 pretraining 설정과 공식 저장소를 확인했으나 pretraining corpus 이름·구성은 공개되어 있지 않다. 논문은 best model을 1T tokens, 32 A100, Adam, weight decay 0.1, 초기 LR 2e-3 cosine schedule로 학습했다고 설명하지만 데이터 source를 재현할 정보는 주지 않는다. 공식 `pretrain.sh`도 pretokenized JSONL 경로를 placeholder로 받을 뿐 corpus를 지정하지 않는다.

따라서 R1은 “원 MobileLLM 학습 재현”이라고 부르면 안 된다. 공식 architecture와 tokenizer를 사용하고, 프로젝트 정본인 다음 controlled corpus/budget을 사용한다.

- `wikimedia/wikipedia`, `20231101.ko`, 설정 weight 0.5
- `HuggingFaceFW/fineweb-edu`, `sample-10BT`, 설정 weight 0.5
- cache 및 consumed training budget의 우선 기준: 300M tokens

주의: 현 `_stream()`의 0.5/0.5는 문서 선택 확률이다. 문서 길이 차이 및 source 고갈 때문에 실제 token 비율은 50/50이 아닐 수 있다. 실제 `mix_token_frac`과 `mix_exhausted`가 결과의 정본이다.

## 6. 구현된 사항

### 6.1 작업환경과 안전 경계

- root `AGENTS.md`에 P018-R1 목적, g6, no-margin 통계 규칙, user-run 자원 경계를 기록했다.
- `.codex/config.toml`로 프로젝트 작업환경을 준비했다.
- explicit interpreter 및 현재 CUDA 환경을 기록했다.
- upstream `MobileLLM/`, reference, 기존 로그·checkpoint·cache를 수정하거나 실행하지 않았다.

### 6.2 architecture와 model routing

- `mobile125 dense`: 30개 독립 MLP, shared input/output embedding.
- `mobile125 tied`: MLP-only g6, 5개 고유 MLP, attention 30개 독립.
- Mobile tied group은 30을 정확히 나누도록 config invariant를 추가했다.
- `build_model(cfg)`를 trainer/checkpoint/generate 경로의 family router로 연결했다.
- Mobile용 AdamW parameter group은 dense와 tied에 동일 LR을 적용한다. 기존 P018의 tied group `lr/sqrt(g)`를 Mobile에 적용하지 않아 optimizer 개입이 섞이지 않게 했다.
- P018 전용 ternary/LoRA/FiLM/Arenas/embedding-rank 옵션이 Mobile에서 조용히 무시되지 않도록 명시적으로 거부한다.
- optional Dense-to-Tied Mobile 초기화는 주 실험과 혼입되지 않도록 아직 명시적 차단 상태다.

### 6.3 tokenizer/cache

- `tiny_bpe` 기본 경로와 기존 cache 이름은 유지했다.
- `mobilellm_32k` loader와 별도 cache namespace를 추가했다.
- cache 재사용 시 tokenizer kind, vocab, filtered 여부를 검사한다.
- 기존 reusable-cache 검색이 filtered/non-filtered cache를 구분하지 않던 baseline 오류를 수정했다.
- trainer/eval/generate/paired eval/KD cache가 checkpoint 또는 preset의 tokenizer identity를 사용한다.
- KD teacher/student 및 KD cache의 vocab/tokenizer 불일치를 실행 전에 차단한다.

### 6.4 계측과 기록

- Mobile report에 logical/unique parameter를 분리했다.
- trainer JSON에 model family, tokenizer hash, cache dir, logical/unique parameter, teacher family/parameter를 추가했다.
- Mobile의 정적 FP32 parameter storage와 실제 CUDA allocated/reserved peak를 구분한다.
- `paired_eval.py --raw-differences`는 고정 margin 판정 없이 raw difference와 95% CI를 출력한다.

### 6.5 스크립트와 로그 문서

- 혼동을 주던 `test_mobile.py`의 유효 검사 항목을 `scripts/validation/validate_mobile_architecture.py`로 정리해 이전하고 원 파일을 삭제했다.
- 새 스크립트는 기본 실행 시 config/산술만 검사하고, 사용자가 `--confirm-heavy`를 명시해야 모델 생성·forward/backward를 수행한다.
- `test_mobile_make_reference.py`와 `test_mobile_weight_parity.py`는 보존했다.
- `parity_reference/PROVENANCE.md`에 reference 세 파일, 생성/검증 스크립트, upstream config와 commit의 hash 경계를 기록했다.
- `P018-R1_test_result`의 세 `.txt` 각각에 대응하는 분석 `.md`를 작성했다.

## 9. 현재 증거 수준

현재 확정할 수 있는 명제:

- TinyLM dense MobileLLM의 선택된 CPU eager path는 공식 source에서 복사한 동일 weight에 대해 seq 8에서 exact parity를 보였다.
- 정적 구현상 g6은 30층을 균등한 5개 MLP 그룹으로 묶고 attention을 공유하지 않는다.
- 공식 32k tokenizer는 로컬에서 load/encode/decode 가능하다.
- 현재 `p018`은 CUDA 지원 build다.

아직 확정할 수 없는 명제:

- 최신 통합 trainer/KD/checkpoint가 실제로 완주한다.
- Tied Teacher가 Dense Teacher와 품질상 같거나 충분히 가깝다.
- memory 절감이 53.24%이거나 속도가 향상된다.
- 어느 teacher가 더 좋은 student를 만든다.
- 3개 seed에서 관측 차이가 안정적이다.

## 10. 사용자와 논의가 필요한 사항

1. **Student architecture**: 가장 통제된 권장안은 `mobile125 tied g6`를 Stage B의 고정 student로 쓰는 것이다. 이 경우 Stage A의 from-scratch Tied Teacher와 No KD Student가 architecture·seed·data·schedule까지 완전히 같다면 동일 run/checkpoint를 두 역할로 재사용할 수 있다. 사용자가 별도의 더 작은 student를 의도했다면 그 shape를 먼저 정해야 한다.
2. **Seed**: 우선안은 `1337, 2024, 3407`이다. 같은 seed 안에서 teacher arm의 초기화/data order, student arm의 초기화/data order 및 평가 예제를 pair한다. 이 세 값을 확정할지 필요하다.
3. **학습 schedule**: 프로젝트 연속성 기준 권장안은 기존 P018의 300M WSD 조건을 양 teacher와 세 student에 동일 적용하는 것이다. 원 논문의 2e-3 cosine/1T는 corpus도 비공개이고 예산이 다르므로 optional replication/sensitivity로 분리하는 편이 타당하다. 정확한 LR·steps·batch를 사용자와 확정해야 한다.
4. **300M corpus의 0.5/0.5 의미**: 기존 정본처럼 문서 선택 확률 0.5/0.5를 유지하고 실제 token ratio를 보고할지, 새 balanced-by-token cache를 만들지 결정해야 한다. 권장안은 R1 1차에서 기존 정본 동작을 유지하되 모든 arm에 같은 exact cache를 쓰고 실측 mix를 명시하는 것이다.
5. **BOS/EOS framing**: 현재 통합안은 공식 SentencePiece segmentation을 쓰되 자동 BOS 없이 문서 끝 EOS 하나를 붙인다. 기존 pipeline과의 일관성은 높지만 원 MobileLLM 비공개 pretokenization과 같다고 증명할 수 없다. 이 규칙을 R1 정본으로 승인할지 필요하다.
6. **실행 조건**: RTX 4070 Ti SUPER에서 sequence length, micro-batch, accumulation, BF16, gradient checkpointing, compile 사용 여부를 mini smoke에서 확정해야 한다. memory 비교는 동일 조건 및 spill 없는 상태에서 수행해야 한다.

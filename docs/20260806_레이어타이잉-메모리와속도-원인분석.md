## 0. 한 줄 답

> **타잉은 기대대로 작동했다.** 상주 메모리를 **2.17배** 줄였고(978.0 → 451.5MB) 이건 유니크
> 파라미터 감소 2.26배와 거의 정확히 일치한다(전이율 108%).
> **기대와 어긋난 것은 타잉이 아니라 두 가지 다른 것**이다:
>
> 1. **메모리** — 절대값이 큰 이유는 타잉이 안 먹혀서가 아니라 **삼진 값을 fp32 로 2벌 들고 있어서**다.
>    파라미터당 이론 **1.71비트**를 **64비트**(4B × 2벌)로 쓰고 있다 = **37.4배**. 타잉과 **직교하는 축**이다.
> 2. **속도** — "묶어서 한 번에 계산" 은 **원리적으로 불가능**하다. 트랜스포머 층은 **잔차 사슬**이라
>    층 i+1 의 입력이 층 i 의 출력이다. **가중치를 공유해도 시간 의존성은 공유되지 않는다.**
>    학습 층 수도 줄지 않는다 — forward·backward 모두 **20층 전부**를 통과한다.
>
> 다만 **사용자 직관이 맞는 지점이 하나 있다**(§5): 계산은 못 묶어도 **언팩(dequant)은 묶을 수 있다.**
> 지금 int8 경로는 같은 MLP 를 층마다 g 번 중복 언팩하고 있고, 이걸 고치면 **타잉이 그대로 속도 레버가 된다.**
> 예상 이득 mC int8 **14.2 → 약 21 tok/s (1.5배)**. 미측정 추정이므로 실험으로 확인해야 한다.

## 1. 실제 구조 — 코드가 무엇을 하는가

### 1.1 가중치는 정말 공유된다 (메모리 축: **의도대로**)

`TiedMLPTransformer.__init__` (`transformer.py`):

```python
self.mid_mlps = nn.ModuleList([MLP(cfg) for _ in range(cfg.n_mlp_groups)])   # ← n_middle/g 개만 만든다
...
for i in range(cfg.n_layers):
    ...
    mlp = self.mid_mlps[j // cfg.mlp_group if cfg.tie_mlp else j]            # ← 같은 객체를 g 번 나눠준다
    layers.append(Layer(cfg, owns, mlp, ...))
```

`Layer.__init__` 은 `self.mlp = [mlp]` — **리스트로 감싸서 모듈 등록을 피한다.** 주석이 그 이유를
밝히고 있다("파라미터 중복 계수 방지"). 즉 **가중치 텐서는 딱 `n_middle/g` 벌만 존재한다.**

**검산** (m100: dim 768 / ffn 2048 / 20층 = 2+16+2):

| 모델 | 유니크 MLP 개수 | MLP 삼진 파라미터 | + 어텐션 | **총 삼진** | 로그값 |
|---|---|---|---|---|---|
| `p6d` (dense, g=1, CLA=1) | 2+16+2 = **20** | 94.37M | 29.49M | **123.86M** | 123.86M ✅ |
| `mC` (g=8, CLA=2) | 2+2+2 = **6** | 28.31M | 26.54M | **54.85M** | 54.85M ✅ |
| `mA` (g=4, CLA=2) | 2+4+2 = **8** | 37.75M | 26.54M | **64.29M** | 64.29M ✅ |

> MLP 하나 = `3 × 768 × 2048` = **4,718,592 파라미터** = fp32 로 **18.0 MiB**.
> dense 의 삼진 파라미터 중 **76.2%가 MLP** 다. 그래서 MLP 만 타이해도 2.26배가 나온다.

**→ 사용자 질문 ①의 답: "n/g 개만 메모리에 올린다"가 맞다.** 저장·상주 모두 그렇다.

### 1.2 그러나 실행은 n 층 전부를 순차로 돈다 (속도 축: **바꿀 수 없다**)

`forward()`:

```python
schedule = self.visit_schedule()          # infer_repeat=1.0 이면 list(range(20))
for step_idx, i in enumerate(schedule):   # ← 20번 돈다
    layer = self.layers[i]
    ...
    x = layer(x, kv, cos, sin, mode_p)    # ← 내부에서 공유 MLP 를 호출
```

`Layer.forward()`:

```python
x = x + self.gates[0] * self.attn(self.ln1(x) * a + self.a_shift, kv, cos, sin, mode_p)
x = x + self.gates[1] * self.mlp[0](self.ln2(x) * m + self.m_shift, mode_p, lora, film)
```

**→ 사용자 질문 ①의 나머지: "반복문으로 실행하는 구조인가, 다 풀어놓고 실행하는 구조인가"**
— 사실은 **둘 다 아니고 그 중간**이다. **가중치는 n/g 벌**(반복문 쪽)인데
**실행은 n 회**(풀어놓은 쪽)다. 그리고 §2 가 보이듯 **그럴 수밖에 없다.**

## 2. 왜 "묶어서 한 번에" 가 불가능한가 — 잔차 사슬

사용자의 기대는 이것이었다:

> g개로 묶어서 동일 가중치의 경우 하나의 그룹 묶음에 해당하는 계산을
> **반복 횟수만큼 묶음으로 연산**가능할 것

묶음 연산(배치 GEMM)이 성립하려면 **g 개의 입력이 동시에 존재**해야 한다. 그런데 층 8개가
같은 MLP `W` 를 쓴다고 할 때 실제 계산은:

```
x₃ = x₂ + g·MLP_W(norm(x₂))
x₄ = x₃ + g·MLP_W(norm(x₃))      ← x₃ 가 나와야 시작할 수 있다
x₅ = x₄ + g·MLP_W(norm(x₄))      ← x₄ 가 나와야 …
```

**층 i+1 의 입력은 층 i 의 출력이다.** 8개를 쌓아 `[x₂;x₃;…;x₉] @ W` 로 한 번에 곱하려면
x₃~x₉ 를 **미리 알아야** 하는데, 그걸 알려면 이미 계산이 끝나 있어야 한다. 순환이다.

> **핵심 구분**: 가중치 공유는 **공간(저장)의 중복**을 없앤다.
> 깊이 방향 의존성은 **시간의 중복이 아니라 시간의 순서**다 — 없앨 대상이 아니다.
>
> ```python
> for i in range(20):
>     x = f(x)          # f 가 하나뿐이어도 20번 불러야 한다
> ```
>
> 이건 RNN 을 시퀀스 축으로 병렬화할 수 없는 것과 **정확히 같은 이유**다.

### 2.1 덧붙여, 층은 MLP 만 공유한다

같은 그룹의 8개 층도 **서로 다른 연산을 한다**:

| 부품 | 공유 여부 |
|---|---|
| MLP `gate/up/down` | **공유**(그룹 내) |
| 어텐션 `q_proj`·`o_proj` | **층마다 독립** |
| 어텐션 `k_proj`·`v_proj` | CLA 그룹(2층)마다 독립 |
| `ln1`/`ln2` 뒤 `a_scale/a_shift/m_scale/m_shift` | **층마다 독립** |
| 잔차 게이트 `gates[0], gates[1]` | **층마다 독립** |
| (설정 시) 층별 LoRA·FiLM | **층마다 독립** |

`Layer.__init__` 이 `mlp_lora=is_mid_tied, mlp_film=is_mid_tied` 로 **타이된 층에만** 층별
보정 장치를 붙이는 것도 같은 취지다 — 공유 MLP 를 층마다 다르게 쓰려고 만든 물건이다.

**→ "같은 계산의 반복" 이 아니다. 같은 가중치를 쓰는 서로 다른 계산의 연쇄다.**

## 3. 왜 학습도 안 빨라지는가

사용자 기대:

> 학습하는 레이어 개수 자체도 n/g 개 층으로 줄어들기 때문에
> 20개 레이어보다는 5개 레이어를 학습하는 것이 빠를 것

**층 수는 줄지 않는다.** 줄어드는 것은 **파라미터 수**이고, 그 둘은 학습 시간에서 완전히 다른 항이다.

| 학습 스텝의 구성요소 | 타잉이 줄이나 | 스텝 시간에서의 비중(m100/4070TiS 실측 기준) |
|---|---|---|
| forward GEMM (20층) | **아니오** | 지배적 |
| backward GEMM (20층, ~2× forward) | **아니오** | 지배적 |
| grad-ckpt 재forward (20층) | **아니오** | 큼 |
| gradient 누적(공유 텐서에 g번 더하기) | **아니오**(오히려 누적이 추가) | 작음 |
| **AdamW 스텝**(파라미터당 elementwise) | **예, 2.09배** | **약 0.1%** |
| **옵티마이저 상태 VRAM**(m,v = 8B/param) | **예, 2.09배** | 시간 아님(용량) |

**AdamW 스텝 비중 추정**: p6d 132.5M 파라미터, AdamW 는 param/grad/m/v 를 읽고 쓰므로
약 20B/param → **2.65GB 의 메모리 트래픽 ≈ 4ms**. 실측 스텝 시간은
`116.6분 × 60 × 1000 ÷ 2289 steps` = **3,057 ms/step**. → **0.13%**.

> **0.13% 짜리 항을 절반으로 줄여도 스텝 시간은 0.07% 빨라진다.** 관측 불가다.

`report()` 의 FLOPs 식이 이걸 그대로 말하고 있다:

```python
per_l = (dim*dim*2 + kv_dim*dim*2) + 3*dim*ffn_dim
flops = 2 * cfg.n_layers * per_l          # ← mlp_group 이 식에 없다
```

**dense 와 mC 는 토큰당 FLOPs 가 `0.248 GFLOP` 로 정확히 같다.** 학습 로그 상단에 둘 다 그렇게 찍힌다.

### 3.1 그래도 실측에는 작은 이득이 있다 (원인은 다른 데 있다)

`docs/EXPERIMENT_BASELINES.md` §2.1 — 같은 300M 풀·300M 학습·plain 조건:

| 태그 | 구성 | 분 | dense 대비 |
|---|---|---|---|
| `dense` | dense | 97.5 | — |
| `t_base` | tied **g4** | 94.9 | **−2.7%** |
| `t_film` | tied g4 + FiLM | 91.4 | −6.3% |
| `t_g8` | tied **g8** | 89.9 | **−7.8%** |

⚠️ **같은 g4 인 `t_base`(94.9)와 `t_film`(91.4)이 3.5분 벌어진다 = 노이즈 폭 ±3.7%.**
g8 의 −7.8% 는 그 2배 남짓이라 **방향은 믿을 만하지만 크기는 못 믿는다.**
그리고 이 표의 런들은 grad-ckpt·EMA 조건이 로그에 안 남아 있다(구 로그 결함, `CLAUDE.md` 참조).

원인은 파라미터 수가 아니라 **§4 와 같은 캐시 지역성**일 가능성이 높다. 확정하려면
**동일 조건 A/B 단일 목적 런**이 필요하다(§6 의 실험 제안 참조).

## 4. 그러면 메모리는 왜 그렇게 큰가 — 원인은 **비트폭 하나**

### 4.1 상주 메모리 실측 (016_log_20260806_P034-stage3b.txt)

| 모델 | 저장(packed, 이론) | **상주(현 구현)** | 배수 |
|---|---|---|---|
| `p6d` | 27.1MB | **978.0MB** | 36.1× |
| `mC` | 13.1MB | **451.5MB** | 34.6× |
| `mA` | 12.4MB | **523.5MB** | 42.2× |

실측식(결과 016):

```
상주 = 유니크삼진 × 4B × 2벌(latent + dequant 사본) + (임베딩 + norm/gate) × 4B
     = 유니크삼진 × 4B × 2벌 + 33.0MB
```

검산: `123,863,040 × 4 × 2 / 1024² = 945.0 MiB` + 33.0 = **978.0** ✅

### 4.2 36배 격차의 분해 — 타잉은 이 격차에 **없다**

| 축 | 배수 | 무엇이 원인인가 |
|---|---|---|
| **비트폭** | **18.7×** | 이론 1.71bpw 를 **fp32(32비트)** 로 들고 있다 |
| **사본 수** | **2.0×** | latent(학습용 원본) + dequant 사본이 동시에 상주 |
| 곱 | **37.4×** | 실측 36.1× 와 일치(차이는 33MB 고정분) |
| ~~타잉~~ | **1.0×** | **격차에 기여하지 않는다** |

> **★타잉은 이 격차의 원인이 아니라, 격차 앞단의 절대량을 이미 줄여 놓은 요인이다.**
> `978.0 → 451.5` 은 타잉이 **이미 벌어 놓은 2.17배**다.

## 5. ★사용자 직관이 맞는 지점 — **계산은 못 묶어도 언팩은 묶을 수 있다**

§2 에서 "묶음 연산은 불가능" 이라고 했지만, 그건 **GEMM 이야기**다. 지금 코드에는
**묶을 수 있는데 안 묶고 있는 작업이 하나 있다.**

### 5.1 현재 int8 경로의 낭비

`TLinear.forward()` (`ternary.py`):

```python
if self._i8 is not None:          # P034 단계3: int8 저장
    wq = self._wq_from_i8()       # ★fp32 로 되돌린다 — forward 호출마다
else:
    wq = self._wq if self._wq is not None else ternary(self._w(), self.cfg)
y = F.linear(x, wq)
```

`_wq_from_i8()` 은 int8 코드 × 그룹 α 를 **fp32 버퍼로 물질화**한다. MLP 하나면 **18.0 MiB 를 쓰고
다시 읽는다.** 그리고 이 함수는 **`TLinear` 객체당이 아니라 `forward` 호출당** 불린다.

**g8 에서 중간 16개 층은 유니크 MLP 가 2개뿐인데 언팩은 16번 일어난다.**

### 5.2 왜 이게 낭비인가 — 층 스케줄이 이미 연속이다

`mid_mlps[j // mlp_group]`, `j = i - n_prelude` 이므로 g=8 에서:

| 층 i | j | 그룹 |
|---|---|---|
| 2 ~ 9 | 0~7 | **그룹 0** (연속 8층) |
| 10 ~ 17 | 8~15 | **그룹 1** (연속 8층) |

**같은 MLP 를 연속으로 8번 쓴다.** 한 번 언팩해서 8층 동안 들고 있다가 버리면 된다.
버퍼는 **동시에 1개**만 살아 있으므로 **메모리 이득을 훼손하지 않는다.**

### 5.3 기대 이득 (추정 — 미측정)

결과 014 §11.4 의 실측: **int8 이 층당 +2.13~2.24ms** 를 얹는다. MLP 는 층당 삼진 파라미터의
76.2% 이므로 그중 약 **1.7ms/층**이 MLP 언팩이다.

| 모델 | 현재 int8 (3B 실측) | 중복 언팩 제거 시 절감 | **예상** |
|---|---|---|---|
| `mC` (g8) | 14.23 tok/s (70.3 ms/tok) | 중간 16층 → 2회: **−23.8ms** | **≈ 21.5 tok/s (1.51×)** |
| `mA` (g4) | 14.33 tok/s (69.8 ms/tok) | 중간 16층 → 4회: **−20.4ms** | **≈ 20.2 tok/s (1.41×)** |
| `p6d` (g1) | 13.73 tok/s | **0** (공유 없음) | 13.73 (불변) |

> **이 최적화의 의미는 숫자보다 방향에 있다** — 지금까지 타잉은 **메모리 축 전용 레버**였다
> (결과 014 §11.3: "타잉은 저장을 줄이지 컴퓨트를 안 줄인다"). 이건 그 문장이 **언팩 비용에는
> 해당하지 않는다**는 뜻이고, **타잉 강도 g 가 클수록 이득이 커진다.**
> **R8(1.375bpw 패킹)에도 그대로 적용된다** — 언팩이 비쌀수록 이득이 커지므로 **오히려 R8 쪽에서 더 크다.**

⚠️ **위 숫자는 전부 추정이다.** 층당 비용 분해(76.2%)가 파라미터 비율에 비례한다고 가정했고,
캐시 거동은 선형이 아니다. **실험(P034 단계3C)으로 확인해야 한다.**

### 5.4 §4.2 의 캐시 지역성 관측과의 관계

결과 014 §11 의 층당 비용 `b`: **g8 0.913 < g4 1.022 < dense 1.163 ms** (g 순서로 단조).
이건 **fp32 경로**의 관측이다. MLP 가중치 fp32 = 18.0 MiB 로 **L3 32MB 안에 들어간다**:

- **dense**: 20개 서로 다른 18.0 MiB 블록 → 매 층 DRAM 에서 읽는다
- **g8**: 같은 18.0 MiB 블록을 연속 8층이 재사용 → L3 에 남아 있을 수 있다

**즉 §5 의 언팩 묶음은 이미 관측된 21.5% 캐시 이득의 "명시적 버전"이다.**
하드웨어 캐시가 우연히 해 주던 일을 코드가 직접 하는 것.

## 6. 결론 — 질문별 답

| 사용자 질문 | 답 |
|---|---|
| n/g 개만 메모리에 올리나, n 개를 다 푸나 | **가중치는 n/g 벌**(§1.1 검산 3건 일치). **실행은 n 회**(§1.2) |
| 묶어서 계산하면 훨씬 빠르지 않나 | **불가능하다.** 잔차 사슬이라 층 i+1 입력이 층 i 출력이다(§2). GEMM 은 못 묶는다 |
| 학습도 n/g 층이면 빨라지지 않나 | **층 수는 안 줄어든다.** 줄어드는 건 파라미터 수 → AdamW 스텝(**전체의 0.13%**)뿐(§3) |
| 그런데 왜 메모리가 그렇게 큰가 | **타잉 탓이 아니다.** fp32(18.7×) × 2벌(2.0×) = **37.4배**. 타잉은 이미 2.17배 벌어 놨다(§4) |
| 왜 속도가 타잉에 따라 안 변하나 | 층당 FLOPs 가 **같기 때문**(`report()` 식에 `mlp_group` 없음). 남는 이득은 **캐시 지역성 21.5%** 하나(§4·§5.4) |
| **그래도 뭔가 할 수 있나** | **있다.** 계산은 못 묶어도 **언팩은 묶을 수 있다**(§5). g 가 클수록 이득이 커진다 |

## 7. 한계

- §5.3 의 이득 추정은 **파라미터 비율 기반 안분**이다. 실제 캐시 거동은 비선형이라 빗나갈 수 있다.
- §3.1 의 학습 시간 표는 **구 로그**라 grad-ckpt·EMA 조건이 남아 있지 않다. **인과 주장에 쓰면 안 된다.**
- §4.2 의 "18.7 × 2.0" 분해는 삼진 항만 본 것이다. 33.0MB 고정분은 두 축 어디에도 안 들어간다.
- CPU 캐시 미스 카운터가 없다 — §5.4 의 L3 설명은 **여전히 가설**이다(결과 014 §11 과 동일한 유보).

## 1. 이 지적이 정확한 이유 — 지금 우리가 보고하는 숫자의 정체

`mem_breakdown()` 은 **"삼진 가중치를 1.95(또는 1.25) bpw 로 패킹했다면 몇 MB 인가"** 를 계산한다.
그건 **디스크·전송 크기**이고 **아직 존재하지 않는 패킹 포맷의 이론값**이다.
현재 코드가 실행 중 실제로 들고 있는 것은 다음과 같다.

| 텐서 | 무엇 | dtype | dense 기준 크기 |
|---|---|---|---|
| `TLinear.weight` | latent(고정밀) 가중치 — **체크포인트에 저장되는 실체** | fp32 | 120.9M × 4B = **461MB** |
| `TLinear._wq` | `refresh_quant()` 가 만든 **dequant 된 삼진값** ({-α,0,+α}) | fp32 | **461MB** |
| 활성값·KV | 시퀀스 길이에 비례 | bf16/fp32 | 별도 |

**즉 최악의 경우 두 벌이 동시에 상주한다.** `_wq` 의 값이 삼진이라도 **저장 형식은 fp32** 이므로
메모리 이득이 **0** 이다. 보고서의 30.9MB / 11.7MB 는 **이 상태를 전혀 반영하지 않는다.**

> **★그러므로 "2.64× 감축"은 현재 조건에서 '전송·저장 기준'으로만 참이다.**
> 실행시 상주 메모리 기준으로는 **아직 측정된 적이 없고, 감축이 없을 가능성이 높다.**
> 이건 프로젝트의 1순위 목표("연산이 아니라 메모리 최적화")에 **직접 걸리는 문제**다.

## 1.1 ★저장↓ 이 상주↓ 와 단조인가 — **아니다. 그리고 순위가 역전한다**

두 감축 레버가 **서로 다른 양**을 줄인다.

| 레버 | 무엇을 줄이나 | 저장 MB | **상주 MB** |
|---|---|---|---|
| **MLP 타잉**(g↑) | **유니크 파라미터 수** | 줄어듦 | **줄어듦** |
| **삼진**(16→1.95bpw) | 가중치당 비트 수 | 줄어듦 | **그대로**(fp32 로 들고 있으므로) |
| **3:4 희소**(1.95→1.25bpw) | 가중치당 비트 수 | 줄어듦 | **그대로** |

상주량은 `유니크 파라미터 × 4바이트 × (latent + dequant 사본)` 이라 **bpw 와 무관**하다.
즉 **저장 감축의 일부만 상주로 전이되고, 전이율은 레버마다 다르다** → 단조도 비례도 아니다.

**그래서 순위가 뒤집힌다**(검정 가능한 예측):

| 모델 | 삼진 유니크 파라미터 | 저장 MB | 상주 예측 |
|---|---|---|---|
| `mC_g8_k4` | **54.9M** | 14.9 (더 큼) | **더 작음** |
| `mA_g4s34_k4` | **64.3M** | 11.7 (더 작음) | **더 큼** |

> **`mA` 는 저장이 가장 작은데 상주는 `mC` 보다 크다.** 우리는 REVIEW1 에서 **저장 MB 를
> 기준으로 A 를 승자로 뽑았다**(A vs C 가 노이즈 안이라 "메모리 작은 쪽"을 택했다).
> **상주 기준이었다면 C 를 뽑았어야 한다.** 단계 1 이 이 역전을 확인하면
> **REVIEW1 의 승자 선정 근거를 재검토해야 한다.** — 이게 이 계획의 최대 파급이다.

## 1.2 저장 ≈ 상주 로 만들 수 있는가 — **가능하다. 다만 커널이 필요하다**

원리적으로 가능하고 업계 표준 해법이 있다(llama.cpp 계열 Q-포맷, bitsandbytes 등).
핵심은 **"패킹된 채로 들고 있다가 GEMM 타일 단위로만 즉시 풀기"** 다.
그러려면 세 가지를 동시에 만족해야 한다.

1. **latent `weight` 를 버린다** — 추론엔 역전파가 없으므로 불필요하다. (단계 2)
2. **dequant 전체 사본을 만들지 않는다** — 지금은 `_wq` 가 전체 텐서다. 타일 단위로 풀어
   레지스터/L1 에서 소비하고 버려야 한다. (단계 3~4)
3. **패킹 포맷으로 저장** — int8(단계 3) → 5비트 무낭비 패킹(단계 4).

이걸 다 하면 상주 ≈ 저장 + 활성값 + KV 로 수렴한다. **단 커스텀 커널 없이는 불가능**하고,
`F.linear` 를 쓰는 한 dequant 된 전체 텐서가 필요하다. **그게 이 계획의 본질적 비용이다.**

**중간 목표로도 의미가 크다**: 단계 2(latent 해제)만으로 **상주가 절반**이 된다.
커널 없이, 되돌릴 수 없는 전환 하나로 얻는다.

## 3. 단계 설계 (싼 것 → 비싼 것, 각 단계가 다음의 게이트)

### 단계 0 — **선결**: 결과 014 의 계측 결함 수정 ✅ **완료(2026-07-31)**

**최초 진단이 틀렸었다.** "`load_model()` 이 `refresh_quant()` 를 안 부른다"가 아니라
**`transformer.forward()` 가 매 호출마다 `refresh_quant()` 를 무조건 부른다**가 실제 원인이다
(학습 중에는 latent 가 스텝마다 바뀌므로 **그게 맞다**. 추론에서만 낭비다).
→ `freeze_quant()` 를 만들어 1회만 계산하고 forward 가 건너뛰게 했다.
`clear_quant()` 가 플래그를 되돌린다(학습 재개 시 안전). `evaluate()` 에도 적용해
eval 루프의 `iters` 배 낭비를 제거했다.

### 단계 1 — **실행시 메모리 실측** (Q1, Q2, Q5) ✅ **완료(결과 016)** — 예측 적중

- **측정 방법**: CPU 는 `psutil.Process().memory_info().rss` 를 (a) 로드 전 (b) 로드 후
  (c) `refresh_quant()` 후 (d) forward 중 피크 로 4점 측정.
  GPU 는 `torch.cuda.max_memory_allocated()`(이미 trainer 에 있는 방식 재사용).
- **모델**: `p6d` / `mC_g8_k4` / `mA_g4s34_k4` — 결과 014 와 같은 3종으로 대조 가능하게.
- **★단조성 검정(Q6)**: 저장 기준 순위와 상주 기준 순위를 나란히 인쇄해 **역전 여부를 직접 본다.**
  `mA < mC`(저장) 인데 `mC < mA`(상주) 로 나오면 §1.1 예측이 맞은 것이다.
- **전이율** = `(상주감축−1)/(저장감축−1)` 을 모델별로 계산한다. 100% 면 완전 전이,
  0% 면 저장만 줄고 상주는 그대로. **레버별로 다를 것**이라는 게 §1.1 의 요지다.
- **동시에 `mem_breakdown()` 의 이론값을 같은 표에 인쇄**해 **이론 대 실측의 괴리를 명시**한다.
  이 표 하나가 P034 의 핵심 산출물이다.
- **판정**: 실측 감축비가 이론 감축비(2.64×)에 **얼마나 못 미치는지**를 배수로 기록한다.

> **예상(정직하게)**: 실측 감축은 **타잉분만** 나타날 것이다. 세 모델 모두 fp32 latent 를
> 들고 있고, 타잉 모델만 유니크 가중치가 적다(mC 는 dense 의 45%).
> **즉 "타잉의 메모리 이득은 실행시에도 진짜, 삼진·희소의 이득은 아직 이론값"** 일 가능성이 높다.
> 그 구분이 나오는 것만으로도 이 단계는 값어치를 한다.

**실행**: `run_P034_memory.bat` (→ `scripts/mem_runtime.py`). CPU·GPU 각 1회, 수 분.

### 단계 2 — **`_wq` 단독 상주 모드** (Q2) ⏸ **대기 — 절감 배수가 정확히 2.00× 로 확정됐다**

추론에서는 latent `weight` 가 **필요 없다**(역전파가 없으므로). `refresh_quant()` 후
`weight` 를 해제하면 **즉시 절반**이 된다.

- 구현: `to_inference()` 같은 메서드로 `_wq` 만 남기고 `weight` 를 `None` 또는 meta 로 교체.
- **주의**: `_w()` 의 `center_weights` 경로와 `clear_quant()` 가 `weight` 를 다시 요구하므로
  **되돌릴 수 없는 단방향 전환**으로 설계하고 그 사실을 문서화한다.
- 판정: 단계 1 대비 **RSS 가 실제로 절반**이 되는지. 안 되면 다른 곳에 사본이 있다는 뜻.

### 단계 3 — **int8 저장 경로** (Q3) ⏸ 대기 — 패킹 전 중간 단계

삼진값 {-1,0,+1} + 그룹별 스케일 α 로 분해해 **int8 + fp16 스케일**로 들고,
GEMM 직전에만 dequant 한다.

- fp32 대비 **4배** 절감(1.95bpw 이론 대비로는 여전히 4배 손해지만, **실현 가능한 첫 이득**).
- GEMM 마다 dequant 하면 연산이 늘어난다 → **메모리는 줄고 속도는 나빠지는 교환**.
  CLAUDE.md 의 "연산 증가는 감수" 원칙과 정합하지만 **얼마나 나빠지는지 실측이 필요**하다.
- 판정: 메모리 4배 절감 대비 tok/s 하락이 **2배 이내**면 채택 검토.

### 단계 4 — **5비트 패킹 커널** (Q4) ⏸ 조건부·최고비용 — **mA 의 우위는 이 단계가 있어야 실현된다**(결과 016 §3)

3:4 희소 삼진은 `C(4,3)·2³ = 32 = 2⁵` 로 **4가중치당 5비트 무낭비 패킹**이 가능하다(P016 설계).
이게 1.25bpw 의 실현이다. **단계 3 이 "메모리는 주는데 너무 느리다"로 끝나면
이 단계가 유일한 출구**이고, 단계 3 이 충분하면 보류할 수도 있다.

- `scripts/bench_fp8_gemm.py` 와 `ternary_kernel.py` 의 기존 자산을 재활용한다.
- **선행 조건**: P030 단계 1(KV 캐시)이 끝나 있어야 커널 이득이 측정 가능한 비중이 된다.

## 5. ★★`mem_breakdown()` 단일 규약 — **수정안 3개 비교** (2026-07-31 신설, 결정 대기)

결과 016 §7.4·§8.4 가 확인한 문제: **삼진 1.95 와 sparse34 1.25 가 다른 회계**였다.
`1.95 = 코드 + 그룹스케일 + 컨테이너` 인데 `1.25` 는 **순수 코드공간뿐**이다.
어느 규약으로 통일할지 결정해야 하고, **셋 다 나름의 근거가 있다.**

### 구성 요소 (셋 다 이걸 조합한다)

| 요소 | 값 | 근거 |
|---|---|---|
| 삼진 코드 | **log₂3 = 1.58496** | 정보이론 하한(세 심볼). **설계 시점에 아는 상수** |
| 3:4 코드 | **1.25** (정확) | `C(4,3)·2³ = 32 = 2⁵` — 5비트 무낭비. 논문 §3.1 |
| 그룹 스케일 | **0.125** | fp16 α 1개 / `micro_group`=128 가중치 |
| 컨테이너 오버헤드 | **0.274**(역산) | `1.95 − (측정엔트로피 1.554 + 0.125)`. GGUF 가정 |

### 세 안의 수치 (임베딩은 3:4 대상이 아니므로 셋 다 삼진 bpw 적용)

| 안 | 삼진 bpw | s34 bpw | `p6d` | `mC_g8_k4` | `mA_g4s34_k4` | mA 감축 | mC 감축 |
|---|---|---|---|---|---|---|---|
| **A 코드만** | 1.585 | 1.250 | 25.0MB | 12.0MB | 11.2MB | 2.23× | 2.09× |
| **B 코드+스케일** | **1.710** | **1.375** | 27.0MB | 12.9MB | 12.3MB | 2.20× | 2.09× |
| **C B+컨테이너** | 1.950 | 1.649 | 30.8MB | 14.7MB | 14.6MB | 2.10× | 2.09× |

> **어느 안에서도 순위는 같고 `mC` 감축비는 2.09× 로 불변**이다. 달라지는 것은
> **절대 MB 와 `mA` 의 감축비**(2.23× ~ 2.10×)뿐이다. 현행 표기(2.66×)는 세 안 어디에도 없다.

### 안별 근거·장단점

| | **A 코드만** | **B 코드+스케일** ★권고 | **C B+컨테이너** |
|---|---|---|---|
| **근거** | 정보이론 하한. "기법 자체"의 비용 | **아키텍처가 결정하는 저장량 전부.** 코드도 스케일도 **우리가 반드시 저장해야** 한다 | 현행 1.95 와의 연속성. 실제 배포 파일 크기에 가장 가깝다 |
| **장점** | 가장 순수. 양자화 기법끼리 비교할 때 공정 | ① **`log₂3 + 0.125 = 1.7100` 이 문서의 "g128 삼진 1.71" 과 정확히 일치**<br>② 논문 기준선 **1.67 과 직접 비교 가능**(Sherry 1.67 → 1.25)<br>③ **포맷 선택에 독립** — 아키텍처 비교에 포맷 오버헤드가 안 섞인다 | 기존 문서 수치가 **비-s34 런에서 전부 그대로**(30.9MB 등). 정정 범위 최소 |
| **단점** | **스케일을 무시** — α 없이는 복원이 불가능한데 안 센다. 실제 파일보다 작다 | 컨테이너 제외 → 실제 GGUF 파일보다 작다 | ★**0.274 는 역산 추정**이고 **GGUF 가정**이다. 그런데 **우리는 GGUF 를 쓰지 않는다**(핸드오프: 현 아키텍처는 bitnet.cpp 비호환).<br>★**log₂3 을 쓰면 1.984 가 되어 1.95 와 어긋난다** — 1.95 를 유지하려면 **학습 후에만 아는 실측 엔트로피(1.554)** 가 필요한데, `report()` 는 **학습 시작 전**에 호출된다(가중치가 난수). **설계 시점에 계산 불가** |

### ★권고: **B 를 정본, C 를 병기**

1. **B 만이 설계 시점에 계산 가능한 고정 상수**로 닫힌다(`log₂3 + 0.125`). C 는 1.95 를
   유지하려면 실측 엔트로피가 필요한데 그건 **학습 후에만** 안다 — `report()` 가 못 쓴다.
2. **B 는 우리가 실제로 저장해야 하는 것 전부**다. 코드 없이는 값을, 스케일 없이는 크기를
   복원할 수 없다. 컨테이너는 **포맷 선택의 문제**이고 아직 포맷을 안 정했다.
   **아키텍처 비교에 포맷 오버헤드를 섞으면 아키텍처가 아닌 것이 비교에 들어온다.**
3. **B 가 논문과 같은 층위**다(Sherry 1.67 vs 우리 1.710). 앞으로 외부 비교가 쉬워진다.
4. **C 를 버리지 않는 이유**: 기존 문서·리뷰의 30.9MB 계열과 연속성이 있고, "실제 파일이
   얼마나 될까"라는 질문에는 C 가 답한다. → **json 에 둘 다 기록**한다.

### 구현안

```python
# mem_breakdown(convention="B") 로 계산하고 json 에 셋을 함께 기록
res["packed_mb"]        = ...   # 안 B (정본)
res["packed_mb_container"] = ...   # 안 C (참고)
res["runtime_mb"]       = ...   # 상주 = 유니크삼진 × 4B × 2벌 + 기타 (결과 016)
res["bpw_convention"]   = "B: code(log2 3) + group scale(16/micro_group)"
```

- **`deploy_mb` 는 유지하되 `packed_mb` 의 별칭**으로 두고 문서에서 사용 중단(구 로그 호환).
- `compare.py`·`report()` 가 **`packed_mb` 와 `runtime_mb` 를 나란히** 출력한다.
- **소급 재계산 가능** — 저장 MB 는 파라미터 수의 함수라 **재학습 불필요**(결과 016 §8.1).

> **결정 필요**: 사용자 승인 후 구현. 승인 전에는 문서에 **"현행 회계"** 임을 병기한다.

## 7. 한계·리스크

- **RSS 는 할당자(allocator) 영향을 받는다.** PyTorch 는 해제한 메모리를 OS 에 즉시 돌려주지
  않는다 → **RSS 가 실제 사용량보다 클 수 있다.** `torch` 텐서 크기 합산과 **두 방식 병기**가 필요하다.
- **단계 3·4 는 품질을 바꾸지 않아야 한다.** 수치적으로 동일한 값을 다른 형식으로 담는 것이므로
  **val_loss 가 비트단위로 같아야** 하고, 다르면 구현이 틀린 것이다. 이 검증을 반드시 넣는다.
- 단계 4 는 공수가 크다. **단계 1~3 의 실측 없이 착수하지 않는다.**
- 이 계획은 **메모리를 다루지 속도를 다루지 않는다.** 속도는 P030 소관이고,
  단계 3~4 는 오히려 **속도를 희생**할 수 있다.
- **§1.1 의 역전 예측이 맞더라도 REVIEW1 의 품질 결론은 그대로다.** 바뀌는 것은
  "어느 모델이 더 작은가"의 기준이지 val_loss 가 아니다. 두 판단을 섞지 않는다.
- 단계 2 의 `to_inference()` 는 **단방향**이다. 같은 프로세스에서 학습을 재개하려면
  체크포인트를 다시 로드해야 한다. 이걸 문서화하지 않으면 나중에 조용한 버그가 된다.

### 신설 — 단계 3C: **언팩을 층이 아니라 유니크 MLP 단위로**

**왜**(근거: [`docs/20260806_레이어타이잉-메모리와속도-원인분석.md`](../docs/20260806_레이어타이잉-메모리와속도-원인분석.md) §5):

현재 `TLinear.forward()` 는 `_wq_from_i8()` 을 **forward 호출마다** 부른다.
그런데 g8 에서 중간 16개 층은 **유니크 MLP 가 2개**뿐이다 → **같은 언팩을 16번 한다.**
층 스케줄이 `mid_mlps[j // g]` 라 **같은 MLP 를 연속으로 g 번** 쓰므로,
한 번 언팩해서 g 층 동안 들고 있다가 버리면 된다. **살아 있는 버퍼는 항상 1개** = 메모리 이득 무손상.

**예측(반드시 대조할 것)**

| 모델 | 현재 int8 | **예측** | 근거 |
|---|---|---|---|
| `mC` (g8) | 14.23 tok/s | **≈ 21.5 (1.51×)** | 층당 +2.24ms 중 MLP 몫 76.2% × 중간 14층 절감 |
| `mA` (g4) | 14.33 | **≈ 20.2 (1.41×)** | 중간 12층 절감 |
| `p6d` (g1) | 13.73 | **13.73 (불변)** | 공유가 없다 → **이게 대조군이다** |

> **`p6d` 가 안 변하는 것이 이 실험의 게이트다.** 셋 다 빨라지면 다른 것을 잰 것이다.

**필수 게이트**: 로짓 동등성 `max|Δlogit| = 0.000e+00`. 언팩 결과는 비트 동일해야 한다.

**구현 범위**(작다):
- `TLinear` 에 `_i8_cache` + `_i8_gen`(세대 카운터) 추가
- `TiedMLPTransformer.forward()` 진입 시 세대 증가 → 같은 forward 안에서만 재사용
- 기본 **off**(`--unpack-cache`)로 넣어 종전 경로 비트 동일 보장

**비용**: 구현 소, 측정 수 분, GPU 0. **★단계 4(R8)보다 먼저 한다** — R8 은 언팩이 더 비싸므로
이 최적화가 **R8 의 전제조건**에 가깝다.

### 신설 — 단계 5: 임베딩·norm 패킹

### 10.1 단계 3C 1차 — **실패. 대조군이 잡았다** ([결과 016 §13](../test_result/016_20260731110000_P034-실행시메모리-순위역전확인.md))

| 예측(§9 단계3C) | 실제 | 판정 |

| `mC` 14.23 → 약 21.5 tok/s (1.51×) | 14.48 → **15.18** (1.05×) | ⚠️ 방향만 |
| `mA` 14.33 → 약 20.2 (1.41×) | 14.25 → 14.29 (1.00×) | 🚫 |
| **`p6d` 불변(대조군)** | 13.85 → **8.26** (**0.60×**) | 🚫 **대조군 붕괴** |

원인 2건(코드 확인 완료): ① 공유되지 않는 모듈까지 캐시를 켰다 → dense 는 적중 0 인데
**fp32 472.5MB** 를 들고 있었다 ② 버퍼를 다음 forward 까지 해제하지 않았다.
그리고 **`tensor_mb()` 가 그걸 안 세서 상주 회계가 눈이 멀어 있었다.**

**수정 완료(2차)**: 공유 모듈만 무장(dense 는 대상 0개 = 완전 동일 경로) + 그룹 이탈 시 즉시 해제
(동시 버퍼 상한 **1벌 ≈ 18.9MB**) + `tensor_mb()` 가 `_i8_cache` 를 센다.
**재실행 = `run_P034_stage3c2_unpackcache.bat`**, 게이트에 **`p6d` 불변 검사** 추가.

> **★얻은 것**: 결과 016 §13.5 가 실패 데이터에서 **대가의 단위 계수**를 역산했다
> — **0.1035 ms/tok per MB**. 이건 앞으로 "메모리를 늘려 속도를 사는" 모든 판단의 환율이다.

### 10.2 ★단계 5 재정의 — 문제는 임베딩이 아니라 **헤드 타이잉**이다

**신규 발견**: `cfg.quantize_embedding=True` 는 **`mem_breakdown()` 의 저장 계산에만** 쓰이고
`self.emb` 는 평범한 `nn.Embedding`(fp32)이다. **임베딩은 한 번도 양자화된 적이 없다.**
→ `packed_mb` 27.1MB 는 삼진뿐 아니라 **임베딩 쪽에서도 없는 포맷을 가정**하고 있었다.

상주 분해(mC, int8 이후 86.9MB):

| 항목 | MB | 비중 |
|---|---|---|
| 삼진 int8 + α | 53.9 | 62% |
| **`emb.weight`(32768×256 fp32)** | **32.0** | **37%** |
| `emb_up` + norm/gate | 1.0 | 1% |

**단순 int8 화가 성립하지 않는 이유**: 임베딩이 **출력 헤드와 묶여 있다**.

```python
logits = F.linear(F.linear(x, self.emb_up.weight.t()), self.emb.weight)
```

조회는 행 몇 개만 되돌리면 되지만 **헤드는 (32768, 256) 전체를 GEMM 에 넣는다.**
int8 저장 + 헤드에서 fp32 복원 = **forward 마다 32.0MB 쓰고 읽기** =
§10.1 의 환율로 **+3.3 ms/토큰(약 +5%)**. **§13 이 방금 저지른 것과 같은 종류의 트레이드**다.

### 10.3 선택지와 판정

| 안 | 내용 | 판정 |
|---|---|---|
| (a) 헤드를 임베딩에서 분리(untie) | 파라미터 +8.4M | 🚫 **메모리 목표와 정면 충돌** |
| (b) 헤드를 int8 GEMM(`torch._int_mm`) | 활성값도 int8 필요 | ⏸ 연구 과제. **P014 와 같은 물건** |
| (c) **어휘 축소** | 32,768 → 24,000 이면 임베딩 −26.7% | 🚫 **P039 가 닫았다** — §10.4 |
| (d) 임베딩 랭크 축소(E 256→128) | 재학습 필요, 품질 미지 | ⏸ **P041 단계2 와 묶어서** 검토 |
| (e) 헤드만 스트리밍 matvec | 디코드는 (1,256)×(256,32768) **matvec** 이라 언팩 사본 없이 스트리밍 가능 | ⏸ **커스텀 커널 = P014** |

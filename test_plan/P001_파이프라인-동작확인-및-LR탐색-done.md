# 실험계획 P001 — 파이프라인 동작확인 + 자동 LR 탐색

## 목적
- 코드/데이터/학습 파이프라인이 오류 없이 도는지 확인(품질 판정 아님).
- 본 실행에 쓸 LR을 발산 없이 안전하게 확정.

## 아키텍처
- `tiny` 프리셋(d=256, 1+4+1, g2, cla2) — 파이프라인 확인용.
- `m100` 프리셋 — LR 탐색용(본 실행과 동일 구조).

## 실행

```cmd
:: (1) 파이프라인 동작확인 — 합성·컴파일, 수 분
python run100m.py all --tiny --data synthetic --tokens 2M --steps 40 ^
    --micro-bs 4 --seq 128 --accum 2 --eval-every 20 --compile

:: (2) 자동 LR 탐색 (range test 기본 + grid 고급)
python run100m.py lrfind --arch tied --data ko-en --tokens 50M --method both
```

## 판정/산출
- NaN·`[skip]` 없이 완주하면 파이프라인 정상.
- lrfind: `|g|`가 10을 넘지 않고 loss 단조감소하는 가장 큰 LR 채택.
  (실측: range test 발산 ~1.7e-3 → 권장 5.6e-4, 실런 검증으로 **1e-3** 채택.)

## 비고
- 합성 데이터는 순수 암기 과제라 품질 판정 불가(파이프라인 전용).
- `--compile-mode reduce-overhead`는 임베딩 타잉과 충돌 → `default` 사용.

# P001B — LR 재탐색 (현행 유효배치 기준) · 2026-07-30 추가

## 왜 다시 하는가 — 위 §실행 (2)의 전제가 **둘 다 만료됐다**

`lr 1e-3` 은 위에서 확정한 값인데, 그 근거 두 개가 지금은 성립하지 않는다.

**(a) 발산을 막으려고 낮춘 값이다.** v5 안정화(**QK-norm**, NaN 가드, `|g|` 클립) 이후
실제 런의 `grad_max` 는 **1.0 근처**다(결과 012 기준). 1e-3 을 강제했던 천장이 사라졌는데
**한 번도 재확인하지 않았다.**

**(b) ★위 명령에 `--accum` 이 없다 → CLI 기본 8 로 측정됐다.**
즉 **유효배치 65K 토큰**에서 찾은 LR 인데, 현행 표준은 **`--accum 16` = 131K** 다(CLAUDE.md).
최적 LR 은 배치 크기에 의존하므로(선형~√ 스케일링) **우리가 쓰는 LR 은 실제 학습 배치의
절반에서 측정된 값**이다. 이건 추정이 아니라 명령줄에서 확인되는 사실이다.

**왜 지금**: P033(Chinchilla)이 **18~28시간**이다. 그 시간을 잘못된 LR 로 태우는 것이
현재 계획 전체의 **최대 단일 리스크**이고, 이 재탐색은 **1시간**이다. 미검증 레버 중 가장 값싸다.

## ★한계 — 코드를 읽고 확인한 것 세 가지 (결과 해석에 반드시 반영)

1. **`lr_finder._make()` 는 `build_config(preset, arch, seq, ckpt)` 만 호출한다.**
   `--mlp-group`·`--sparse34` 를 **반영하지 않는다.** 따라서 이 실험이 주는 값은
   **plain dense / plain tied 의 LR 이고 mA(g4+s34) 의 LR 이 아니다.**
   mA 의 LR 을 직접 알려면 `_make` 를 확장해야 한다(별건).
2. **`set_anneal(0.0)`(완전 FP, 삼진 없음)에서 측정한다.** 과거 발산이 어닐 이전에
   났으므로 의도된 설계지만, **삼진 QAT 구간의 안정성은 전혀 보지 않는다.**
3. **range test 의 `safety=3.0` 은 CLI 로 조정할 수 없다.** 그리고 **이 저장소에서
   이미 한 번 과보수적임이 드러났다** — P001 에서 range 는 5.6e-4 를 권했는데 실런은
   1e-3 을 문제없이 소화했다. → **grid 를 신뢰하고 range 는 천장(`diverge_lr`)으로만 읽는다.**

## ★함정 — `lrfind.json` 은 고정 파일명이다

`lr_find()` 는 항상 `runs/logs/lrfind.json` **하나에** 덮어쓴다(태그 없음).
호출을 3회 하면 **앞의 두 결과가 사라진다.** 배치가 매 호출 직후 회차별 파일로
복사하므로 **그 `copy` 줄을 지우면 안 된다.**

## 실행 → `run_P001B_lrfind.bat`

```cmd
:: [1] dense, accum 16 — 교사. 가장 중요(모든 KD 런이 품질을 물려받고, P033 dense 가 17h)
python run100m.py lrfind --arch dense --preset m100 --data ko-en --tokens 300M --method both ^
    --micro-bs 8 --seq 1024 --accum 16 --lrs 6e-4,1e-3,2e-3,3e-3,4e-3 --lrfind-steps 150

:: [2] tied, accum 16 — 학생. MLP 공유로 가중치당 그래디언트 크기가 달라 최적이 같을 이유가 없다
python run100m.py lrfind --arch tied  --preset m100 --data ko-en --tokens 300M --method both ^
    --micro-bs 8 --seq 1024 --accum 16 --lrs 6e-4,1e-3,2e-3,3e-3,4e-3 --lrfind-steps 150

:: [3] 대조군 — dense, accum 8 (P001 조건 재현). 이게 이 실험의 타당성을 검증한다
python run100m.py lrfind --arch dense --preset m100 --data ko-en --tokens 300M --method both ^
    --micro-bs 8 --seq 1024 --accum  8 --lrs 6e-4,1e-3,2e-3,3e-3,4e-3 --lrfind-steps 150
```

**설계 결정 3개**

| 결정 | 이유 |
|---|---|
| `--tokens 300M`(기존 정본 캐시 재사용) | 새 `prepare` 를 안 돌린다. **풀 크기는 여기서 무의미** — 품질이 아니라 발산을 재기 때문. 위 P001 은 50M 을 썼는데 별 캐시를 또 만들 이유가 없다 |
| `--lrs` 상단 확장(`…3e-3,4e-3`) | 기본값이 `3e-4,6e-4,1e-3,2e-3` 인데 **우리 가설은 "1e-3 위에 여유가 있다"** 다. 상단을 넓히지 않으면 가설을 검정할 수 없다 |
| **대조군 [3] 포함** | (b) 주장을 **가정이 아니라 측정**으로 만든다. accum 8 이 P001 의 발산 1.7e-3 근처로 재현되고 accum 16 이 더 높게 나오면 배치 의존성이 실증된다. **같게 나오면 (b)가 틀린 것이고 (a)만 근거로 남는다** — 그것도 정보다 |

## 판정

| grid 결과 | 판정 |
|---|---|
| **1e-3 선택** | 현행 LR 확정. **P033 의 LR 리스크 해소**, 이 항목 종결 |
| **1e-3 초과** | 여유 존재. **단 60스텝으로 채택하지 않는다** — 짧은 런은 속도만 읽는다(CLAUDE.md 판정기준). **300M 실런 1개가 `p6d` 3.7045 를 0.024 초과로 이겨야** 채택 |
| **1e-3 미달** | 지금까지 과하게 높은 LR 로 학습해 온 것. 과거 json 의 `grad_max` 를 먼저 확인한 뒤 믿는다 |
| **accum 8 ≠ 16** | 배치 의존성 확정 → **P033 의 더 큰 배치는 자체 lrfind 가 필요**하다. 이 값을 그대로 못 쓴다 |

> **채택 절차를 못박는다.** lrfind 는 **후보를 좁히는 도구**이고 채택 근거가 아니다.
> 실제 갱신은 **300M 공정 풀 실런 1개(약 2.1h)** 로 확인한 뒤에만 한다.
> σ=0.012 이므로 **개선이 0.024 를 넘지 않으면 LR 을 바꾸지 않는다**(바꿀 이유가 없다).

## 비용

3회 × 약 18분(range 150스텝 + grid 5×60스텝, accum 16) ≈ **1시간**.
체크포인트를 쓰지 않으므로 `runs/ckpt/` 오염 없음. 정본 태그 무영향.

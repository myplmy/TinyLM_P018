## 1. 왜 — 논문의 절반이 우리에겐 이미 있다

### 1.1 논문이 한 일

FP8 로 내린 것은 **Linear 의 GEMM 3개**(Fprop·Dgrad·Wgrad)**뿐**이고,
**임베딩 · 출력 헤드 · 게이팅 · 정규화 · 어텐션 · master weight · gradient · optimizer state 는
전부 고정밀**이다(기술보고서 §3.3.1). 정확도는 네 장치로 지켰다 —
**활성 1×128 타일 / 가중치 128×128 블록 스케일**, **N_C=128 마다 CUDA Core FP32 누산 승격**,
**전 텐서 E4M3**, **온라인 amax**. 결과: BF16 대비 **상대 손실 오차 < 0.25%**(16B·230B, ~1T 토큰).

### 1.2 ★우리는 가중치 쪽 오차가 **원리적으로 0** 이다

어닐 완료 시 `wq[o,i] = sign[o,i] × α[o, g(i)]`, `sign ∈ {−1,0,+1}`, `g = micro_group = 128`.

- α 로 나누면 값이 **정확히 {−1, 0, +1}** 세 개
- **E4M3 는 이 셋을 정확히 표현**한다(가수 3비트가 남는다)
- → **스케일 입도가 α 입도와 같기만 하면 가중치 FP8 왕복 오차 = 0**

| | DeepSeek-V3 | **TinyLM** |
|---|---|---|
| 가중치 스케일 입도 | 128 × 128 블록 | **행 × 128**(더 미세) |
| 가중치 FP8 오차 | 작지만 0 아님 | ★**0**(입도가 맞을 때) |
| 누산 승격 간격 N_C | 128 | `micro_group` = **128**(일치) |
| 내부 차원 K | 4096+ | **768 / 2048**(작아서 **누산 오차에 유리**) |

### 1.3 ⚠️ 바로 그것이 장벽이다 — §5(T-MAC) U2 와 **같은 벽**

기술보고서 §3.3.2 원문:
*"per-group scaling factors along the **inner dimension** of GEMM ... **is not directly
supported in the standard FP8 GEMM**."* → DeepSeek 은 **CUTLASS 커널을 직접 만들었다**(DeepGEMM).

우리 α 도 **정확히 K축 그룹 스케일**이다. `torch._scaled_mm` 은 통상 per-tensor·per-row 만 받는다.
**저비트 추론 커널(P014B U2)에서도, FP8 학습 커널에서도 막히는 지점이 같다.**
→ 그래서 **한 번 재면 두 축에 다 쓰인다.**

## 2. 질문

| # | 질문 | 왜 중요한가 |
|---|---|---|
| **Q1** | `torch._scaled_mm` 이 **sm_89 에서 어떤 스케일 입도**까지 받는가 (per-tensor / rowwise / blockwise) | 이 답이 나머지를 전부 결정한다. **문서가 아니라 실제 호출로** 확인한다(결과 028 §11 이 `_weight_int8pack_mm` 에서 한 것과 같은 방식) |
| **Q2** | 우리 `_wq` 를 **E4M3 로 왕복**시키면 품질이 얼마나 나빠지는가 — **스케일 입도별로** | ★**이게 본 질문이다.** g128 = 0 이어야 하고(자기검증), per-row·per-tensor 가 얼마인지가 갈림길 |
| **Q3** | **활성** 쪽 E4M3 는 얼마나 아픈가 (per-tensor vs per-token vs 1×128 타일) | 가중치가 0 이어도 **활성이 오차원으로 남는다**. 논문이 미세 입도를 만든 이유가 이쪽이다 |
| **Q4** | Ada 의 FP8 누산 정밀도가 Hopper 의 FP22(가수 13비트)와 같은가 | 논문 §3.1.1 은 Hopper 값이다. **우리는 K 가 작아 유리할 것**으로 기대하지만 미확인 |
| **Q5** | AdamW 모멘트를 BF16 으로 내리면 VRAM 이 얼마나 도는가 / 품질이 변하는가 | 논문 §3.3.3. **속도가 아니라 메모리** = 우리 1순위 목표 |

## 4. 단계 설계

### 단계 0 — ✅ **완료 2026-08-07 = [결과 035](../test_result/035_20260807_P022B-단계0-per-tensor로도-FP8은-거의-공짜다.md)**

> **G0 전부 통과.** [A] sm_89 는 **per-tensor 만** 받는다(rowwise·blockwise 전부 FAIL, **P5 적중**).
> [B] g128 자기검증 **0.00000** ✅. **[D] 최선 Δbpb +0.0002 / 최악 +0.0005** = 게이트선 0.008 의 **1/40~1/16**.
> ★★**P2·P3 가 크게 빗나갔다** — per-tensor E4M3 왕복이 **+0.0005** 인데 결과 028 의 per-tensor
> **α 재추정**은 **+0.0862** 였다(**173배**). **두 오차원이 완전히 다르다** — E4M3 는 α 를 **보존**하고
> (가수에 실린다) α 재추정은 α 를 **버린다**. *같은 단어 'per-tensor' 가 다른 규약을 가리키고 있었다.*
> [C] 활성도 per-tensor 로 +0.0003 → **P4 도 빗나감**(활성이 더 아플 것이라 예측했다).
> ★★★**결론 전환: 커널이 필요 없다.** `torch._scaled_mm(per-tensor)` 만으로 성립하고
> 그건 결과 010 이 이미 **1.63~2.08×** 로 쟀다. **단계1 의 구현 난이도가 계획서 상정보다 훨씬 낮다.**
> ⚠️ 그래도 **P6(지금 구현 안 함)은 유지** — 이유가 품질이 아니라 **값어치**이기 때문이다(§6).

### 단계 0 (원설계) **학습 0 · GPU 수 분**

배치 `run_P022B_stage0_fp8_probe.bat` · 도구 `scripts/diag_fp8_precision.py`

**[A] `_scaled_mm` 능력 조사** — 우리 실제 형상 3종에 대해 per-tensor / rowwise / blockwise(1×128,128×128)
스케일을 **실제로 호출**하고 성공·실패·속도를 표로 찍는다. **이름만 보지 않는다**(결과 028 §11 방식).

**[B] 가중치 E4M3 왕복** — `freeze_quant()` 한 `_wq` 를 스케일 입도별로 E4M3 왕복시켜
**가중치 상대오차 + 공통 원문 bpb** 를 잰다. 입도 = `g128(자기검증) / g256 / per-row / per-tensor`.
`diag_alpha_group.py` 와 **같은 뼈대**를 쓴다(도구 신뢰가 이미 확보돼 있다).

**[C] 활성 E4M3 왕복** — forward hook 으로 `TLinear` 입력을 E4M3 왕복시키고 같은 bpb 를 잰다.
입도 = `per-tensor / per-token / 1x128 타일`(논문 규약).

**[D] 가중치+활성 동시** — 실제 FP8 GEMM 에 가장 가까운 조건.

**게이트 G0**:

| 조건 | 판정 |
|---|---|
| **[B] g128 행의 상대오차가 0 이 아니다** | 🚫 **도구 결함.** 다른 행을 읽지 않는다 |
| **[D] 최선 조합 Δbpb < 0.008**(= 우리 실무 분해능 bpb 환산) | ✅ **FP8 수치 게이트 통과** → 단계1 검토 |
| 0.008 ~ 0.02 | ⚠️ **재학습(QAT)이 필요**하다는 뜻 — 비용이 크게 오른다 |
| **> 0.02** | 🚫 **여기서 종결.** 커널을 만들어야만 성립하고, 그건 P014B 에서 접은 것과 같은 작업 |

⚠️ **이 단계는 속도를 판정하지 않는다.** 속도는 결과 010 이 이미 쟀다.

### 단계 1 — **FP8 GEMM 실 구현** ⏸ **G0 통과 + P022 §3 트리거 T1~T3 중 하나**

범위·설계는 **결과 010 §4 를 그대로 승계**하되 이 검토가 바꾼 것:

| 항목 | 결과 010 설계 | **P022B 개정** |
|---|---|---|
| 스케일링 | delayed scaling(amax 이력) 필요 | ★**온라인 amax 로 충분**(논문 §3.3.2 "Online Quantization") → **공수 감소** |
| 포맷 | Fprop E4M3 / 역전파 E5M2 관행 | ★**전 텐서 E4M3**(논문이 관행을 바꿨다) |
| 활성 gradient | 미규정 | ⚠️ **반드시 1×128 타일.** 블록 양자화하면 **발산**(논문 부록 B.2, 16B/300B 토큰 실측) |
| 대상 | MLP 3 GEMM | 동일. **어텐션 q/o 는 2단계** — 단 논문의 "attention operators 고정밀" 은 **SDPA·softmax** 지 q/o **투영이 아니다**(오독 주의) |
| 게이트 | 250스텝 ms/step −10% | 동일 |

### 단계 2 — **BF16 옵티마이저 상태**(논문 §3.3.3) ✅ **구현 완료 2026-08-07** · 배치 `run_P022B_stage2_optstate.bat`

**속도가 아니라 메모리 실험이다.** 논문은 AdamW 1·2차 모멘트를 BF16 으로 두고
**master weight·gradient 는 FP32 유지**해 *"관측 가능한 성능 저하 없음"* 을 1T 토큰 규모로 보고했다.

| 항목 | 값 |
|---|---|
| mC 학습 파라미터 | 약 **63.5M**(삼진 54.85M + 임베딩 8.59M + 기타) |
| 현재 AdamW 상태 | 2 × 4B × 63.5M = **약 508MB** |
| BF16 화 | **약 254MB 절감** |

#### 2.1 구현 — `tinylm/train/adamw_bf16.py` + `--opt-dtype`

| 모드 | 무엇 | 왜 있나 |
|---|---|---|
| **`fp32`**(기본) | 종전 `torch.optim.AdamW(fused=True)` | **비트 동일.** 켜지 않으면 아무것도 안 바뀐다 |
| **`fp32c`** | 우리 `AdamWLowPrec`, 상태 fp32 | ★**자기검증.** 구현 위험과 dtype 위험을 **분리**한다 |
| **`bf16`** | 우리 `AdamWLowPrec`, 상태 bf16 | 실험 조건 |

**바꾸는 것은 상태 저장 dtype 하나뿐이다.** master weight(`p`)·gradient(`p.grad`)·**산술 전부 fp32**.
매 스텝 fp32 로 올려 갱신하고 저장할 때만 내린다. 임시 텐서는 파라미터 하나 크기(≤12.6MB).

**수식 검산 완료**(numpy, 2289스텝 × 64파라미터): torch `_single_tensor_adamw` 와
**최대 절대차 1.1e-16 = 기계 엡실론.** 순서(weight decay → 모멘트 → addcdiv)도 동일.

#### 2.3 ★★실행 중 사용자가 확인해야 할 것 (사용자 요청 2026-08-07)

이 실험은 **조용히 발산할 수 있는 유일한 실험**이다. 다른 실험은 틀리면 죽거나 값이 이상하지만,
저정밀 옵티마이저는 **그럴듯한 손실 곡선을 그리면서 서서히 나빠질 수 있다.** 그래서 감시 항목을 둔다.

| 시점 | 볼 것 | 정상 | ⚠️ 즉시 중단 |
|---|---|---|---|
| **시작 직후** | `[opt] ★AdamWLowPrec state_dtype=bf16` 줄 | 있다 | **없으면 플래그가 안 걸린 것 → 이 런은 무가치.** Ctrl+C |
| 시작 직후 | 같은 줄의 `상태 2벌 예상 …MB` | 약 **254MB** | 508MB 근처면 dtype 이 안 내려갔다 |
| **step 0** | `ce` | **대조군 `mC_wsd` 와 같은 값**(같은 시드·같은 초기화) | 다르면 초기화가 다른 것 → 조건 불일치 |
| **step 0~100** | 인쇄 `\|g\|` | 0.3~2 대에서 요동 | **10 이상이 연속으로** 나오면 발산. 정본은 json 이지만 **실시간 조기 신호로는 인쇄값을 본다** |
| **매 100스텝 eval** | `val_loss` | 단조 감소, 대조군 곡선과 **나란히** | **val 이 2회 연속 상승**하면 중단하고 보고 |
| 매 100스텝 | `skip N` | **0** | 1 이상 = NaN 가드 발동 = 수치 문제 |
| 로그 말미 | `[vram] peak reserved` | 대조군보다 **약 0.25GB 낮다** | 같으면 절감이 안 일어난 것 |
| 로그 말미 | `ms/step` | 대조군 +2% 이내 | +10% 넘으면 파이썬 루프 대가가 예상 밖 |

> ★**중단해도 손해가 작다.** 단계2 배치는 **[1] tiny 게이트 → [2] 250스텝 → [3] 2289스텝** 순이라
> [1]·[2] 에서 이상이 보이면 3.5h 를 안 태운다. **[3] 을 시작하기 전에 [1]·[2] 를 눈으로 확인할 것.**

#### 2.4 단계 설계

| 단계 | 무엇 | 시간 | 게이트 |
|---|---|---|---|
| **2a** | tiny 30스텝 × 3(`fp32` / `fp32c` / `bf16`) | 수 분 | **S-a**: `fp32` vs `fp32c` 인쇄 4자리 일치. **안 맞으면 구현 버그 — 여기서 멈춘다** |
| **2b** | 250스텝 × 2(`fp32` / `bf16`), `mC` 조건 | 약 40분 | **S-b**: VRAM 차 ≈ 0.25GB · `skip 0` · `grad_max` < 3. ⚠️**val 은 안 읽는다** |
| **2c** | 2289스텝 × 1(`bf16`) + `paired_eval` vs `mC_wsd` | 약 3.5h | **S-c**: paired Δ < 0.024 |

⚠️ **2c 의 대조군 `mC_wsd` 는 재학습하지 않는다** — `--opt-dtype` 하나만 다르다.

#### 2.5 한계

- **결정론적 반올림**이다(stochastic rounding 아님). 반올림 편향이 **긴 런에서만** 쌓이므로
  **2289스텝 결과를 그대로 더 긴 예산에 외삽하지 않는다.** 논문 조건(1T 토큰)과 다르다.
- **`--resume` 은 권장하지 않는다.** `Optimizer.load_state_dict` 가 상태를 파라미터 dtype 으로
  캐스팅한다 — 오버라이드로 되돌리지만 조건이 흐려진다.
- 시드 1개. `paired_eval` 은 **두 체크포인트**를 말하지 아키텍처를 말하지 않는다.
- **`fused=True` 를 잃는다.** S4 가 맞으면 무시할 만하지만 **측정으로 확인한다.**

**★그리고 P042 단계1·2 결과를 먼저 본다** — 결과 033 이 타잉 VRAM **−35.3%**(7.82→5.06GB)를 실측했으므로
기준표 §5 의 "tied+KD 15.7GB" 자체가 낡았을 수 있다. **낡은 숫자 위에 절감을 설계하지 않는다.**
(단계2 자체는 P042 와 **독립**이므로 순서를 지킬 필요는 없다 — `--no-ckpt` 해석에만 필요하다.)

## 7. 한계

- **단계0 은 "왕복 오차" 를 잰다. 실제 FP8 GEMM 의 누산 오차는 못 잰다** —
  Ada Tensor Core 의 누산 가수 폭은 이 방법으로 안 보인다(Q4 는 단계1 이 아니면 답 못 함).
  ★**그래서 단계0 의 값은 하한이다**(실제는 더 나쁠 수 있다).
- **재학습하지 않는다.** g128 로 학습된 모델을 사후 왕복시키는 것이므로
  **QAT 로 적응시켰을 때의 값은 더 좋을 것**이다 — 결과 028 이 같은 성격의 상한/하한 관계를 갖는다.
- **bpb 는 SQuAD 영문 원문**이다(`common_bpb.py`). 한국어 성능은 안 본다.
- 단계2 의 254MB 는 **계산값**이다. 실측은 구현 후.
- 논문 수치(0.25%)는 **128블록 + 승격 커널 + 온라인 양자화가 전부 갖춰진** 조건이다.
  **하나라도 빼면 인용할 수 없다**(부록 B.2 가 실제 발산 반례).

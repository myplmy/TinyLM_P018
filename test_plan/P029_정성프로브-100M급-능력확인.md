# P029 — 정성 프로브: 100M급 모델이 "학습 텍스트를 유추"하는지 눈으로 확인 (소규모)

## 왜

지금까지 우리는 **val cross-entropy 하나로만** 모델을 판단해 왔다. 그건 아키텍처 A vs B 를
비교하는 데는 충분하지만, **"이 모델이 뭔가를 하기는 하는가"** 에는 답하지 못한다.
val 3.70 (ppl 40) 이 실제로 어떤 텍스트를 만들어내는지 **한 번도 본 적이 없다.**

`docs/methods/03_knowledge_quality.md` 의 "다운스트림 평가 도입" 항목이 💡(미도입) 상태인데,
정식 벤치마크는 비용이 크다. **그 전에 가장 싼 확인**을 한다.

## ★기대치를 먼저 못 박는다 (이걸 안 하면 실망하거나 과대평가한다)

| 항목 | 값 |
|---|---|
| 파라미터 | 132.5M(dense) / 63~73M(tied) — **삼진 양자화** |
| 학습 토큰 | **300M** |
| Chinchilla 권장 | 파라미터당 ~20토큰 → 132M 이면 **2.6B 토큰** |
| 실제 | 파라미터당 **~2.3 토큰** — 권장의 **1/9** |
| 학습 데이터 | 한국어 위키 50% + FineWeb-Edu(영문) 50% |

**즉 이 모델은 GPT-2(124M, 40B 토큰) 대비 토큰이 1/130 이다.**
심하게 undertrained 이며, 아래를 **기대하면 안 된다**:

- 사실 정확성(연도·인명·수치) — 거의 확실히 틀린다
- 문단 수준의 논리 전개
- 지시 따르기(instruction following) — **사전학습만 했고 SFT 는 없다**
- 질의응답 형식 — 학습 데이터에 Q&A 형식이 없다

**기대해도 되는 것**(= 이 실험이 확인하려는 것):

1. **형태론적 타당성** — 한국어 조사·어미가 그럴듯하게 붙는가(`~은/는`, `~했다`, `~이다`)
2. **문자체계 일관성** — 한글 프롬프트에 한글로, 영문 프롬프트에 영문으로 이어가는가
3. **도메인 관성** — 위키 문체 프롬프트에 위키 문체로 이어가는가
4. **국소 문법** — 한 문장 안의 어순·품사 배치가 무너지지 않는가
5. **반복 붕괴 없음** — 같은 토큰/구절을 무한 반복하지 않는가

> **판정은 정성적이다.** 이 실험은 순위를 매기거나 아키텍처를 고르는 데 쓰지 않는다.
> 그건 val_loss 와 REVIEW1 이 한다. **여기서 얻는 것은 "숫자 뒤에 뭐가 있는지"에 대한 감각**이다.

## 프롬프트 5개 (선정 근거 포함)

전부 **학습 분포 안**에서 골랐다 — 학습 데이터가 위키 + 교육 웹텍스트이므로 그 문체로 시작한다.
"무엇을 물어보는가"가 아니라 **"어떤 텍스트를 이어쓰게 하는가"** 로 설계했다(사전학습 모델의 실제 능력).

| # | 프롬프트 | 무엇을 보는가 |
|---|---|---|
| 1 | `대한민국의 수도 서울은` | **한국어 위키 문체 + 최빈 도메인.** 가장 쉬운 조건. 여기서도 무너지면 근본 문제 |
| 2 | `조선 시대의 과학 기술은 세종대왕 때` | **긴 한국어 문맥 유지.** 조사·어미 연쇄와 시대/주제 관성 |
| 3 | `물이 끓는 온도는 섭씨` | **국소 사실 + 숫자 문맥.** 100 이 나오면 좋고, 안 나와도 **숫자 자리에 숫자**가 오는지가 관전 포인트 |
| 4 | `The Industrial Revolution began in` | **영문 전환.** 절반이 영문 데이터인데 문자체계를 섞지 않는지 |
| 5 | `인공지능 기술의 발전은 사회에` | **추상 개념 + 열린 문장.** 반복 붕괴가 가장 잘 드러나는 조건 |

## 실행 설계

- **모델**: REVIEW1 완료분 중 하나. 기본은 **`mA_g4s34_k4`**(g4+s34+k4, 11.7MB) —
  결과 012 에서 dense 와 **구분 불가**(0.16~0.40σ)로 나온 현재 최선 후보다.
  비교용으로 **`p6d`(dense, 30.9MB)** 도 같은 프롬프트로 돌려 **압축의 정성적 대가**를 본다.
- **샘플링**: 각 프롬프트를 **온도 2종**(0.7 = 보수적, 1.0 = 다양) × `--top-k 40`, `--max-new 100`.
  온도 하나만 보면 "반복 붕괴"와 "무작위 붕괴"를 구분하지 못한다.
- **배치**: `run_P029_probe.bat`. GPU 를 쓰지만 **추론만** — 프롬프트당 수 초.

> **주의**: `generate` 는 KV 캐시 없이 매 스텝 전체 시퀀스를 재계산한다(정성 확인용).
> 속도를 재는 데 쓰면 안 된다.

## 판정

체크리스트를 **눈으로** 채운다. 점수화하지 않는다(표본 5개로 점수는 무의미).

| 확인 | mA | p6d(dense) |
|---|---|---|
| 한글 프롬프트 → 한글 유지 | ☐ | ☐ |
| 영문 프롬프트 → 영문 유지 | ☐ | ☐ |
| 조사·어미가 그럴듯함 | ☐ | ☐ |
| 위키 문체 관성 | ☐ | ☐ |
| 무한 반복 없음(t=0.7) | ☐ | ☐ |
| 문자 깨짐·제어문자 없음 | ☐ | ☐ |

- **전부 ☐ 이면** → 파이프라인/토크나이저/체크포인트 로딩에 문제가 있을 수 있다(디버깅 대상).
- **1~4 는 되고 사실은 틀린다** → **정상**. undertrained 100M 급의 예상 거동.
- **mA 와 p6d 가 눈에 띄게 다르다** → 압축의 정성적 대가를 처음 관측한 것. 기록할 가치가 있다.
  단 **표본 5개 × 2온도라 통계가 아니다.** "인상"으로만 적는다.

## 비용

추론만, 총 20~40회 생성 × 수 초 = **수 분**. 학습 없음. `runs/` 오염 없음(생성은 파일을 안 쓴다).

## 실행 이력 / 수정

**2026-07-30 1차 실행 실패** — `AttributeError: 'TMTConfig' object has no attribute 'seq_len'`.

- **직접 원인**: `probe_prompts.py` 초판이 `cfg.seq_len` 을 참조. 실제 필드는 **`max_seq_len`**.
- **근본 원인**: **이미 있는 샘플링 루프를 복제**했다. `infer/generate.py` 에 검증된 구현이
  있었는데 스크립트 안에 다시 짰고, 그 과정에서 필드명을 잘못 적고 **autocast(bf16)도 누락**했다.
- **수정**: `generate.py` 에 **`sample(model, cfg, tok, prompt, ...)`** 을 분리해
  **샘플링 단일 소스**로 만들고, `generate()` 와 `probe_prompts.py` 가 둘 다 이걸 호출한다.
  프롬프트별 `try/except` 도 추가해 한 프롬프트 실패가 나머지를 막지 않게 했다.
- **재발 방지**: `scripts/check_attrs.py` 신설 — `cfg.<attr>` 을 `TMTConfig` 선언 필드와
  **AST 로 대조**한다(torch·GPU 불필요, 수 초). `run_smoke.bat` 선두에 편입.
  오타를 되돌려 넣어 검출·오타 후보 제시(`max_seq_len`)까지 확인했다.
- **교훈**: 이 저장소의 스모크 철학("긴 런 전에 값싸게 계약 검증")을 **새 스크립트 자신에는
  적용하지 않았다.** 샌드박스에 torch 가 없어 `--list` 경로만 실행해봤고, 그 경로는 `cfg` 를
  건드리지 않는다. **실행 못 하는 코드일수록 정적 검사가 필요하다.**

## 한계 (반드시 함께 기록)

- **표본 5개는 통계가 아니다.** 여기서 나온 인상으로 아키텍처를 고르지 않는다.
- **샘플링은 확률적이다.** 같은 프롬프트도 매번 다르게 나온다 — 재현하려면 여러 번 돌린다.
- **정성 평가는 평가자 편향에 노출된다.** 좋게 보려 하면 좋아 보인다.
- 이 실험은 **다운스트림 벤치마크의 대체가 아니다.** 정식 평가는 별건(03 원장 참조).

# P014C — 우리 구조에 맞는 **역양자화 제거** 경로 (α 그룹 규약부터 정한다)

> **신설 2026-08-07.** [P014B](P014B_LUT커널-실사-및-속도게이트.md) 단계0 이
> **U2 부정**(외부 커널은 스케일이 텐서당 1개)을 확정했고,
> [U5 빌드](../docs/20260807_T-MAC와-bitnetcpp-실사-우리구조적용가능성분석.md#16) 는
> **저장소 구조 문제로 중단 권고**가 됐다.
> **그래서 "외부 구현을 빌려온다" 가 아니라 "우리 규약으로 역양자화를 없앤다" 로 방향을 바꾼다.**
>
> **근거**: 분석보고서 §16·§17 · 결과 014 §11.4 · 결과 016 §12·§15

---

## 1. 왜 — 병목은 하나로 좁혀져 있다

| 관측 | 값 | 출처 |
|---|---|---|
| int8 저장의 CPU 속도 대가 | **−62~67%** | 결과 016 §10·§12 |
| 그 대가의 정체 | **분리된 unpack 이 층당 +2.1~2.2ms** | 결과 014 §11.4 |
| 언팩을 유니크 모듈당으로 묶으면 | **`mC` +42.7%** | 결과 016 §15 |
| **언팩 1회당 실측 비용** | **1.54~1.60 ms**(두 모델 4% 안) | 결과 016 §15.3 |
| CUDA 에서는 | **−12~15%**(1/5) | 결과 016 §12.3 |

**즉 CPU 배포의 남은 최대 손실은 `_wq_from_i8()` 의 fp32 물질화 하나다.**
언팩 캐시(P034 3C)가 **횟수를 줄였고**, 이 계획은 **아예 없애는 것**을 노린다.

### 1.1 없애는 방법은 융합 mpGEMM 뿐이고, 그건 스케일 규약을 요구한다

| 규약 | α 개수(mC) | 융합 연산 가용성 |
|---|---|---|
| **g128**(우리, `micro_group=128`) | 약 **428,000** | ❓ 우리가 커널을 짜야 한다 |
| **per-row** | O 개(층당 768~2048) | ★**PyTorch 내장 후보 있음**(§4 확인 선결) |
| **per-tensor** | **1** | bitnet.cpp I2_S·TL — 단 **빌드 불가**(§16) |

> **★그래서 이 계획의 첫 질문은 커널 성능이 아니라 "거친 α 를 감당할 수 있는가" 다.**
> 그리고 그것은 **학습 없이 GPU 수 분에** 측정된다. 그게 단계0 이다.

### 1.2 사용자 하드웨어가 조건을 좋게 만든다

| 항목 | 값 | 함의 |
|---|---|---|
| **AMD Ryzen 7 9700X**(Zen 5) | 8C/16T | **AVX-512 완전 지원**(512비트 데이터패스) |
| **L3 32.0 MB** | | **MLP 하나 fp32 = 18.0 MiB → 들어간다.** 결과 014 §11 의 캐시 지역성과 정합 |
| L2 8.0 MB(코어당 1MB) | | **int8 MLP 하나 = 4.5MB → L2 에도 거의 들어간다** |

## 2. 질문

| # | 질문 |
|---|---|
| **Q1** | α 를 **per-row** 로 거칠게 하면 품질이 얼마나 나빠지는가 |
| **Q2** | per-tensor(= bitnet.cpp 규약)는 얼마나 나빠지는가 |
| **Q3** | PyTorch 에 **per-row 스케일 융합 int8 matmul** 이 실제로 있는가 |
| **Q4** | 있다면 우리 크기(768/2048, 배치 1)에서 **실제로 빨라지는가** |
| Q5 | 안 되면 **g128 커널을 우리가 만들 값어치가 있는가** |

## 3. ★예측

| # | 예측 | 근거 | 틀리면 |
|---|---|---|---|
| **P1** | **per-row Δbpb 는 0.008~0.05** — 분해능을 **넘지만 재앙은 아니다** | 합성 α 로 상대오차 11%(I=256). 실제 I=768/2048 은 그룹이 6~16개라 **더 크다**. 다만 삼진은 값이 세 개뿐이라 α 오차가 부호를 안 바꾼다 | 0.008 미만이면 **커널 불필요 = 최선의 결말** |
| **P2** | **per-tensor 는 크게 넘는다**(0.05 이상) | 합성 상대오차 36%. 층마다 α 분포가 다른데 하나로 뭉갠다 | 안 넘으면 **bitnet.cpp 를 그대로 쓸 수 있다**(단 빌드 문제는 별개) |
| P3 | g256 은 g128 과 **거의 같다**(Δ < 0.008) | 그룹을 2배로만 키운다 | |
| **P4** | Q3 는 **있다**(`_weight_int8pack_mm` 계열) | gpt-fast·torchao 계열이 쓰는 연산 | 없으면 `torch.compile` 융합·`torchao`·자체 커널 순으로 |
| P5 | **재학습하면 대가가 줄어든다** | 거친 α 에 적응할 자유도가 있다 | 이 계획은 재학습을 **안 하므로** 단계0 표는 **비관적 상한**이다 |

> **★P1 이 이 계획의 갈림길이다.** 그리고 **어느 쪽이든 결과다** —
> 통과하면 커널이 필요 없고, 초과하면 **왜 외부 구현을 못 쓰는지의 정량 근거**가 생긴다.

## 4. 단계 설계

### ✅ 단계 0 — **α 그룹 규약 스윕** (구현 완료) · GPU **수 분** · 학습 0

`scripts/diag_alpha_group.py`(2026-08-07 신설). 배치 `run_P014C_stage0_alpha_group.bat`.

- 배포되는 `_wq`(= sign × α_g)의 **부호를 보존**하고 α 만 `{g128, g256, g512, per-row, per-tensor}`
  로 다시 묶는다. **L2 최적 재추정 `A = mean(|w|)`**(비영 위치) — **변환기가 실제로 할 일과 같다**
- 각 규약에서 **SQuAD 공통 원문 bpb** 를 실제로 잰다
- **로직 검산 완료**: g128 이 **상대오차 0.000000**(원래 α 복원) + 0 위치 보존 ✅

**★판정 분기**

| per-row Δbpb | 다음 |
|---|---|
| **< 0.008** | **단계1(융합 연산 확인) → 단계2(속도)**. 커널 불필요 |
| 0.008~0.05 | **단계1 은 하되, 재학습 대가 측정(단계3)이 선결**이 된다 |
| **> 0.05** | **단계4(g128 커널)로 직행.** 외부 규약은 포기 |

### ✅ 단계 0 결과 (2026-08-07) — **per-row 통과. 그리고 메모리 레버가 하나 나왔다**

전문 = [결과 028](../test_result/028_20260807_P014C-단계0-per-row는-공짜고-per-tensor는-못쓴다.md).

| | per-row Δbpb | per-tensor Δbpb | per-tensor Δnats |
|---|---:|---:|---:|
| `p6d` | +0.0059 | +0.0465 | +0.1407 |
| `mC_g8_k4` | +0.0050 | +0.0694 | +0.2101 |
| `mA_g4s34_k4` | +0.0050 | +0.0707 | +0.2140 |
| **`mC_wsd`** | **+0.0063** | **+0.0862** | **+0.2610 (21.7σ)** |

- **G0 통과** — per-row 최대 0.0063 < 0.008. **여유 21%**(안전하지는 않다)
- **per-tensor = bitnet.cpp 규약**이므로 **P014B 중단 권고에 품질 근거가 붙었다**:
  빌드가 됐어도 **0.26 nats** 를 잃는다 = 우리가 아키텍처로 벌어 온 것과 같은 자릿수
- **g256 은 완전 공짜**(+0.0010~0.0015 = 분해능 1/5) → `micro_group` 은 한 번도
  스윕하지 않은 축이다
- ★**부수 소득**: α 개수가 줄면 **스케일 비트도 준다** → **단계1B 신설**
- ⚠️ 결함 2건(g512 행 전부 스킵 / `requires_grad` 경고) **수정 완료, 재실행 불필요**

### 단계 1 — **융합 연산 확인** ⏸ **← 지금 여기** · GPU 0 · 1분

```
python -c "import torch; print(torch.__version__); print(hasattr(torch, '_weight_int8pack_mm'))"
```

`True` 면 시그니처·디바이스 지원(CPU/CUDA)·shape 제약을 확인한다.
`False` 면 대안 순서: `torch.compile` 융합 → `torchao` → 자체 커널.

⚠️ **per-row 가 통과해도 연산이 없으면 소용없다.** 그래서 단계1 이 별도 게이트다.

### ★단계 1B — **α 규약을 메모리 레버로 계상한다** (신설 2026-08-07) · GPU 0 · 구현 소

단계0 이 **목적 밖의 것을 찾았다.** α 개수가 줄면 **α 를 저장하는 비트도 준다**.
규약은 **코드에서 확인했다**(`transformer.py:454~466`): `SCALE_BITS = 16.0`(**fp16**),
`b_t = log2(3) + 16/micro_group` → g128 에서 정확히 **1.7100** ✅.

| 규약 | 스케일 bpw | 삼진 bpw | Δ | mC packed |
|---|---:|---:|---:|---:|
| **g128**(현재) | 0.1250 | 1.7100 | — | 13.05MB (2.08×) |
| g256 | 0.0625 | 1.6475 | **−3.7%** | ⚙ 12.64MB |
| **per-row** | 0.0186(가중평균) | 1.6036 | **−6.2%** | ⚙ **12.25MB (2.21×)** |

> **★그래서 per-row 는 "커널을 안 짜도 되는 조건" 이면서 동시에 "저장 −6.1% 레버" 다.**
> 대가는 **+0.005~0.006 bpb = 분해능 미만**. 구현은 α 재추정 한 번(학습 0).

⚠️ **자기 정정** — 결과 028 §4 를 처음 **−13%** 로 썼다. α 를 fp32 로 가정한 탓이고
실제는 fp16 이라 **이득이 절반**이다. 정본 1.7100 을 식으로 재현해 보니 안 맞아서 잡혔다
(**함정 7**). **규약 값은 코드에서 읽는다.**

⚠️ **저장과 상주를 섞지 말 것**(함정 1). int8 경로에서 α 는 `tern × 4/micro_group` 바이트
= mC 에서 **1.71MB / 86.94MB = 2.0%** 뿐 → **per-row 는 상주를 −1.9% 밖에 못 줄인다.**
**저장 −6.1% / 상주 −1.9%** 로 나눠 인용한다.

**할 일**: ⓐ ✅ 완료(위 표) ⓑ `micro_group` 을 프리셋/CLI 로 스윕 가능하게
(현재 `TMTConfig.micro_group=128` 고정. `assert dim % micro_group == 0` → 768 % 256 = 0 ✅)
ⓒ **g256 은 대가가 분해능의 1/5 이니 단계2 와 무관하게 독립 채택 검토** — 단
**재학습이 필요하다**(학습 중 α 그룹이 g256 이어야 STE 가 그 규약에 적응한다).
즉 ⓒ 는 "무료" 가 아니라 **3.5h 짜리**다.

**게이트 G1B**: ✅ 통과 — 스케일 항이 `_bpw()` 에 실제로 들어 있다(`16/micro_group`).

### 단계 2 — **속도 게이트** ⏸ 단계1 통과 후 · GPU 0 · 수 분

`TLinear.forward` 에 **per-row α + 융합 matmul** 경로를 플래그로 추가(기본 off)하고
**같은 런에서 세 조건**을 잰다:

| 조건 | 값 |
|---|---|
| int8, 캐시 off(기준선) | `mC` 13.36 tok/s (결과 016 §15) |
| int8 + 언팩 캐시 | `mC` **19.07**(1.427×) |
| **per-row 융합** | ? |

**게이트 G2**: **언팩 캐시(19.07)보다 나아야** 한다. 못 하면 **이 경로를 접고** 언팩 캐시로 만족한다.
(외부 의존이 없으므로 P014B 의 1.3× 기준보다 관대하게 봐도 되지만, **이미 있는 것보다 나쁘면 의미가 없다**)

### 단계 3 — **재학습 대가 측정** ⏸ 조건부(단계0 이 0.008~0.05 일 때) · GPU **약 3.5h**

`micro_group` 을 per-row(= `in_f`)로 두고 `mC` 를 **처음부터 학습**해 P5 를 검정한다.
⚠️ `micro_group` 이 `in_f` 와 같으면 `__post_init__` 의 `dim % micro_group == 0` 을 만족한다
(768%768, 2048%2048). **단 층마다 `in_f` 가 달라 프리셋 필드 하나로는 표현 안 된다** →
**`micro_group=0` = "per-row" 센티널**을 추가하는 구현이 선결(소).

### 단계 4 — **g128 커널** ⏸ 단계0 이 > 0.05 일 때 · 큼

P014 본체가 소유한다. **T-MAC/bitnet.cpp 의 설계를 참고**하되 **우리 규약을 유지**한다:

| 참고할 것 | 어디서 | 우리에게 왜 |
|---|---|---|
| **LUT 원리**(4비트 묶음 16패턴 사전계산 → 조회+덧셈) | T-MAC §3 | 곱셈 제거. 우리 삼진에 그대로 성립 |
| **표를 레지스터에 상주**(축 재정렬·타일링) | T-MAC | **L3 32MB·AVX-512** 환경에 유리 |
| **mirror consolidation**(`표[¬p] = −표[p]`) | T-MAC | 표 크기 절반 |
| `gemm-config.h` 의 **블록 파라미터화** | BitNet | shape 무관 GEMM 의 형태 |
| **`ggml_vec_dot_i2_i8_s` 의 int8 내적 구조** | BitNet mad | AVX2/512 인트린식 참고 |
| 🚫 **하드코딩 shape**(`kernel_config.ini`) | — | 우리는 768/2048. **codegen 대신 파라미터화** |
| 🚫 **텐서당 스케일** | — | 우리는 g128 **유지가 목적** |

**구현 형태**: `tinylm/model/ternary_kernel.py` 가 이미 자리를 잡고 있다(P014 레퍼런스).
CPU 는 **C++ extension 또는 numpy/torch 벡터화**, GPU 는 **Triton**.
⚠️ **`--ternary-kernel` 은 `--compile` 과 병용 금지**(기존 규약, `trainer.py` 가 막는다).

## 7. 한계

- 단계0 은 **영문 전용**(SQuAD)이다. 한국어 쪽 α 민감도는 안 나온다.
- 단계0 은 **재학습하지 않는다** → **비관적 상한**이다(P5).
- 단계2 는 **배치 1 디코드**만 본다. prefill·서버 처리량은 다른 주제다.
- 단계4 를 하게 되면 **우리가 커널을 유지보수**한다. 그게 실질 비용의 대부분이다.
- `mA`(sparse34)는 이 계획 전체에서 **다루지 않는다** — 5비트/4가중치 코드북은
  별도 커널이 필요하고, 결과 021·024·027 이 이미 `mC` 를 지지한다.

## 1. 왜 — 이건 개선이 아니라 **감사(audit)** 다

우리 이력에서 **가장 큰 단일 품질 이득**은 아키텍처가 아니라 데이터에서 나왔다:

| 조치 | 이득 | 출처 |
|---|---:|---|
| **스팸 필터 후 재학습**(`ko-edu-en`) | **−0.296 nats (24.7σ)** | 결과 011 §2 |
| KD | −0.15 급 | 결과 021 |
| 타잉 격차 회복 | +0.15~0.17 를 닫음 | 결과 002·007 |
| 실무 분해능 | 0.024 | 결과 012 |

그리고 그 실험은 부수적으로 이렇게 말했다: **`ko-edu-en` 격차의 63%가 스팸이었다.**

**그런데 우리 표준 코퍼스는 `ko-en` 이고, `ko-en` 의 스팸률은 한 번도 측정하지 않았다.**

결과 018 이 `ko-en` 을 "건강한 대조군(줄바꿈 0.3~2.3% / 줄 고유율 94.8~99.6%)" 으로
쓴 것은 **표본 몇 개**를 본 것이다. **전량 스캔이 아니다.** 즉 지금 우리가 가진 것은
*"표본에서 안 보였다"* 이고 *"없다"* 가 아니다.

### 1.1 왜 REVIEW2 **앞**이어야 하는가

REVIEW1·REVIEW2 의 모든 서열(mA vs mC vs p6d, KD 유무, 타잉 g)은 **`ko-en` 300M 위**에서
매겨졌다. 만약 `ko-en` 에 스팸이 있으면:

- 서열이 **틀렸다는 뜻은 아니다** — 모든 런이 같은 오염을 공유하므로 상대 비교는 살아남는다
- 그러나 **모든 절대 수치가 나쁜 기준선 위**에 있고, `−0.3 nats` 급 개선이 무료로 대기 중이다
- 그리고 그건 **리뷰를 고치는 문제가 아니라 기준선을 다시 만드는 문제**다(전 런 재학습)

> **★그래서 REVIEW2 를 쓰기 **전에** 알아야 한다.** 리뷰를 쓴 다음에 이걸 발견하면
> 리뷰 자체를 다시 써야 한다. **측정은 GPU 0 이고 몇십 분이다.** 순서가 명백하다.

### 1.2 이 계획이 하는 것과 하지 않는 것

| | |
|---|---|
| **한다** | **측정만.** `ko-en` 에서 필터가 버릴 문서를 세고, 서명 근접 사례의 분포를 본다 |
| **안 한다** | 재학습. 필터 채택. 기준선 교체 — **전부 단계1 이후이고 별도 판단**이다 |

**이유**: 필터를 켠 재학습은 **기준선 전체 재작성**(수십 GPU시간)이다.
결과 026 이 보여 준 것처럼 **값싼 게이트를 앞에 세우는 것이 이 저장소의 방식**이다.

## 3. ★예측 — 정직하게

| # | 예측 | 근거 | 틀리면 |
|---|---|---|---|
| **P1** | **`ko-en` 스팸률은 `ko-edu-en` 보다 훨씬 낮다** | `ko-en` 은 위키(편집된 문서) + fineweb-edu(교육 필터 통과). `ko-edu-en` 의 오염원은 `korean-webtext-edu` 의 웹 크롤 | 위키/fineweb 에도 통짜 대형 문서가 있다는 뜻 — 그건 새 사실이다 |
| **P2** | **그러나 0 은 아닐 것이다** | fineweb-edu `sample-10BT` 는 10B 토큰 규모 웹 크롤이고, 교육 점수 필터는 **내용 품질**을 보지 스팸 구조를 보지 않는다 | 0 이면 **표준 코퍼스가 안전하다는 첫 확인** = 좋은 결과다 |
| **P3** | **문자 비중은 0.1% 미만일 것이다** | 대형 문서 자체가 희귀하다 | 넘으면 즉시 단계1(재학습) |
| **P4** | ⚠️ **비중이 작아도 손실 기여는 클 수 있다** | 결과 023 §8: 스팸은 토큰의 소수인데 **val 손실의 53%** 였다 | — **이건 예측이 아니라 해석 규칙**이다. 게이트를 "비중" 이 아니라 **"존재"** 로 잡는 근거 |
| **P5** | **대형 문서의 다수는 `nl_frac` 조건은 통과하지만 `uniq` 는 아닐 것** | 위키 대형 문서는 목록·표가 많아 줄이 반복된다 | 반대면 서명의 두 조건 중 하나가 `ko-en` 에서 무의미하다는 뜻 |

> **★P2 와 P3 는 서로 반대 방향을 짚는다** — "0 은 아니지만 작다". 이렇게 적어 두면
> 어느 쪽으로 나와도 **한쪽 예측은 틀린 것**이 되고, 그게 "예상대로" 로 뭉개지는 것을 막는다.

## 4. 단계 설계

### 단계 0 — **스팸률 측정** ⏸ · **GPU 0** · 스트리밍 20~60분 · 배치 `run_P047_stage0_spam_rate.bat`

`scripts/diag_spam_rate.py`(2026-08-07 신설).

- **`prepare.spam_signature()` 를 import 해서 호출한다** — 베끼지 않는다(함정 14).
  그래서 세는 것이 정확히 **`--doc-filter` 가 버릴 문서**임이 보장된다
- **`prepare._stream()` 을 그대로 쓴다** — `rng` seed 0 고정이라 **`prepare` 와 같은 순서**를
  훑는다. 즉 여기서 센 집합은 실제 캐시에 들어간 집합과 (예산 안에서) 같다
- **토큰화하지 않는다.** 서명은 문자 수·줄바꿈·줄 고유율만 보므로 토크나이저가 불필요
  → `prepare` 의 12분 토큰화 없이 순수 스트리밍 속도
- **양성 대조군을 같은 배치에 넣는다** — `ko-edu-en` 도 400MB 훑는다.
  **거기서 스팸이 검출되지 않으면 도구가 고장난 것**이다(함정 17: 대조군 없는 측정 금지)
- 중간 보고를 200MB마다 찍고 `Ctrl+C` 를 받아도 집계를 인쇄한다 → **비율이 수렴하면 끊어도 된다**

**산출**
1. 스팸 문서 수·문자 비중, **95% 상한**(0건일 때 "최대 이만큼" 으로 바꿔 준다)
2. **소스별** 귀속 (위키 vs fineweb-edu)
3. **대형 문서(≥50,000자) 전량 프로파일** — `nl_frac`·`uniq` 와 서명 판정.
   조건 **하나만** 맞는 문서가 몰려 있으면 Q3 의 답이 "서명이 못 본다" 쪽이다

**게이트 G0**

| 관측 | 판정 |
|---|---|
| **스팸 0건 + 대형 문서 존재 + 양성 대조군 검출** | ✅ **`ko-en` 은 깨끗하다. P047 종결.** 기준선이 안전하다는 **첫 확인**. `--doc-filter` 는 `ko-edu-en` 전용 도구로 남는다 |
| **스팸 문자 ≥ 0.01%** 또는 문서 ≥ 10건 | ⚠️ **단계1 로 간다.** 그리고 그것은 기준선 재작성이다 |
| 스팸 0 **인데 대형 문서도 0** | ⚠️ **판정 불가.** 서명이 발화할 대상이 없었다 → `--min-chars 10000` 으로 재측정 |
| **양성 대조군에서 검출 안 됨** | 🚫 **도구 고장.** 다른 값은 읽지 않는다 |

### 단계 1 — **손실 기여 측정** ⏸ 조건부(G0 이 양성) · GPU 0 · 수 분

**스팸이 있다고 바로 재학습하지 않는다.** 먼저 **그것이 손실을 얼마나 먹는지** 본다.
`scripts/diag_val_docs.py` 가 이미 하는 일이다(결과 018·023 §8 이 이 경로로 나왔다).

- `ko-en` val 의 문서별 손실 → 상위 기여 문서가 **스팸 서명과 겹치는가**
- 결과 023 §8 의 지표를 그대로 쓴다: **상위10 제외 시 손실 변화의 부호**
  (`ko-edu-en` 은 −1.5245, 필터 후 +0.0144 = 건강. `ko-en` 은 **+0.0197 = 이미 건강**)

> ★**여기서 이미 답이 있을 수 있다.** 결과 023 §8 이 `ko-en` 의 상위10 제외를
> **+0.0197(건강)** 으로 기록했다. 그게 스팸이 없다는 **간접 증거**이고,
> 단계0 은 그걸 **직접 증거로 바꾸는 것**이다. 두 결과가 어긋나면 그게 신호다.

### 단계 2 — **필터 재학습** ⏸ 조건부(단계1 이 양성) · GPU **약 3.5h** + 캐시 생성

`--doc-filter` 로 `ko-en` 캐시를 새로 만들고(**별도 디렉터리 `ko-en_600M_filtered`,
기존 캐시 무변**) `mC_wsd` 를 재학습해 **공통 원문 bpb** 로 판정.

- **태그 `mC_wsdf`** — 정본 오염 금지
- **판정은 `common_bpb.py`** 로만. `val_loss` 는 필터가 스트림을 밀어 **다른 시험지**가 된다(L5, 함정 19)
- 통과하면 **표준조건 개정**이고 그건 REVIEW2 의 전제를 바꾼다

## 7. 한계

- 서명은 **`ko-edu-en` 의 스팸을 보고 만든 것**이다. 다른 형태의 오염(반복 boilerplate,
  기계 번역, 코드 덤프)은 **이 진단이 못 본다.** 대형 문서 프로파일이 사각지대를 좁히는 장치이지
  없애는 장치가 아니다

- 예산을 다 못 채우면 비율은 유효하나 **고갈 지점(약 280.6M 토큰) 이후 믹스가 다르다**(L4)

  그래서 판정을 **공통 원문 bpb** 로만 한다

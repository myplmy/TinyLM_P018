## 2. ★★교락 발견 — `--arch dense` 는 **두 가지**를 끈다

`dense_baseline(cfg)` = `dataclasses.replace(cfg, tie_mlp=False, cla_group=1)`.
**타잉만 끄는 게 아니라 CLA 도 함께 끈다.**

그래서 이 A/B 는 *"타잉 유무"* 가 아니라 *"타잉+CLA2 유무"* 다.

| 증거 | 값 |
|---|---|
| KV 소유 층 | dense **20/20** vs g8 **10/20** |
| KV 캐시 | 15.0 vs 7.5 KB/token |

### 2.1 ⚠️ 그리고 배치가 세운 게이트 자체가 틀렸다

배치 헤더는 이렇게 적었다:

> *"the token-per-FLOPs line from each report() header. **It should read 0.248 GFLOP for BOTH — that is the point.**"*

**두 런 다 0.248 로 나왔다. 그런데 그건 실제 연산이 같다는 뜻이 아니다.**
`report()` 의 FLOPs 식은

```python
per_l = (dim*dim*2 + kv_dim*dim*2) + 3*dim*ffn_dim
flops = 2 * n_layers * per_l
```

로 **모든 층이 k/v 를 갖는다고 가정**한다 — **`cla_group` 이 식에 없다.**
즉 **CLA 를 켜도 `report()` FLOPs 는 안 변한다.** 같은 값이 나온 것은
"연산이 같다" 가 아니라 **"이 지표가 CLA 를 못 본다"** 는 뜻이다.

> **★함정 4 의 계열**(*"인쇄값 ≠ 정본"*)이고 이번엔 **내가 그 인쇄값으로 게이트를 세웠다.**
> `mlp_group` 이 FLOPs 식에 없다는 것은 결과 014 §11.3 에서 이미 확인했는데
> **`cla_group` 도 없다는 것은 확인하지 않았다.**

### 2.2 CLA 몫을 빼면 얼마인가 (⚙추정)

층당 MAC:

```
q+o :  2 × 768 × 768   = 1,179,648
k+v :  2 × 768 × 192   =   294,912   ← CLA2 가 절반을 없앤다
MLP :  3 × 768 × 2048  = 4,718,592
합계                    = 6,193,152
```

k/v 비중 = 294,912 / 6,193,152 = **4.762%** → CLA2 가 없애는 몫 = **2.381%**.

| | 값 |
|---|---:|
| 관측 격차 | **−5.53%** |
| CLA2 몫(⚙, MAC 비례 가정) | **−2.38%p** |
| **타잉 단독(⚙추정)** | **약 −3.15%** |

⚠️ **"MAC 비례" 가정이 들어갔다.** k/v 투영은 작은 GEMM 이라 벽시계 비중이 MAC 비중과
다를 수 있다. **±1%p 정도의 불확실성으로 읽을 것.**

## 3. 판정 — 배치가 미리 적어 둔 세 갈래 중

| 갈래 | 조건 | 결과 |
|---|---|---|
| 2% 미만 | 기준표 §2.1 이 노이즈였다 | 🚫 아니다 |
| **5~10%, g 방향** | **진짜다. 원인은 캐시 지역성** | ✅ **관측 −5.53% 는 여기** |
| tied 가 느림 | 공유 텐서 누적이 추가 작업 | 🚫 아니다 |

**단 CLA 를 빼면 −3.15% 로 "5~10%" 밖으로 나간다** — 배치가 그 대역을 안 만들어 뒀다.
**정직한 판정**:

> **타잉은 학습시간을 번다. 다만 기준표 §2.1 의 −7.8% 보다 작고,
> 그 중 절반 가까이는 CLA 몫이다.**
> **기준표 §2.1 을 −7.8% → "약 −5.5%(타잉+CLA2), 타잉 단독 ⚙−3.1%" 로 정정한다.**

### 3.1 원인 — AdamW 는 아니다

결과 014 §11.3 이 확인한 대로 **타잉은 컴퓨트를 안 줄인다**(층당 FLOPs 동일, 20층 전부 통과).
줄어드는 것은 **AdamW 스텝(스텝 시간의 0.13%)과 옵티마이저 상태 용량**뿐이다.
**0.13% 로는 3.1% 를 설명할 수 없다.**

남은 후보 둘, **이 실험으로는 구분 못 한다**:

| 후보 | 근거 |
|---|---|
| **캐시 지역성** | 유니크 MLP 6개(11.2MB)가 dense 20개(25.2MB)보다 L2/L3 에 잘 앉는다. 결과 014 §11.3 의 *"mC 가 층당 21.5% 싸고 g 순서로 단조"* 와 같은 방향 |
| **옵티마이저 메모리 대역폭** | AdamW 는 파라미터당 모멘트 2개를 읽고 쓴다. 132.5M → 63.5M 이면 그 트래픽이 절반. "스텝 시간 0.13%" 는 **연산** 기준이라 대역폭을 포함하지 않을 수 있다 |

→ **분리하려면** g4 arm 을 넣어 g 단조성을 보거나, 옵티마이저를 SGD 로 바꿔 재측정한다. **미착수.**

## 4. ★진짜 상금 — VRAM −35.3%

배치가 미리 적어 둔 문장이 맞았다:

> *"Tying should cut optimiser state roughly in half; that is a **CAPACITY win** and it is real even if the time win is not."*

| | dense | g8 |
|---|---:|---:|
| VRAM reserved | 7.82 GB | **5.06 GB** |
| 여유(16GB 카드, 스필벽 13~14GB) | 5.2~6.2 GB | **8.0~9.0 GB** |

**이것이 시간 이득보다 값어치가 크다.** VRAM 여유는 곧

- **`--no-ckpt` 개방**(−17.3%, `CLAUDE.md`) → **P042 의 전제**
- 더 큰 `M = micro_bs × seq`
- **KD 교사를 함께 올릴 여지**

⚠️ 단 이 런은 **KD 없음**이다. KD 를 켜면 교사 몫이 얹혀 그림이 달라진다 — **그게 P042 다.**

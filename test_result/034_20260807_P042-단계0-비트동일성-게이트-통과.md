### 3.1 속도 — 참고값, 순위 매기지 않음

| 조건 | step29 인쇄 | step0 | **환산 정상상태** |
|---|---:|---:|---:|

비 0.794 = **−20.6%**. **이 숫자를 인용하면 안 된다.** 교락이 셋이다:

1. **OFF 가 먼저 돌았다.** 같은 배치 안에서 순서가 고정이고 직전에 dense 부모 런이 있었다 —
   열·CUDA 컨텍스트·캐시 상태가 두 런에서 다르다(결과 016 §12.5 가 요구하는 "단독·직전 5분 유휴" 미충족).
2. **tiny 프리셋이라 비율이 다르다.** 교사가 5.5M 이고 층이 6개뿐이라
   `refresh_quant()` 가 스텝에서 차지하는 비중이 m100(132.5M·20층)과 같을 리 없다.
3. **30스텝**이다. 첫 스텝을 뺐어도 표본이 29개다.

## 9.1 정상상태 ms/step — **drift 를 먼저 계산한다**

환산 `(누적평균×250 − step0)/249`:

| 런 | 태그 | 누적평균(step249) | step0 | **정상상태** |
|---|---|---:|---:|---:|
| [1/3] OFF_A | `mC_tinf_off` | 3712 | 62,852 | **3474.5 ms** |
| [2/3] **ON** | `mC_tinf_on` | 3790 | 59,444 | **3566.5 ms** |
| [3/3] OFF_B | `mC_tinf_off2` | 3740 | 58,038 | **3521.9 ms** |

```
drift  = OFF_B − OFF_A = +47.4 ms  (+1.37%)
effect = ON − mean(OFF) = +68.3 ms  (+1.95%)   ← 부호가 +다. 느려졌다
|drift| / |effect| = 0.69
```

> ★**배치 꼬리말이 미리 정한 판정 규칙**: *"drift 가 effect 와 비슷하면 그건 열이지 효과가 아니고,
> 정직한 답은 숫자가 아니라 '이 장비의 노이즈 이하'다."* → **그 갈래에 정확히 들어갔다.**
> **정직한 결론: 교사 추론 모드는 학습 속도를 바꾸지 않는다.** 굳이 부호를 말하면 **미세하게 느리다.**

### ★★그리고 이것이 결과 034 §3.1 의 참고값을 **폐기**한다

§3.1 은 tiny 게이트에서 **−20.6%** 를 보고 *"P1(−0~5%)이 기각될 수 있다"* 고 적었다.
**틀렸다.** 그 −20.6% 는 **순서 교락 하나로 전부 설명된다**(OFF 가 먼저 돌았다).
**3런 설계가 아니었으면 이번에도 같은 착각을 했을 것이다** — OFF_A 만 있었다면
effect 를 +2.6% 로 읽었을 것이고, OFF_B 만 있었다면 +1.3% 로 읽었을 것이다.
**둘 다 노이즈인데 숫자가 달라진다.**

| 예측 | 결과 |
|---|---|
| **P1** 교사 forward 는 크게 안 빨라진다(−0~5%) | ✅ **적중.** 다만 *"안 빨라진다"* 가 아니라 **"측정 불가"** 가 더 정확하다 |

## 10.1 두 번 돌았고 결과가 갈렸다

| 시각 | NVIDIA "CUDA — 시스템 메모리 대체" | 결과 |
|---|---|---|
| 03:19 | **비대체 선호**(스필 금지) | 🚫 **OOM, 35초** |
| 03:35 | **기본값**(대체 허용) | ✅ **완주 12.2분** |

**OOM 메시지 전문의 핵심**:

```
torch.OutOfMemoryError: ... Tried to allocate 1024.00 MiB.
GPU 0 has a total capacity of 15.99 GiB of which 0 bytes is free.
Of the allocated memory 13.00 GiB is allocated by PyTorch,
and 1.71 GiB is reserved by PyTorch but unallocated.
```

발생 지점은 **`F.kl_div`** — 즉 **KD 손실 계산**이다.

> ★★**1024.00 MiB 는 우연이 아니다.** `M × V × 4B = 8192 × 32768 × 4 = 정확히 1024 MiB`.
> **KD 손실이 어휘 전체(32,768) × 토큰 전체(8,192) 위에서 fp32 텐서를 여러 개 만든다.**
> 이 사실이 §11 과 `docs/methods/09_training_memory.md` 의 출발점이 됐다.

> ★그리고 **1.71 GiB 가 "reserved but unallocated"** = 단편화다. 즉 **용량이 부족해서가 아니라
> 연속 1 GiB 를 못 찾아서** 죽었다. 메시지가 직접 `expandable_segments:True` 를 권한다.

## 10.2 완주한 런의 수치

| 항목 | 값 | 비교 |
|---|---:|---|
| peak reserved | **15.37 GiB** | 총 15.99 GiB 중 **여유 0.62 GiB** |
| peak alloc | **14.00 GiB** | |
| **정상상태 ms/step** | **2836.1** | 단계1 ON(3566.5) 대비 **−20.5%** |
| 벽시계 | 12.2분 | 15.9분 대비 −23.2% |
| `grad_max` / `skip` | 1.196 / **0** | 건강 |
| final val | 4.0809 | (250스텝 — 품질 판정 금지) |

★**−20.5% 는 기준표의 −17.3% 보다 크다.** 기존 값은 dense·비KD 조건에서 나온 것이다.

## 10.3 ★스필했는가 — 순간 ms/step 으로 판별했다

누적평균을 구간 순간값으로 되돌렸다(`((n₁+1)c₁ − (n₀+1)c₀)/(n₁−n₀)`):

| 런 | reserved | step100 이후 순간 ms/step |
|---|---:|---|
| `mC_tinf_nockpt`(fallback ON) | 15.37 | **2694 2903 2708 2907 2711 2907 2713 2912 …** ±0.5% |
| (참고) `mC_ct250_nockpt`(P018) | 14.95 | **4095 4029 4182 5643 3772 5478 3625 …** 변동 **+67%** |

두 값이 번갈아 나오는 것은 **KD 스텝(1/4)과 비KD 스텝**의 차이다 — **완벽하게 규칙적**이다.
→ **15.37 GiB 런은 스필하지 않았다.** (VRAM 이 더 적은 P018 런은 스필했다 — 결과 037 §5)

## 10.4 단계2 판정 — **조건부 통과**

| 게이트 | 결과 |
|---|---|
| **G3** `--no-ckpt` 250스텝 완주 | ⚠️ **조건부 통과** — 시스템 메모리 대체가 **허용된 상태에서만** |

**그러므로 `EXPERIMENT_BASELINES` §5 를 지금 "안전" 으로 고쳐 쓰지 않는다.** 사실은 이렇다:

- 기준표 §5 의 *"tied+KD+dense교사 15.7GB"* 는 **거의 맞았다**(실측 15.37).
  §4-B 에서 *"낡았을 수 있다"* 고 의심한 것은 **빗나갔다** — 그 숫자는 살아 있다.
- **−35.3%(결과 033)와 모순되지 않는다** — §11 참조.
- `--no-ckpt` 는 **여유 0.62 GiB** 로 성립한다. 이건 **표준 조건으로 승격하기엔 너무 얇다.**
  단편화 하나로 03:19 처럼 죽는다.
- ★**그래서 P042 §7 안 B(압축 교사)가 답이 됐다** — 결과 037 이 **같은 조건에서 −1.88 GiB** 를 잰다.

# 11. ★사용자 질문 — **왜 결과 033 의 −35.3% 가 단계2 에서 안 보이는가**

> *"프리셋(m100R1c)이 P40 실험과 큰 차이가 있어서 그런건지 아니면 −35.3%로 줄었음에도 메모리가 모자랐던 것인지"*

**후자다. 그리고 프리셋은 무관하다.** 결과 033 의 재현 명령을 보면 조건이 다르다:

```
결과 033  ts_dense : --arch dense --mlp-group 없음  --kd 없음  --init-from 없음   -> 7.82 GB
결과 033  ts_g8    : --arch tied  --mlp-group 8     --kd 없음  --init-from 없음   -> 5.06 GB   (−35.3%)
P042 단계2         : --arch tied  (m100R1c=g8)      --kd 있음  --init-from 있음  --no-ckpt -> 15.37 GB
```

**−35.3% 는 "학생 단독 학습" 축의 값이고 여전히 유효하다.** 우리 표준 런이 그 위에 **KD 교사**와
**`--no-ckpt`** 를 얹을 뿐이다. 실측으로 분해하면:

| # | 구성 (전부 M=8192, tied g8) | reserved | **alloc** | 직전 대비 alloc |
|---|---|---:|---:|---:|
| a | tied 단독, ckpt ON, **KD 없음** (`ts_g8`, 결과 033) | 5.06 | **4.55** | — |
| b | a + **KD dense 교사** (`mC_tinf_off`) | 12.47 | **10.03** | ★**+5.48 GiB** |
| c | b + 교사 추론 모드 (`mC_tinf_on`) | 11.45 | **9.55** | −0.48 |
| d | b 의 교사를 **압축 교사**로 (`mC_ct250`, 결과 037) | 10.59 | **9.52** | −0.51 |
| e | c + **`--no-ckpt`** (`mC_tinf_nockpt`) | **15.37** | **14.00** | **+4.45** |

★★**KD 교사 하나가 +5.48 GiB 다.** 그런데 **교사 파라미터 상주는 945 MiB 뿐**이다
(dense 삼진 latent 472.5 + dequant 사본 472.5 MiB). **나머지 약 4.5 GiB 는 파라미터가 아니라
교사 forward 의 활성과 KD 손실 계산의 대형 텐서**다.

**KD 손실 영역 회계**(M=8192, V=32768, `torch.autocast(bf16)` — `cross_entropy`·`log_softmax`·
`softmax` 는 autocast 의 **fp32 목록**에 있다):

| 텐서 | dtype | 크기 | 그래프 보존 |
|---|---|---:|---|
| 학생 `logits` | bf16 | **512 MiB** | ✅ |
| `cross_entropy` 내부 log_softmax | fp32 | **1024 MiB** | ✅ |
| `logits / T` | bf16 | 512 MiB | 임시 |
| 학생 `log_softmax(logits/T)` | fp32 | **1024 MiB** | ✅ |
| 교사 `tlog` | bf16 | 512 MiB | 임시 |
| 교사 `softmax(tlog/T)` | fp32 | **1024 MiB** | 임시 |
| `kl_div` 원소별 임시 | fp32 | **1024 MiB** | 임시 |
| | | **피크 ≈ 5.1 GiB** | |

**회계가 실측 +5.48 GiB 와 맞는다.** 그리고 **OOM 이 요구한 1024.00 MiB 가 이 표의 한 줄**이다.

> ★★★ **결론: 우리 학습 VRAM 의 최대 단일 항목은 모델도 옵티마이저도 교사 파라미터도 아니라
> "어휘 전체 위의 KD 손실 계산" 이다. 이 저장소는 그것을 한 번도 본 적이 없다.**

## 11.1 이 답이 바꾸는 것

- 기준표 §5 의 **"tied+KD+dense교사 15.7GB" 행은 살아 있다** — §4-B 의 의심을 **철회**한다.
- **결과 033 의 −35.3% 도 살아 있다.** 두 값은 **다른 축**이라 모순이 아니다.
- ⚠️ **그러나 둘을 나란히 인용하면 오해를 부른다.** 기준표에 **"어느 축의 값인가" 를 명시**한다.

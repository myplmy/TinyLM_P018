# 실험 003 — P014①: 커스텀 삼진 커널 레퍼런스 정확성

- 실험계획: P014 (커스텀 삼진 커널 검증)

## 결과 (수정 전)
- k_off(기존 경로) vs k_ref(커널 레퍼런스): **step0부터 loss 불일치** (10.4017 vs 10.3978, 최종 9.318 vs 9.371).

## 원인
- 커널이 **삼진 어닐링을 미구현**. 기존 경로는 `_wq = wq + (1-anneal)·(w-wq).detach()` 로
  anneal<1 구간에서 **full-precision↔삼진 블렌드**(step0은 anneal=0이라 사실상 full-precision)를 쓰는데,
  커널은 **항상 순수 삼진** → 어닐 구간(=이 40스텝 대부분) 내내 달라짐. anneal=1에서만 일치.
- **P014가 의도대로 버그를 사전 포착**(실사용 전 검증 게이트).

## 수정
- 커널 forward가 동일 어닐 값(eff = wq + (1-anneal)(w-wq))을 쓰고, **anneal>=1(완전 삼진)에서만 저비트 경로**
  사용하도록 재작성. backward는 STE window(어닐 무관) 유지 → 기존 경로와 값·gradient 모두 동일.
- (별건) backward dtype 충돌(bf16 @ float32)도 수정.

## 다음
- P014① 재실행 → k_off와 k_ref loss가 **정확히 일치**해야 정상. 이후 ② Triton 정확성, ③ 속도.

## 재검증 (어닐 수정 후)
- k_off vs k_ref: **step0 정확히 동일(10.4017=10.4017)** → forward bit-exact. 최종 9.3181 vs 9.3169(차 ~0.001).
- 잔차 원인: backward의 **가중치 grad를 커널은 float32, 기존 경로는 autocast(bf16)로 계산** → bf16 누적 정밀도 차이.
  **로직 버그 아님, 커널이 오히려 더 정밀.** → **수학적 등가 확인, 수정 불필요.** P014① 사실상 통과.
- (원하면 backward를 bf16로 맞춰 완전 일치 가능하나 float32가 정확도상 유리.)

## P014② — Triton forward 정확성 테스트 (2026-07-25)

- 실험계획: P014 (커스텀 삼진 커널 검증) — ② Triton 경로.
- 증상: `--ternary-kernel-triton` 로 t_kd_g16 진행 중, **약 10스텝 이후** Triton 실패 →
  레퍼런스 폴백 메시지가 **매 forward마다** 출력되어 cmd 버퍼를 초과, 로그 확인 불가.

### 원인 (확정, 디버그 로그 불필요)
1. **Triton 컴파일 에러 = `arange's arguments must be of type tl.constexpr`.**
   커널 `_tern_mm_kernel` 의 `offs_g = tl.arange(0, G)` 에서 `G`(=micro_group=128)를
   **런타임 커널 인자**로 넘겼다. `tl.arange` 의 상한은 반드시 **컴파일타임 상수(constexpr)** 여야 한다.
   → JIT 컴파일 단계에서 실패.
2. **왜 "10스텝 이후"에 터졌나 = 정상 동작.** Triton 저비트 경로는 `anneal>=1.0`(완전 삼진)에서만
   활성. 어닐이 1.0에 도달하기 전(초기 ~10스텝)은 full-precision 블렌드(`F.linear`)라 커널 미호출 →
   조용. 어닐=1 도달 순간 모든 TLinear가 Triton 시도 → 전부 컴파일 실패 → 폴백.
3. **로그 폭주 = 폴백 print 가 forward마다 실행.** TLinear 다수(q/o/k/v/gate/up/down×층) × 스텝 ×
   accum → 수천 회. (결과는 오염 안 됨: 폴백이 레퍼런스=기존 경로와 수학적 동일이므로 **학습은 정상**.)

### 수정
- `ternary_kernel.py`: 커널 시그니처에서 `G` 를 **`tl.constexpr`** 로 이동, 런치 시 `G=group`(키워드
  constexpr)로 전달. 루프 내 alpha 그룹 인덱스는 수동 카운터(`g_idx`) 대신 **`kb // G`**(constexpr 나눗셈)로.
- **폴백 경고 1회화**: 모듈 전역 `_KERNEL_WARNED` 플래그 → 최초 1회만 출력(`...(이후 조용히)`), 이후 침묵.
  에러 메시지도 120자로 절단. → 폭주 원천 차단(향후 다른 커널 오류가 나도 로그는 1줄).

### 상태
- 컴파일 에러 원인 **확정 → 별도 디버그 로그 추가 불필요**. constexpr 수정으로 해소 예상.
- 안전성: 설령 Triton이 또 실패해도 폴백=레퍼런스(정확)라 **학습 오염 없음**, 로그도 1줄. 재실행 안전.
- 다음: `--ternary-kernel-triton` 재실행 → (a) 폴백 경고가 최대 1줄인지, (b) Triton이 실제로 도는지
  (경고 없으면 성공), (c) k_ref vs k_triton loss 일치(bit-exact 또는 bf16 잔차 ~0.001) 확인. 그 뒤 ③ 속도.

## P014② — Triton 재실험 결과·분석 (2026-07-25, constexpr 수정 후)

명령: `... --tiny --data synthetic ... --ternary-kernel --ternary-kernel-triton --compile --tag k_triton`
(t_kd_g16 과 GPU 동시 사용 상태)

### 정확성 = 통과
- k_off 9.3181 / k_ref 9.3169 / **k_triton 9.3181**, best 모두 9.315~9.316. 차이 ~0.001 = bf16 잔차.
  → **constexpr 수정으로 Triton forward 정상 컴파일·실행, 레퍼런스와 수치 등가.** 폴백 폭주도 없음(경고 0줄).

### 특이 로그 = recompile 폭주 (원인 규명)
- `torch._dynamo hit config.recompile_limit (8)`, 이유 `quant_anneal.item() == 0.4117...`.
- 원인: 커널 진입점 `ternary_kernel_linear` 이 `float(cfg.quant_anneal)` 로 **anneal 값을 파이썬 스칼라로 읽음**
  → torch.compile 이 그 값에 **가드**를 검. anneal 은 매 스텝 변함 → 스텝마다 재컴파일 → 한도(8) 초과 →
  dynamo 포기(이후 eager). **일반 TLinear 경로는 `_anneal` 버퍼(텐서)를 써서 가드가 없음** → 커널 경로 특유 문제.
- 게다가 `if anneal >= 1.0` 분기가 **데이터 의존 제어흐름**이라 compile 과 근본적으로 상성 나쁨(그래프 브레이크).

### 속도 = GPU에선 커널이 느린 게 정상
- k_triton 5000~7000 ms/step vs k_ref ~500 ms → 10×+. 원인 3가지:
  1) **recompile 폭주**(위) — compile 이 매 스텝 재시도하며 churn.
  2) **커널 자체가 소박함**: BM=BN=64, fp32 누적, 오토튠 불가("Not enough SMs")·d=256 극소 모델 →
     **커널 런치 오버헤드 지배**, cuBLAS(F.linear, TF32/bf16)엔 원천적으로 못 미침.
  3) t_kd_g16 동시 실행으로 GPU 공유(부차적).
- **결론: 정상이며 예상된 결과.** 이 Triton 커널은 **GPU 학습 가속기가 아니다.** 목적은 CPU LUT
  배포 커널의 정확성 프로토타입. GPU 학습은 cuBLAS(F.linear)가 정답.

### 조치
- `trainer.py`: `--ternary-kernel-triton` + `--compile` 동시 사용 시 **경고 출력**(recompile 폭주 안내,
  커널 벤치는 `--compile` 없이 실행 권장).
- 커널 정확성 게이트 **통과**. 향후 방향은 GPU 속도가 아니라 **CPU LUT/AVX2 배포**(P016 Sherry 3:4 정합)로.

## P014② — `--compile` 없이 재측정 (2026-07-25, 로그 `003_log_..._(2)`)

명령: `... --tiny --data synthetic ... --ternary-kernel --ternary-kernel-triton --tag k_triton` (**--compile 제거**)

### 속도 = recompile 아티팩트였음 (정정)
- k_triton **435ms(step0)→160~250ms/step** 로 안정. 직전 `--compile` 동반 실행의 **5000~7000ms 및 4000ms**
  는 **torch.compile 재컴파일 폭주(quant_anneal 값 가드)** 가 지배한 수치였고, **커널 자체 문제가 아니었다.**
- 즉 003 앞 절의 "10×+ 느림"은 **compile-recompile 병리**에 기인. `--compile` 을 빼면 k_off(기존 경로)와
  **큰 속도 차이 없음**(tiny·d=256에선 둘 다 런치 바운드로 사실상 동급).

### 재검토 필요성 판단
- **전략적 결론은 불변**: weight-only 삼진은 dequant 후 dense와 **동일 FLOPs** → GPU **학습** 가속은
  스케일에서도 기대할 수 없다(handoff §3). tiny에서 triton≈k_off인 것은 "가속 증거"가 아니라 **둘 다
  런치 바운드**여서다(GEMM이 극소).
- 다만 003의 "커널이 10× 느리다"는 **표현은 오해 소지** → 위처럼 정정(원인=compile 재컴파일). 커널은
  기능·정확성 정상.
- **추가 재측정 가치**: GPU **decode/추론**(M=1) 을 겨냥한다면 m100(d=768) 에서 `--compile` 없이
  k_off vs k_triton A/B 가 의미 있다(그때 SplitK/StreamK 업그레이드 근거). **학습 목적이면 저순위**
  (FLOPs 논리상 이득 없음). 배포(CPU LUT)가 본 목적임은 그대로.

### 조치 (코드)
- `trainer.py`: 이제 `--ternary-kernel[-triton]` + `--compile` 동시 사용은 **경고가 아니라 SystemExit로
  학습을 중단**한다(로그의 dynamo IndexError 크래시·재컴파일 폭주 원천 차단). 커널 벤치는 `--compile` 없이.

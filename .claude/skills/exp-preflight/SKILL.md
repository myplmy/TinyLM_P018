# exp-preflight

## 왜 이 스킬이 필요한가

이 프로젝트에서 지금까지 가장 비싼 실수는 **코드 버그가 아니라 실험설계 오류**였다.

| 사고 | 낭비 | 원인 |
|---|---|---|
| P007 정본 300M 풀 계열 전체 | 약 18h | 학습토큰과 **데이터 풀 크기**를 분리하지 않아 dense 가 0.12 핸디캡을 안았다(결과 006) |
| P012 큐레이션 데이터 비교 | 약 4h | 데이터셋마다 **토크나이저·val 셋이 다른데** bpb 로 교차비교했다(결과 009) |
| P021 [4/4] 미실행 | 수동 재실행 | 배치가 `goto ERROR` 라 [3] OOM 이 [4]를 죽였다(결과 007) |
| 결과 005 초판 | 재측정 | `--accum 16` 을 빠뜨려 150M 만 학습됐다 |

넷 다 **돌리기 전 5분 대조로 잡을 수 있었다.** 이 스킬은 그 5분을 강제한다.

## ★한계 — 반드시 사용자에게 함께 말할 것

이 스킬은 **설계 검증(design check)** 이지 **결과 예측이 아니다.**

- 통과 = "알려진 실수를 반복하지 않았다". **가설이 참이라는 뜻이 전혀 아니다.**
- 통과 = "이 조건이 좋은 조건"이라는 뜻도 아니다. 효과 크기·수렴 여부·안정성은 **실제로 돌려야만** 안다.
- 기준표는 **과거 실측치**다. 새 아키텍처·새 데이터·새 스케일에서는 그 수치가 통하지 않을 수 있고,
  기준표 자체가 틀렸음을 새 실험이 밝힐 수도 있다(실제로 결과 006이 "토큰 늘리면 격차 닫힘" 가설을 기각했다).
- σ(재현 노이즈)가 **미측정**이라 "예상 효과가 노이즈보다 큰가" 항목은 **현재 판정 불가**다.
  이건 이 스킬의 알려진 구멍이고, P021 추가검증 A 가 나오면 메워진다.

보고 마지막에 이 한 줄을 반드시 붙인다:

> 이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.

## 절차

### 0. 기준 읽기 (건너뛰지 않는다)

1. `docs/EXPERIMENT_BASELINES.md` 를 읽는다. 특히 §1 표준조건 · §2 레지스트리 · §3 비교유효성 ·
   §7 확정된 사실.
2. `python scripts/check_run_registry.py` 로 현재 로그 상태를 조회한다.

### 1. 체크리스트 (항목마다 통과/경고/중단 판정)

**A. 계산**
- [ ] 학습토큰 = `steps × micro_bs × accum × seq` 를 실제로 계산했는가?
      → `python scripts/check_run_registry.py --steps N --micro-bs M --accum A --seq S`
- [ ] `--accum` 을 명시했는가? (**기본값 8**. 300M 라인 표준은 16. 빠뜨리면 절반만 학습)
- [ ] `--tokens` 를 학습길이로 착각하지 않았는가? (그건 캐시 크기다)
- [ ] steps 를 바꿨으면 목표 토큰이 여전히 맞는가?

**B. 데이터 풀**
- [ ] 풀 ≥ 2× 학습토큰인가? (`--pool-tokens` + `--exact-cache`) — 결과 006
- [ ] 비교 대상 런들이 **같은 풀**인가? 다르면 그 비교는 **무효**다
- [ ] `ko-edu-en` 을 쓰려 하는가? → **진단 전 사용 보류**(결과 009, P028)

**C. 태그·덮어쓰기**
- [ ] `python scripts/check_run_registry.py --tag <새태그>` 를 실행했는가?
- [ ] 정본(`dense`/`tied`, 태그 없음)을 덮어쓰지 않는가? — 스윕은 반드시 태그를 붙인다
- [ ] 태그를 `EXPERIMENT_BASELINES.md` §2.6 네임스페이스 표에 추가할 계획인가?
- [ ] 교사·부모를 정본이 아니라 **태그된 것**에서 가져와야 하는가? (`--kd-teacher-tag`/`--init-from-tag`)

**D. 중복**
- [ ] `python scripts/check_run_registry.py --plan "<조건 자유문>"` 으로 유사 런을 확인했는가?
- [ ] 완전히 같은 조건이면 **돌리지 말고 기존 로그를 쓴다**
- [ ] 일부만 다르면 **무엇이 독립변수인지** 한 문장으로 쓸 수 있는가? 못 쓰면 설계가 안 된 것이다

**E. 비교 유효성** (`EXPERIMENT_BASELINES.md` §3)
- [ ] 토크나이저·데이터셋이 같은가? (다르면 val_loss·bpb 둘 다 무효)
- [ ] 학습토큰·교사·부모초기화 소스가 같은가?
- [ ] grad-ckpt on/off 가 섞이지 않았는가? (수식은 같지만 수치 드리프트가 있다)
- [ ] steps 수가 같은가? (250 vs 2289 는 warmup 비율도 달라 품질 비교 불가)
- [ ] 유효배치가 다르면 ms/step 을 **토큰당**으로 정규화할 계획인가?

**F. 자원**
- [ ] VRAM 이 예산표(§5) 안인가? **tied+KD+dense교사 + `--no-ckpt` 는 금지**(OOM 위험)
- [ ] 총 예상 시간을 계산했는가? (레지스트리의 분 값으로 추정)
- [ ] 배치가 한 런 실패로 중단되지 않는가? (`run-batch` 스킬 참조)

**G. 판정 가능성**
- [ ] 무엇을 보면 성공/실패인지 **사전에** 정했는가? (기준 = 어떤 런의 어떤 수치)
- [ ] 예상 효과 크기가 얼마인가? **σ 미측정이라 `≤0.05` 급은 판정 불가**임을 계획서에 명시했는가?
- [ ] 안정성은 인쇄 `|g|` 가 아니라 json `grad_max` 로 볼 계획인가?

### 3. 중단 규칙

다음 중 하나라도 걸리면 **명령을 제시하지 말고** 사용자에게 먼저 알린다.

1. 독립변수를 한 문장으로 쓸 수 없다
2. 태그가 정본을 덮어쓴다
3. 비교 대상과 풀·토크나이저·학습토큰이 다르다
4. 완전히 동일한 조건의 런이 이미 있다
5. VRAM 예산 초과가 예상된다
6. 성공/실패 판정 기준이 없다

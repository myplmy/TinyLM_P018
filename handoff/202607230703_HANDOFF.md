## 0. 프로젝트 목표

저사양 CPU/엣지 환경용 초경량 LLM 아키텍처를 설계하고 검증한다.
**연산량이 아니라 메모리를 최적화**하는 것이 목적이다 (연산 증가는 감수).

최종 지향점: dense 대비 절반 이하 메모리로 유사 품질. 성공 시 8B급을 1.7B급
메모리로, 27B급을 8B급 메모리로 구동.

## 1. 현재 아키텍처 (v4) — 확정 스펙

```
prelude 2층      어텐션·MLP 전부 독립          (임베딩 직후 조정)
   ↓
중간 16층        어텐션: 층마다 독립 (16세트)
                 MLP:    4층씩 묶어 4그룹만 저장 (g=4)
                 K/V:    인접 2층이 공유 (CLA2)
                 adaLN:  층별 scale/shift/gate
   ↓
coda 2층         어텐션·MLP 전부 독립          (lm_head 직전 조정)
   ↓
최종 RMSNorm → factorized lm_head (전치 공유)
```

**검증용 100M급 설정** (`d=768 ffn=2048 heads=12/3 vocab=32768 E=256`)

| | tied | dense 기준선 |
|---|---|---|
| 파라미터 | 72.9M | 132.5M |
| 배포 메모리 (1.95bpw) | 17.1 MB | 30.9 MB |
| L3(32MB) 상주 | 가능 (여유 14.9MB) | 불가 |
| KV 캐시 | 7.5 KB/token | 15.0 KB/token |
| 토큰당 FLOPs | 0.248 GFLOP | 0.248 GFLOP (동일) |

감축 비율 **1.82배**. FLOPs가 같은 건 의도된 것 — 타잉은 메모리를 줄이지 연산을 줄이지 않는다.

### 유지 중인 요소
- g128 삼진 양자화 (llama.cpp Q2_0_g128 / T-MAC 호환 레이아웃)
- TWN 임계(0.7·E|w|) + L2 최적 alpha
- weight 기반 AMP-안전 STE (grad에 선형 → GradScaler·배치크기 불변)
- 삼진 어닐링 (배포 시점 = 학습 종료 시점, train/test 불일치 없음)
- 공유 MLP LR 1/√g, weight decay 미보정
- gradient checkpointing (선택), 삼진화 호이스팅

### 기본 off인 요소
- mode-delta (`mode_rank=0`) — adaLN만으로 동등한 효과 확인 (0.0134 vs 0.0132)
- 모드 라우팅 (`n_modes=1`)

## 2. 설계 결정과 근거 (측정 기반)

### 2-1. depth-delta 폐기 — **측정으로 확정**

Qwen3-1.7B에서 `rank_spectrum_v3.py`로 레이어 간 잔차의 저랭크 구조를 측정.

**레이어 쌍별 코사인 유사도가 전 항목 0** (최대 +0.009, gate_proj).
고차원에서 서로 다른 가중치 행렬은 거의 직교한다. → 그룹 구성(adjacent vs
similarity)으로 얻을 게 없다.

**excess ÷ 비용 효율** (excess = 널 대조군 대비 초과 포착률, 비용 = r/r*):

```
행렬          r*        r=16              r=32              r=64
q_proj       109   14%/15%=0.96      20%/29%=0.68      27%/58%=0.46
k_proj        73   14%/22%=0.64      20%/44%=0.46      27%/88%=0.31
v_proj        73    7%/22%=0.32      12%/44%=0.27      18%/88%=0.21
o_proj       109    6%/15%=0.41      10%/29%=0.34      15%/58%=0.26
gate_proj    164    5%/10%=0.51       7%/19%=0.36      11%/39%=0.28
up_proj      164    3%/10%=0.31       5%/19%=0.26       8%/39%=0.21
down_proj    164    4%/10%=0.41       6%/19%=0.31      10%/39%=0.26
```

**효율 1.0 미만 = 같은 메모리로 레이어를 그냥 하나 더 두는 게 낫다.
전부 1.0 미만이므로 delta는 depth 특화에 쓸 수 없다.**

특히 파라미터의 75%를 차지하는 MLP가 0.26~0.51로 가장 나쁘다.

### 2-2. 측정 방법론 함정 — 활성 가중은 지표를 오염시킨다

v2에서 활성 가중(`--calib`)을 켜자 수치가 49~75%로 치솟았으나, **구조가 전혀
없는 랜덤 행렬**로 널 대조군을 돌려보니:

```
가중 방식              동적범위      r=16    r=32    r=64
가중 없음                 1.0        6%     11%     21%
LLM 유사 (heavy)    187,253x        81%     92%     97%   <-- 구조 0인데 81%
```

동적범위 무제한이면 실측·널 모두 100%로 포화해 판별력이 완전히 사라진다.
**v3은 널 대조군(열 노름 보존 셔플)을 함께 계산하고 차이(excess)만 보고한다.
기본 clip=10x. 판정선: excess < 10%p → 구조 없음, > 30%p → 구조 있음.**

### 2-3. 어텐션은 층별 독립, MLP만 타잉

EPFL "Tying the Loop" (arXiv:2606.16825) 컴포넌트 ablation:
- 어텐션을 풀면 모든 토폴로지에서 손실 0.030~0.058 개선
- 라우터만 풀면 최대 0.009 변화, 부호도 일정하지 않음
- 그런데 파라미터 수는 FFN이 어텐션을 자릿수 단위로 압도

→ **타이드 레이어를 구별시키는 건 어텐션이지 라우터/delta가 아니다.**
2-1의 측정과 상보적: MLP는 차이가 full-rank 잡음이라 delta로 못 잡고,
동시에 기능적으로 묶어도 싸다. 어텐션은 반대.

### 2-4. prelude/coda 분리가 단일 최대 이득

같은 논문: MoEUT식 전층 타잉 vs 2+2 언타이드 prelude/coda의 격차가
0.097~0.202로, 타잉 모드 효과(~0.05)와 토폴로지 차이(~0.04)를 압도.
첫·마지막 층은 임베딩 입력/lm_head 출력 조정이라 질적으로 다르다.

### 2-5. 타잉 비용의 기준선

- g=2: 손실 +0.02~0.03, 파라미터 29~35% 절감
- g=4: 손실 +0.05~0.07, 43~52% 절감, 다운스트림 최대 -1.9%p
- **7B에서 g=4는 손실·정확도 동률**(2.825 vs 2.820 / 47.5% vs 47.4%), 50.9% 절감
- 큰 모델일수록 타잉 손해가 줄어든다 (우리 확장 목표에 유리)

Relaxed Recursive Transformers (ICLR 2025): 2:1 공유 + LoRA로 원본 대부분 회복.
**검증된 건 2:1까지. 4:1 이상은 외삽.**

### 2-6. 임베딩 처리

151,936×2048 = 311M 파라미터 = 삼진화해도 76MB. 블록을 아무리 줄여도
이 크기는 그대로라 **메모리 바닥**이 된다.

```
방안                              파라미터   메모리   절감
현재 (151,936 × 2048, 삼진)        311.2M   72.3MB   1.0x
(a) vocab 64k로 축소               131.1M   30.5MB   2.4x
(b) factorized E=512               78.8M   18.3MB   3.9x
(c) 1-bit 임베딩                   311.2M   37.1MB   2.0x
(a)+(b) 64k + E=512                 33.8M    7.9MB   9.2x  <-- 채택
```

부수 효과: lm_head 연산도 8배 싸진다. 리스크: 로짓 랭크가 E로 제한됨.

### 2-7. L2/L3 상주는 1.7B급에서 포기

전체 L3 상주에 필요한 총 가중치 < 24MB = 약 103M 파라미터. 764M(1.7B 구성)은
7배 초과. **그리고 이 목표 자체가 불필요하다** — 타잉으로 대역폭을 줄인 결과
CPU가 이미 연산 바운드(28.19ms)가 대역폭(3.72ms)의 7.6배다.

RTX 4070 Ti와 비교하면 GPU가 10~30배 빠르고, 1.7B fp16(3.4GB)은 12GB에 그냥
들어간다. **삼진화의 가치는 GPU가 아니라 CPU·모바일·임베디드에서만 성립한다.**

### 2-8. 벤치마크 함정 — 합성 데이터는 순수 암기 과제

```
구절 수        dense val    tied val         격차    |g|max
512             7.7873      7.9054     +0.1181      27.6
50,000          8.7505      8.7508     +0.0002       1.6
```

반복 구절 코퍼스는 암기하면 끝이라 파라미터 수가 그대로 성능이 된다.
타잉은 정의상 파라미터를 줄이므로 구조적으로 불리하게 나온다.
**합성 데이터로는 품질 판정을 하면 안 된다. 파이프라인 동작 확인 전용.**

## 5. **미해결 — 최우선 과제: 학습 발산(NaN)**

### 증상

300M 토큰 실전 학습에서 dense·tied 양쪽 모두 NaN.

```
dense:  step 40  |g| 36.51  → step 60  nan      (lr 2.00e-03 도달 직후)
tied:   step 70  |g| 40.42  → step 90  |g| 228.71 → step 100  nan
```

### 진단

**NaN이 `anneal 0.00`에서 발생 → 삼진화 이전, 완전 FP 상태의 발산.
dense도 동일하게 터짐 → 타잉 문제도 아님.** 순수 학습 불안정.

원인 셋:

1. **LR 2e-3 과다.** d=256 소형 실험값을 d=768에 그대로 적용한 실수.
   폭 3배 → LR 1/3, 유효 배치 131K는 nanoGPT 기준(0.5M)의 1/4 → 또 낮아져야 함.
   **적정선 6e-4.**
2. **QK-norm 부재.** `|g| 3 → 36 → 228 → nan`은 어텐션 로짓 폭주의 전형.
   EPFL 참조 설정은 q·k 내적 전에 RMSNorm을 건다. **주원인으로 추정.**
3. **NaN 가드 부재.** `clip_grad_norm_`이 nan을 반환해도 `opt.step()`이 실행되어
   전체 가중치가 영구 오염. 186분을 그대로 낭비.

**Windows/Triton은 무관.** 로그의 두 경고는:
- `Not enough SMs to use max_autotune_gemm` — 4070 Ti SM 수가 적어 자동튜닝 생략. 무해.
- `hit config.recompile_limit (8) ... quant_anneal` — Python float가 매번
  dynamo 가드를 깨뜨려 재컴파일. **성능 문제**(step 170에서 eager 폴백,
  3931 → 5513 ms/step). NaN은 step 60이므로 원인 아님.

### 적용해야 할 패치 (미검증 — 사용자 테스트 필요)

#### 패치 1: QK-norm (`tied_mlp_transformer.py`, `Attention`)

```python
# __init__ 안, o_proj 정의 뒤에 추가
        self.q_norm = RMSNorm(cfg.head_dim, cfg.norm_eps)
        self.k_norm = RMSNorm(cfg.head_dim, cfg.norm_eps)

# compute_kv 안: apply_rope 호출 전에 k를 정규화
        k = self.k_norm(k)
        return apply_rope(k, cos, sin), v

# forward 안: apply_rope 호출 전에 q를 정규화
        q = self.q_norm(q)
        q = apply_rope(q, cos, sin)
```

`RMSNorm`은 학습 파라미터가 없으므로 추가 비용은 무시할 수준.

#### 패치 2: NaN 가드 (`run100m.py`, `train` 루프)

```python
        gn = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        gmax = max(gmax, float(gn))
        if not torch.isfinite(gn):                      # <-- 추가
            opt.zero_grad(set_to_none=True); model.clear_quant()
            n_skip += 1
            print(f"  [skip] step {s}: non-finite grad ({n_skip}회째)")
            if n_skip > 20:
                print("  !! 20회 초과. LR을 낮추고 재시작하세요."); break
            continue
        opt.step(); opt.zero_grad(set_to_none=True)
```

루프 시작 전에 `n_skip = 0` 선언 필요.

#### 패치 3: torch.compile 안전한 어닐 (`tied_mlp_transformer.py`)

```python
# TLinear.refresh_quant — Python 분기 제거
    def refresh_quant(self, anneal=1.0):
        wq = ternary(self.weight, self.cfg)
        self._wq = wq + (1.0 - anneal) * (self.weight - wq).detach()

# TiedMLPTransformer.__init__ — 버퍼 추가
        self.register_buffer("_anneal", torch.ones(()), persistent=False)

# TiedMLPTransformer — set_anneal 추가, refresh_quant 수정
    def set_anneal(self, v: float):
        self._anneal.fill_(float(v)); self.cfg.quant_anneal = float(v)

    def refresh_quant(self):
        for m in self._tlinears():
            m.refresh_quant(self._anneal)
```

`run100m.py`의 `model.cfg.quant_anneal = ...` 를 `model.set_anneal(...)` 로 교체.
`evaluate()` 안의 두 곳도 동일하게 교체.

#### 패치 4: warmup 비율 (`run100m.py`)

```python
    warm = max(5, min(steps // 10, 100))     # 기존: max(20, steps // 50)
```

기존 식은 짧은 런에서 warmup이 학습의 50%를 차지했다.

#### 패치 5: 합성 데이터 캐시 무효화 (`run100m.py`, `prepare`)

```python
    if meta_p.exists() and name != "synthetic":   # 합성은 매번 재생성
```

생성 로직을 바꿔도 낡은 바이너리를 재사용하던 버그. 합성 구절 수도
512 → 50,000으로 늘려야 함 (2-8 참조).

#### 패치 6: 합성 데이터에서 판정 억제 (`run100m.py`, `compare`)

합성 데이터일 때는 손실 격차 판정 대신 "품질 판정 불가" 경고를 출력.

## 6. 다음 세션 시작 시 할 일

### 순서

1. **패치 1~6 적용** (위 코드 블록)
2. **파이프라인 동작 확인** (합성, 컴파일 포함)
3. **LR 탐색** — 200스텝씩 3개 LR을 짧게 돌려 발산 여부만 확인.
   3시간짜리를 통째로 날리지 않기 위한 필수 단계.
4. LR 확정 후 300M 본 실행

### 명령줄

```bash
# (1) 파이프라인 동작 확인 — 컴파일 포함
python run100m.py all --tiny --data synthetic --tokens 2M --steps 40 \
    --micro-bs 4 --seq 128 --accum 2 --eval-every 20 --compile

# (2) 데이터 준비 — 이미 300M ko-en 바이너리가 있으면 생략됨
python run100m.py prepare --data ko-en --tokens 300M

# (3) LR 탐색 (각 15~20분)
python run100m.py train --arch tied --steps 200 --micro-bs 8 --seq 1024 \
    --accum 16 --lr 1e-3 --eval-every 100
python run100m.py train --arch tied --steps 200 --micro-bs 8 --seq 1024 \
    --accum 16 --lr 6e-4 --eval-every 100
python run100m.py train --arch tied --steps 200 --micro-bs 8 --seq 1024 \
    --accum 16 --lr 3e-4 --eval-every 100
# |g| 가 10을 넘지 않고 loss가 단조 감소하는 가장 큰 LR 선택

# (4) 본 실행 — 체크포인팅 켬(--no-ckpt 없음) + 유효배치 131K + 컴파일
python run100m.py all --data ko-en --tokens 300M --steps 2289 \
    --micro-bs 8 --seq 1024 --accum 16 --lr <탐색결과> \
    --eval-every 100 --compile

# 중단 시 재개
python run100m.py train --arch tied --steps 2289 --resume [나머지 동일]

# 비교
python run100m.py compare
```

### 실행 중 감시할 것

1. `|g|`가 10을 넘는가 → 넘으면 즉시 중단, LR 절반
2. `anneal`이 0.00 → 1.00으로 매끄럽게 올라가는가
3. `[skip]` 메시지가 뜨는가 → 몇 회 이내면 정상, 반복되면 LR 문제

### 판정 기준

`compare` 출력의 **손실 격차** 하나만 본다.

- `≤ +0.07` → 아키텍처 성립. g를 6, 8로 올려가며 한계 탐색
- `+0.07 ~ +0.15` → prelude/coda를 3+3으로 늘리거나 g=2로 후퇴
- `> +0.15` → `|g|max` 먼저 확인. 10 이상이면 학습 문제지 아키텍처 문제 아님

메모리 감축(1.82배)은 이미 확정값이라 측정 대상이 아니다.
**이 실험은 그 감축의 대가가 얼마인가만 잰다.**

## 7. 로드맵 (100M 검증 이후)

1. **g 스윕** — g=4에서 6, 8로 올리며 손실 격차 곡선 확보
2. **어텐션 g=2** — 메모리가 더 필요하면. 논문이 비싸다고 지목한 영역
3. **1.7B 확장** — 한/영 64k 토크나이저 + factorized E=512
   - 목표: Bonsai 1.7B(471MB) 이하 용량으로 dense 1.7B 품질 85% 이상
   - **주의: Qwen3-1.7B가 아니라 동일 토큰 예산의 자체 dense 기준선과 비교**
4. **KV 추가 압축** — CLA2 위에 KDA 3:1 하이브리드 + NoPE, 이후 4bit KV
   - 예상: 112 KB/token → 3.5 KB/token (32K 컨텍스트 3.50GB → 0.11GB)
   - 걸림돌: KDA는 GPU 전용 chunkwise 커널. CPU 커널 없음
5. **모드 제어 활성화** — `n_modes>1` + adaLN. 부족하면 mode_rank=32 추가,
   그 다음 RMoE식 GRU 라우터(약 0.7%)
6. **CPU 커널** — T-MAC/llama.cpp 계열. DeepGEMM의 융합·JIT 패턴 참조
7. **배포 최적화** — InfiniteHiP (학습 불필요, 드롭인)

### 미해결 최대 리스크

**삼진화와 타잉을 동시에 거는 조합은 아무도 검증하지 않았다.**
둘 다 용량을 줄이는데 가산적으로 합쳐질지 곱셈적으로 무너질지 데이터가 없다.
100M 검증 실험이 답할 첫 번째 질문이 이것이다.
